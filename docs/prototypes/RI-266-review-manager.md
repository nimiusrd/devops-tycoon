# RI-266: 投資を任せ、レビュー順だけを選ぶ責任者モード

Issue: [#662](https://github.com/nimiusrd/devops-tycoon/issues/662)。開始main: `d0e0b25bfbf65432fa2caebfec7c6666faad55ae`。判定: **再試作**（2026-11-18）。通常ランへの採用判断ではなく、隔離APIと比較記録を残す。

## 仮説と今回の境界

投資を固定方針へ任せると、レビューを先に通す群と待たせる群の判断に集中できるか。高価値の複雑変更4件と通常の定型変更8件を同じシニアが処理する。重要群の早期出荷と通常群の件数・待ちを比較し、期限が伸びたとき同じ方針が有利かを調べる。

今回は操作APIと実sim比較が成立する最小試作。ブラウザの入口・完成UI・人間プレイ評価はない。通常画面への見せかけの統合は行わない。#538 の通常経営委任、独自CIモデルの `reviewDepth` / `reviewPriority`（#558 / #561、関連PR #1112）とは別の実装で、それらを実simと呼ばない。RI-188で見送った廃止・維持費・返却益も導入しない。

## 既存ルールと試作で追加したルール

既存の処理は `createOrgState` / `createSprint` / `playCardFromHand` / `stepSprint` / 内部の `reviewOne` / `summarizeSprint` を使用する。出荷のAI倍率・コンボ、手戻り・障害確率、シニア消費・自然回復、炎上・自動鎮火・延焼、期限切れの未出荷打ち切りを変更しない。

試作で追加するもの:

- 開始時に一度だけ「自動テスト強化」レベル1を自動購入・発動。予算24から既存価格18を差し引き、既存発動処理が集中力8から3を課金する。残予算6・集中力5。既存カードの効果（品質+10、セキュリティ+8、手戻り加算−0.15、障害率×0.8、開発速度×0.95）を使用する。購入契機と固定方針が新設ルールで、通常ショップの自動購入化ではない。
- `viewReviewManager` は開始前からカード・契機・全費用・効果を返し、閲覧は無消費。開始後は `investmentLog` で結果を確認できる。予算不足は無課金で `failed` となり、再開始できない。
- 開始用fixtureはレビュー待ち12件。`id % 3 === 2` の4件を高価値complex、残りをroutineとし、全件AI支援済みの状態から始める。過去の投入・実装履歴を主張しない。`createSprint` の乱数消費位置を保持した後、この固定盤面を設定する。通常のBacklogからの流入時間は比較しない。
- 人間が指定できる判断は、各tick開始時のレビュー待ちIDの完全な順列だけ。順序指定と1tick進行は同じ入力に束ねる。順序変更そのものは集中力0（役割の基本操作）。深度・配分・投資選択・通常介入は受け付けない。
- 配列のレビュー位置だけを入れ替え、既存工程を1tick進め、終了後はID順へ戻す。未指定なら毎tick ID順。手戻りから戻った仕事は次tickに選べる。既存の延焼先もそのtickのレビュー順に従う。通常simの順番の意味を隠して別の独立レビュー計算にしない。

初期組織は標準シナリオ（品質60、シニア体力100等）、AI有効。投資後品質70・セキュリティ68。完全な組織値・盤面・設定・乱数位置・資源は比較JSONの `initial`、操作全列は `inputs`、支出は `investmentLog`、結果は `result` に残す。全方針で自動投資を同一にし、投資効果そのものの因果推定は行わない。

## 再現と指標

```sh
devcontainer exec --workspace-folder . node scripts/ri266-review-manager-evaluation.mjs
devcontainer exec --workspace-folder . npm test -- src/prototypes/reviewManager.test.ts --maxWorkers=1
```

[比較JSON](review-manager-comparison.json) は3seed（`RI-266` / `RI-266:1` / `RI-266:2`）×4期限（12 / 24 / 48 / 60tick）×3固定方針、合計36条件。期限だけを変え、資源・仕事・投資は固定する。

| 方針 | 入力規則 |
| --- | --- |
| none | 順番に介入せずtickを進める対照。通常simのID順 |
| important-first | 毎tick、高価値群→通常群、群内ID順 |
| ordinary-first | 毎tick、通常群→高価値群、群内ID順 |

`delivered` は実simの出荷ポイント。群別 `done` は出荷済み件数、`completedBaseValue` は既存 `taskValue` の合計で、コンボ・AI倍率を配賦した出荷ポイントではない。`reviewOccupancyTicks` はtick開始時にレビュー待ちの各タスクへ1加算し、処理したtickも含む。炎上・手戻りの滞在時間は含まない。

群別 `reviewAttempts` は実reviewOneの出荷・手戻り・レビュー起因の点火から数える。延焼起因の点火をレビューに数えない。`reviewHpDemand` は試行数×既存のレビュー費用で、体力0のclamp・自然回復前の要求量。`autoContainHpSpent` は当該群の自動鎮火ログの実費。実残体力は全体の `seniorHp` を見る。単一の恣意的総合点は設けない。

## 結果と採否

seed `RI-266` の例。群別完了は「重要 / 通常」、待ちは同じ順。

| 期限 | 方針 | 実出荷 | 群別完了 | 群別待ち | 残体力 |
| ---: | --- | ---: | --- | --- | ---: |
| 12 | 無介入 | 78 | 1 / 5 | 37 / 64 | 91.75 |
| 12 | 重要先行 | 138 | 3 / 3 | 14 / 87 | 91.75 |
| 12 | 通常先行 | 34 | 0 / 6 | 48 / 53 | 91.75 |
| 24 | 無介入 | 130 | 2 / 8 | 48 / 79 | 87.95 |
| 24 | 重要先行 | 159 | 3 / 7 | 14 / 113 | 87.95 |
| 24 | 通常先行 | 164 | 3 / 7 | 73 / 54 | 87.95 |

3seedとも12tickでは重要先行の出荷が上、24tickでは通常先行が上だった（24tickの重要先行は159 / 177 / 217、通常先行は164 / 300 / 300）。重要先行は通常群の待ちを増やし、レビューによる体力要求も重要群へ先に配分する。期限の延長で、コンボを積んでから高価値を出す順序が上回る例が得られた。ただし乱数をどのタスクに割り当てるかも変わるので、差をコンボだけの因果効果とは断定しない。

無介入でも12tickで6 / 6 / 7件を出荷し、即敗北にはならない。60tickでは `RI-266` と `RI-266:1` は全12件を完了するが `RI-266:2` は11件で打ち切り。全36条件で同じseed・期限の方針間の実残体力は一致した。群への負荷配分は変わっても、消耗全体が軽くなるという仮説の裏付けは得られていない。固定方針の結果で、人間の適応行動・楽しさ・最適戦略・本番係数を証明しない。

**再試作**: 二群の成果と待ちを順序で変え、期限により有利さが反転するAPI上の判断は確認できた。次は同じ固定投資・同じ仕事で、順序を理解して触れる最小UIと人間評価を設ける。終了条件は、プレイヤーが「どの群を先にしたか」「何を待たせたか」「投資の自動支出」「期限が伸びたら順を変える理由」を説明でき、操作しない判断も選べること。単に群別数値が違うだけで面白いとしない。評価未実施のためIssueはopenを維持し、PRは `Refs #662` とする。

## 保存・上限・本番境界と検証

試作専用ruleset `ri266-review-manager-v1` とversion 1。最大60tick、12タスク、seed128文字、成立入力61件（開始1+tick60）。入力に束ねた順序は最大12ID。保存はUTF-8で64KiBまで、入力の再実行は最大61回。復元は入力列を再実行してPRNGの内部状態チェックポイントまで照合する。無効入力、重複開始、完了/打切り/失敗後入力、異なるruleset、破損RNG、長過ぎる保存を拒否する。通常simのイベントは既存64件のring、fireEventsとtimelineはこの60tick・12タスクの実行上限内。保存には派生sim状態や履歴を丸ごと入れない。

通常の固定トラック・WinType自動判定・投資・介入・報酬・メタ・デイリー・通常セーブ/リプレイ・storage所有権は変更せず、試作に接続しない。`reward: 0` は隔離試作の無報酬を表す値で、通常報酬の計算変更ではない。本番採用時には順序入力の保存互換・リプレイ・ルールセット更新・UI/実WebGL検証を別途設計する。

標準 `.devcontainer/devcontainer.json` で `devcontainer up --workspace-folder .` を実行。Docker buildxのホストメタデータ書込みにsandbox権限が必要だったため、同じ標準設定で権限付き再実行し成功。GH feature省略の代替configは不使用。コンテナNodeは `v24.16.0`。

対象ユニット（9件）、`npm run build`、`npm run lint`、`npm run format:check` をDev Containerで実行する。対象ユニットは通常stepSprintとの逐次一致、順序指定の実処理、二群の差、RNGを含む全比較入力のJSON再開、二重課金/成果/報酬防止、成功/時間切れ/失敗後拒否、履歴・保存上限を検証する。API/文書のみのためローカルE2E・gallery・全体coverageは対象外。必須CIの全体unit/coverageと実WebGLを含むE2EはPRで確認する。人間プレイ評価は未実施。
