# RI-263: 指定時刻に必須3件を揃える顧客デモ

対象: #659 / 親: #548。採否: **再試作**。期限前の総出荷と指定3件の完成を分ける判断は数値上で確認できる。人間のプレイ評価は未実施で、本番採用は決めない。

## 既存試作との境界

RI-153 / #549 / PR #733 の `featureSets` は、個別出荷に加えて最後の必須仕事で機能完成と統合価値を記録する。RI-158 / #554 / PR #752 の `minimumRelease` は、必須1件の公開と追加部分の先送り・次期約束を比較する。両PRは開始時にマージ済みと確認した。既存文書と実装を照合している。

本件は1機能の加点や公開版の選択を再実装する案ではない。顧客が指定した3仕事を**デモ時刻に揃える**ため、任意仕事へ使える時間を譲る判断に絞る。出荷への完成ボーナス・先送り操作・製品モデルは持たない。デモの判定時刻と1戦の終了時刻を分け、遅れて完成した成果も出荷に残す。

## 着手前に公開する契約

純TSの `src/prototypes/customerDemoBoss.ts`、固定1戦のみ。`viewCustomerDemo(createCustomerDemoBoss('RI-263'))` が以下の条件を開始前から返す。閲覧は状態を変えず、返した配列やオブジェクトの編集も内部へ届かない。

| 仕事 | デモ必須 | 工数 | 完成時の出荷 |
| --- | --- | ---: | ---: |
| api | 必須 | 2 | 4 |
| screen | 必須 | 2 | 4 |
| data | 必須 | 3 | 4 |
| urgent | 任意 | 2 | 4 |
| bulk | 任意 | 2 | 8 |

- デモ期限7tick、戦の終了10tick、作業者1枠・1工数/tick、総作業予算10、初期信頼6。依存・手戻り・隠れた工数はない。
- 優先指定は時間を消費しない。`step` はプレイヤー操作ではなく経過tickで、時間と作業を進める。優先仕事が完了したら既定順 bulk → api → screen → urgent → data から未完了を選ぶ。無操作でもシミュレーション時計を進めれば出荷する。資源切れ・全仕事完成後も終了時刻までは時計が進む。
- デモは期限tickの作業を含めて一度だけ評価する。3件すべて完成で成立。未完成仕事の途中工数にはデモ評価を与えず、完成した必須1件につき部分評価2（0/2/4/6）を残す。
- 必須の未完成1件につき信頼2低下、信頼0で下げ止まる。信頼0や最後の1件未完了で戦を強制終了しない。出荷・途中進捗・残工数は没収しない。
- 総出荷は完成した仕事の出荷だけ。部分評価は別単位で、総出荷へ加算しない。期限後の完成は総出荷を増やすが、デモ成立・部分評価・信頼低下を遡って変更しない。
- 入力は単調な `seq` を持ち、受理された入力を保存する。同じ入力の再送・古い番号・未来の番号・完了済み仕事の指定は無変化。優先指定だけを繰り返しても作業は進まない。

## 同条件・異なる優先順

同seed、同初期資源、同工数・期限・係数を使う。一つの仕事が終わるまで作業する固定方針で、途中の適応的判断や人間の楽しさの証拠にはしない。

| 方針 | 優先順 | 期限時の総出荷 | 必須完成 | 部分評価 | 期限時の任意出荷 | 信頼低下 | 10tick時の総出荷 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| デモ集中 | api → screen → data → bulk → urgent | 12 | 3 | 6 | 0 | 0 | 20 |
| 同量対照 | api → screen → urgent → data → bulk | 12 | 2 | 4 | 4 | 2 | 16 |
| 総量優先 | bulk → urgent → api → screen → data | 16 | 1 | 2 | 12 | 4 | 20 |
| 無介入 | bulk → api → screen → urgent → data | 16 | 2 | 4 | 8 | 2 | 20 |

デモ集中と同量対照は総出荷12が同じでも、3件完成と2件完成でデモ成立が異なる。同量対照のdataは期限時1/3工数で、残り2。tick 9で完成してもデモ記録を上書きしない。デモ集中は期限まで任意出荷を譲り、総量優先に比べ期限時の出荷4・任意出荷12が少ない。一方、総量優先は必須2件が間に合わず信頼4を失い、10tickでもdataが残り1工数。デモ集中の10tickではurgentが1/2工数で、出荷4が未確定となる。

この機会費用は同条件の別入力列との差として示す。未出荷価値をすべて「実現できた損失」とは呼ばない。個々の未完成仕事は進捗・残工数・未確定の出荷を併記する。総出荷と信頼・部分評価を恣意的な総合点にまとめず、どちらを重視するかは未確定のまま残す。

## 一要因ずつの感度

基準以外はデモ集中と総量優先を比較し、その他の係数・順序・seed・初期資源は同じにする。

| 変更条件 | 確認する境界 |
| --- | --- |
| デモ期限6 | デモ集中でもdataが残り1、必須2件の部分評価4。期限7の成立へ反転する |
| デモ期限8 | デモ集中は成立、総量優先は必須2件・data未着手。期限時総出荷は12対20 |
| デモ期限9 | 総出荷20対20でも必須3件対2件。デモ集中の任意出荷8と総量優先12が競合する |
| data工数4 | デモ集中のdataは期限時3/4で未完成。1工数の増加が成立を切る |
| 作業予算6 | デモ集中でも必須2件。資源切れ後の時計は進み、途中進捗を保持する |
| bulk出荷4 | 基準の8から4へ。任意出荷の機会費用を縮めても成立条件・投入工数は変わらない |
| 未完成信頼低下0 | 総量優先の低下は0。総出荷を重視する選択がしやすくなるが、部分評価・成立は変えない |
| 未完成信頼低下4 | 総量優先は未完成2件で信頼6を失う（0で下げ止まり）。デモ集中は低下0 |

乱数は使わず、seedは再生の識別子として保存する。複数seedによるばらつきを装わず、期限・工数・予算・任意出荷・代償の感度を記録する。

## 再現と検証

`customer-demo-boss-comparison.json` に各条件の初期状態、全入力列、係数、期限時評価、最終出荷、資源、未完成の代償を保存する。Node 24のDev Container内で再生成する。

```sh
devcontainer exec --workspace-folder . node scripts/customer-demo-boss-comparison.mjs
devcontainer exec --workspace-folder . npx prettier --write docs/prototypes/customer-demo-boss-comparison.json
devcontainer exec --workspace-folder . npm test -- src/prototypes/customerDemoBoss.test.ts --maxWorkers=1
devcontainer exec --workspace-folder . npx tsc -p tsconfig.json --noEmit
devcontainer exec --workspace-folder . npm run lint
devcontainer exec --workspace-folder . npm run format:check
```

対象テストはJSONの再生成一致、同seed・入力列の再生、毎入力のJSON保存再開一致、元状態と閲覧の不変性、資源保存、完了重複計上防止、部分完成、期限境界、期限後の継続、重複入力、無介入進行、資源切れ・全仕事完了を検証する。version 1の信頼済み内部JSONのみを扱い、外部JSON検証や通常セーブの移行は対象外。

本番・UI・Pixi・保存・ruleset・通常のWinType自動判定・SPEC・製品モデルへは接続しない。デモ成立から通常の勝利種別を選ばず、未成立から通常ランの敗北を確定しない。本番導入を検討するなら、デモの指定条件・期限通知・期限時評価の保存と通常勝敗との関係を別Issueで設計する。純TS独立試作なので、ローカルの追加通常ランsmoke・E2E・galleryは対象外。必須の全体unit/build/E2EはPRのCIで確認する。
