### RI-64 独立状態を持つ複数チーム運営

現在の全社・部署ビューは、プレイヤーチームの状態を基準に他チームを決定論的に合成している。各チームが独立して成長・悪化し、全社施策と特定チームへの介入を使い分けるという第4.7章の要件を満たすよう再設計する。

受入条件:

- チームごとに安定したIDと、人員、能力、AI習熟度、士気、技術的負債、レビュー能力、障害傾向などの状態を持つ。
- チーム状態はラン中・四半期継続・セーブ復帰・リプレイで維持される。
- 非選択チームは粗い決定論シミュレーション、選択中チームは詳細なスプリントとして進行できる。
- 全社、部署、チームの施策スコープを分離し、効果が対象チームへ適用される。
- 特定チームへ入り込む判断に、集中力、期間、他チームを見られない機会損失などの制約を持たせる。
- すべてのチームを部署ビューから選択して状態確認でき、選択チームの現場へドリルダウンできる。
- チーム結果が部署・全社指標へ集約され、上位施策が下位状態へ波及する。
- seed再現性、集約不変条件、チーム切替、保存・復元をVitestとPlaywrightで検証する。

実装は次の単位に分割する。

1. `RunState`に永続的なチーム状態と選択チームを導入する。
2. 粗粒度チームシミュレーションと部署・全社集約を導入する。
3. 全社／部署／チーム施策と「入り込む」コストを導入する。
4. 任意チームへのドリルダウン、保存、リプレイ、E2Eを接続する。

### RI-65 カードコレクション画面

現在はラン中の所持デッキと、研修方針画面の解放済みカードだけを一覧できる。ラン外で全カードと収集状況を確認できる図鑑を追加する。

受入条件:

- `CARD_DEFS`の全カードをレアリティ別に一覧表示する。
- 解放済み／未解放を区別する。
- 解放済みカードはコスト、効果、タグ、未解放カードは解放条件を表示する。
- 解放済みカードから研修方針を確認・変更できる。
- キーボード操作と狭い画面に対応し、一覧・詳細・フィルターをE2Eで検証する。

### RI-66 ペーシング規定の統計検証補強

通常スプリントの代表seedとボス上限は検証済みだが、第3.1章全体の回帰検知を補強する。

受入条件:

- ボススプリントの90〜180秒帯を、単なる定数ではなく代表seedの分布で検証する。
- 1四半期10〜15分、1ラン15〜45分の目安を自動操作モデルで集計する。
- 1スプリントあたり介入3〜8回の余地を、利用可能回数または介入ポリシーの統計で検証する。
- ランダムな単発外れ値ではなく、p50・p90など安定した指標を採用する。

### RI-67 オンボーディングとシニア燃え尽きの断絶

Easy でも無介入・素直プレイだと第1四半期スプリント2でシニア燃え尽き（`seniorBurnout`）敗北する。スターター編成はシニア1人が唯一のレビュアーで、レビュー負荷が集中する（`src/data/members.ts`）。生存の決定打は編成での「レビュー分散」だが、チュートリアル（`src/ui/tutorial.ts`）は介入バー・レビュー渋滞・コンボのみで、編成でのレビュー分散もシニア体力の概念も教えない。実測と経緯は[playtest-findings.md](./playtest-findings.md)参照。

受入条件:

- 初見プレイヤーがシニア燃え尽きを回避する手段（編成でのレビュー分散、andon 等）へ導かれる。
- チュートリアルまたは盤面・HUD の警告で、シニア体力と燃え尽きリスクを事前に伝える。
- Easy の序盤（第1四半期）で、標準的な操作理解のプレイが2スプリントで即敗北しない。
- 難易度別のシニア消耗・レビュー負荷の妥当性を自動操作モデルまたはユニットテストで検証する。

### RI-68 四半期レビュー Delivery KPI のスケール不整合

四半期レビューで Delivery 目標（概ね1スプリント相当）に対し、四半期累計 `quarterTotals.delivered` を比較しているため、看板KPI「出荷ポイント＝勝利条件の進捗」が常に自明達成となる（実測: Q2 目標20 vs 実績1693）。目標生成は `src/sim/run/quarterReview.ts` の `deliveryTarget`。

受入条件:

- `deliveryTarget` と判定値の単位（1スプリント平均 vs 四半期累計）を一致させる。
- Delivery 目標が四半期を通じて意味のある達成／未達の分岐を生む。
- 実際に効く制約（Morale・Quality・Incident・燃え尽き）が勝敗条件として表示で伝わる。
- 代表 seed で目標と実績の分布が妥当な範囲に収まることを検証する。

### RI-69 スプリント上部操作バーと盤面の重なり

デスクトップ幅（1440px 実測）で、上部の操作バー（`通常スプリント / ❚❚ / 1x-2x / 渋滞メーター / 炎上タイマー / COMBO`）が盤面キャンバス上端と重なり見切れる。対象は `src/ui/SprintScreen.tsx` 周辺のヘッダ・盤面レイアウト。

受入条件:

- 主要なデスクトップ幅で操作バーと盤面が重ならない。
- `npm run gallery` またはE2E視覚回帰で重なりの再発を検知する。

### RI-70 モバイルのスプリント操作性

390px 幅で横スクロール・崩れは無いが、縦積みKPIカードの下に盤面とアクションバーが来るため、時限スプリント中に盤面と介入ボタンへスクロールが必要になる。

受入条件:

- 狭幅ではKPIを折り畳み／要約し、盤面とアクションバーを1画面に収める。
- 狭幅でスプリント中に介入バーへ到達できることをE2Eで検証する。

### RI-71 favicon 未設定による 404

`index.html` に favicon 宣言が無く `public/` にも実体が無いため、`/favicon.ico → 404` が毎ロード時にコンソールへ出る。

受入条件:

- `<link rel="icon">` とアイコン配置で 404 が出ない。
- ブラウザタブにアイコンが表示される。

### RI-34 ローカル完結の将来拡張

外部API・共有バックエンドは対象外。着手時に個別IDへ切り出す。

- ツール別シナリオ
- 組織シナリオ共有（ローカルファイル／文字列による入出力）
- 組織診断ダッシュボードの時系列・部門比較
- 四半期レビューの高度化

カードデッキの研修方針、デイリーラン、AI導入失敗図鑑、レビュー地獄リプレイ、「なぜ燃えたか」は実装済み。社内LT／経営プレゼンモードと外部サービス連携は対象外。

## 2. 確定した判断

2026-07-20のSPEC監査で以下を確定した。

- Zustandは要件ではない。`RunEngine`を状態の正本とし、決定論、保存、リプレイ、UI同期を満たせばよい。
- 巨大組織は表示用の合成チームではなく、独立状態を持つ複数チームとして扱う。
- カード、レリック、進化ノードのSPEC内の具体例は方向性であり、実装データとの差を許容する。
- カードはラン外のコレクション画面で一覧・解放状況を確認できるようにする。

## 4. バックログ運用

- IDは`RI-NN`の連番とし、欠番を再利用しない。
- 状態は`未着手`、`進行中`、`保留（要判断）`、`完了`を使う。
- 1項目は原則1PRで完了できる大きさに分割する。エピックは受入条件と分割順を記載する。
- 完了時は詳細な実装日誌を追記せず、上の完了要約と[spec-mapping.md](./spec-mapping.md)を更新する。
