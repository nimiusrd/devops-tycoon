# RI-298 条件付き挑戦コード

対象: [#694](https://github.com/nimiusrd/devops-tycoon/issues/694)。採否: **再試作**。実行契約の最小試作を保存し、本番統合・編集画面・共有UI・人間プレイ評価は未実施。Issueはopenを維持する。

## 仮説と今回の境界

同じ開始条件でも強いカードの発動を禁止し、追加課題へ集中力を振り分ける判断を友人に渡せる、という仮説。カードを使う利益、現場介入へ集中力を使う利益、その機会費用を説明できることが次の評価対象になる。

既存の `StartRecipe` がseed・難易度・試練・シナリオ・研修方針を表す。本試作は既存 `parseStartRecipe` を読み、別形式の版付きJSONに次の2要素だけを加える。#669の新規schemaや他の試作には依存しない。

- `restrictions: [{ kind: "forbid-activation", cardIds: [...] }]`: **発動禁止**。候補・所持・研修方針の禁止ではない。ドラフト、購入、イベントによる獲得と手札交換は許可する。禁止札のbaseline加算を含む効果は、発動そのものを拒否することで適用されない。
- `objective: { kind: "successful-interventions", minimum: N }`: 成功した実 `RunEngine.dispatch` 回数がN以上かを測る。失敗・クールダウン中・カード発動・交換は数えない。対象は通常の現場介入全種類で、対象指定を伴わない自動選択のみ対応。

本試作はローカルの全カード・全レリックを候補とする実験用カタログを使い、受信側メタの解放状態を読まない。通常タイトルの未解放チェックとは別契約である。研修方針と禁止札が重なっても矛盾ではない。所持と発動を区別する試作なので許可する。

## 形式と拒否

コードの識別子は `format: "devops-tycoon-challenge"` / `version: 1`。試作ruleset `ri298-activation-ban-v1` と、実バランスの版・指紋を必須にする。完全なコード例は比較JSONの `runs[].save.code` に格納する。

未知キーを黙って除去せず、未知カード、空の禁止リスト、重複ID、複数の制限（allow/denyの矛盾を含む）、未対応制限・課題、範囲外の閾値、壊れた既存レシピ、版・ruleset不一致を理由付きで拒否する。制限は一種類一件だけであり、複数制限の優先順位や合成規則は作らない。

上限は `CHALLENGE_LIMITS` が正本。コード16,384文字、seed128文字、入力256文字、受理履歴4,096件、再開JSON524,288文字、JSON入れ子16段、課題閾値1〜1,000。禁止カード数は現行カタログ件数まで。IDは既存の有限カタログに限定する。自由記述、作者履歴、追加タスク、リプレイフレームの直接入力は持たず、盤面の仕事・組織・固定トラックは実エンジンの生成規則に従う。入力上限に達したセッションは保存・閲覧できるが、それ以上は進行できない。

## 専用APIと抜け道

`src/prototypes/challengeCode.ts` の `openChallenge(raw)` / `resumeChallenge(raw)` は、凍結した `act(rawInput)` / `view()` / `save()` だけを返す。実エンジンはクロージャ内に保持する。継承、エンジンの公開、任意メソッド名の動的呼出し、外部フレームのhydrateは使わない。

発動入口は `act({ type: "playCard", deckIndex })` の1か所だけ。呼出し時の実デッキに対してIDを照合し、イベントで増えたカードや同じIDの別indexにも適用する。`allowedCards` は設定しない。同機能が候補だけを絞り、イベント獲得や発動を強制しないことを禁止実装の根拠にしない。

操作はJSON文字列を渡す。利用例:

```ts
const opened = openChallenge(JSON.stringify(code));
if (!opened.ok) throw new Error(opened.reason);
opened.value.act(JSON.stringify({ type: 'begin' }));
opened.value.act(JSON.stringify({ type: 'dispatch', actionId: 'pairReview' }));
opened.value.act(JSON.stringify({ type: 'tick' })); // 実時間の1000msを固定ステップで進行
const saved = opened.value.save();
const resumed = resumeChallenge(saved);
```

準備開始、tick、発動、交換、現場介入、結果確認、ドラフト選択/スキップ、進化フェーズ終了、イベント選択、カード購入、退店、休息heal/repay、採用hire/skip、四半期レビュー/目標修正を実エンジンへ渡す最小API。編成変更、組織レバー、進化購入等の全操作を提供した完成UIではない。無効な操作・未知入力・二重開始・二重購入は受理履歴へ入らず、資源・課題・RNGを消費しない。完了後の操作も拒否し、結果の再取得には副作用がない。

## 勝敗・報酬・保存再開

通常の固定トラック、ボス、勝敗、自動WinType判定を実エンジンに任せる。追加課題は別結果であり、課題達成済みの敗北も表せる。通常のRunKindをUI向け結果へ渡さず、`mode: "challenge-prototype"` として返す。結果は常に `rewardEligible: false` / `metaReward: 0` / `dailyReward: 0`。通常meta/daily/save/replay/storageの読書きを行う入口は作らない。課題達成を独自のWinTypeに追加しない。

専用保存は `format: "devops-tycoon-challenge-save"` / `version: 1`。初期コード、全受理入力、実測値を含む状態のSHA-256、内部状態のSHA-256、現在のスプリントRNG位置を保存する。再開時は現行の実エンジンで入力を再実行し、内部状態・累算ms・課金台帳・RNGと課題実測を照合する。入力や保存状態を直接hydrateしないので、禁止発動を履歴へ挿入しても拒否される。通常StartRecipe/replay parserがこの形式を拒否することも検証する。

ハッシュは整合性チェックであり、署名や対戦用の不正防止ではない。任意の作者がコードと正当な全入力を作り直すことは可能。長期互換・移行は未対応。実simの式/乱数消費順変更時は通常バランス版、試作規則変更時は専用rulesetを更新して旧形式を拒否する。

## 比較と再現

`devcontainer exec --workspace-folder . node scripts/ri298-challenge-code-evaluation.mjs` で `challenge-code-comparison.json` を再生成する。通常スコアや固定の手入力点数を使わず、実RunEngineを公開APIから決着まで動かす。

条件は easy / default / 試練なし / 優先ai-guideline / ai-guideline発動禁止。seedは `ri298-1`〜`ri298-5`。各seedの組織・ロスター・予算60・初期目標を同じにし、「手札を先に発動」「さらに可能な時だけpairReview」の固定方針を比較する。ドラフト先頭、ショップ購入なし、休息heal、即時採用/即敗北を避ける先頭イベント肢、最初の修正案を使う。カード以外に適応的な状況判断は加えない。

純消費は各成功操作直前/直後の実集中力の差を積算する（レリックの割引や回復を含む）。出荷には現行の粗粒度チーム・イベント成果も含まれる。比較JSONには資源・規則・入力列・実測・費用・終端状態・RNGを保存する。閾値5の10ランに全入力を残し、閾値1/5/10の30ランの感度結果を別配列へ残す。

カードのみの課題実測は全seedで0。併用方針は閾値1/5で5件とも達成、閾値10で4件達成。閾値を変えても同じseed/方針の出荷・費用・通常勝敗は変わらず、課題結果だけが変わる。全30ランは通常勝敗で敗北した。禁止の強さや勝利できる代替策の比較は今回の固定方針だけでは評価できない。

## 判断と次の終了条件

**再試作**。形式の識別、発動強制、課題の実測と再開、報酬隔離はAPIで確認できる。一方、「回数を稼ぐ」ことが有効な挑戦か、集中力配分が理解できるか、友人へ渡して再挑戦したいかは未確認。人間プレイ・編集/説明UIの評価は実施していない。試作PRのマージは本番採用やIssue完了を意味しない。

次は勝利可能性を確認した同一条件で、禁止札に対する代替手段と介入の機会費用が説明できる最小プレイ文脈を作る。人間が条件を読み取れること、禁止理由と実操作が一致すること、課題だけを稼ぐ以外の判断が記録されることを終了条件にする。条件を達成できなければ課題種類を再検討する。本番統合は解放カタログ、操作UI、通常報酬境界、互換/上限、SPEC・受入条件を別単位で設計する。
