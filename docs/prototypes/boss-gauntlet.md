# RI-267 ボス連戦の実 sim 試作

Issue: [#663](https://github.com/nimiusrd/devops-tycoon/issues/663)。判断は **再試作**。通常ラン・UI への統合、人間プレイ評価は未実施。試作のマージや固定方針の成績を、本番採用・面白さ・人間の適応行動の証明とはしない。

完成した会社の得意不得意を短い危機の連続で試す仮説を検証する。選ぶ手は、連戦で一度だけ使える残業号令を初戦/後半のどちらに使うかと、初戦後に費用を払って体力を回復するか。回復は余力を買う一方で残予算を減らす。残業号令は既存 sim の速度向上と HP・士気・集中力の代償をそのまま使う。

## 対象と再現方法

`src/prototypes/bossGauntlet.ts` と専用テスト、比較スクリプトだけに隔離した。既存 `handExchange.ts` / `sprintLoadout.ts` と同様に `createSprint` / `stepSprint` / `applyAction` と `createRngFromState` / `getRngState` を使う。固定値の採点モデルではなく実際のタスク流入・手戻り・事故・出荷・組織指標を進め、`summarizeSprint` / `evaluateBoss` / `evaluateLose` で判定する。

開始 main は `d0b5b72d57721f2471202d9b1942d1c300731c5c`。同じコード・seed・入力列・係数で再現する。参照した関連 PR は #744 / #746 / #876 / #1118（すべて merged）。通常ランの手札交換は本番導入済みだが、連戦の開始・持越し規則は存在しなかった。

```sh
devcontainer exec --workspace-folder . node --version
devcontainer exec --workspace-folder . node scripts/ri267-boss-gauntlet-evaluation.mjs
devcontainer exec --workspace-folder . npm test -- src/prototypes/bossGauntlet.test.ts --maxWorkers=1
```

通常の `.devcontainer/devcontainer.json` で起動し Node `v24.16.0` を確認。GitHub CLI feature を省く代替 config は使っていない。起動時はホストの Docker buildx 管理領域へのアクセスに昇格を要した。プロジェクトのコマンドは専用 worktree の Dev Container 内で実行した。

比較データは [boss-gauntlet-comparison.json](./boss-gauntlet-comparison.json)。seed は `RI-267:1`〜`RI-267:8`。標準/仕事量増/回復量半減/回復費倍増/時間費4倍 × 2ビルド × 4方針 × 8 seed = 320条件。JSON の `resultColumns` / `battleColumns` / `orgColumns` で圧縮列を定義し、各実行の全入力列（空白区切り）、各戦の前後状態・成果・実費と連戦総費用を保存する。平均は説明用に小数3桁へ丸め、各実行の費用は整数 cents を保持する。未到達の第2戦を成果ゼロの実測に置き換えない。

## 持込みの契約

任意の通常セーブから戦力は抽出しない。`gauntletPreset` が生成する次の2種だけを `validateGauntletImport` が全キー・全値で照合する。欠損、余計なキー、カード重複、改変した体力/予算/使用回数を拒否する。開始後は入力を複製し、呼び出し元と状態を共有しない。

| 項目 | 共通の値/検証 |
| --- | --- |
| 持込み版 | `version: 1`、ビルドIDは `speed` / `resilient` のみ |
| 組織全項目 | AI有効、依存40、リテラシー65、テスト40、文書40、品質45、セキュリティ50、士気65、HP70、負債22、累積出荷0に下記カードの恒久加算を一度だけ適用 |
| 完成施策 | 各3枚、全てlevel 2 / baselineAppliedLevel 2。ID・レベル・順序・適用済み状態を含め照合 |
| 初期予算 | 6000 cents = 60。通常ランの予算や報酬とは別資源 |
| 切り札/回復 | 残業号令1回、戦間回復1回。初戦開始前には回復しない |

| ビルド | 完成施策 | 適用後の差分 |
| --- | --- | --- |
| speed（実装・レビュー能力） | copilot / hire-senior / review-bot | 品質63、依存47.5、セキュリティ42.5 |
| resilient（検証・安全性） | auto-test / docs / pr-size-limit | 品質67.5、依存40、セキュリティ69.5 |

完成施策の乗算効果は両戦で有効。恒久加算は戦間に再適用しない。通常ランの「手札から発動したカードだけが有効」という取得/発動ループを再現したものではなく、完成ビルドの比較用入力である。両ビルドは同じ3枚・level 2・持込み予算だが、通常ランでの取得価格/成長時間まで同額に揃えた比較ではない。レリック・編成・文化・メタ解放は持ち込まない。

## 連戦順と持越し/リセット

順序は専用の `GAUNTLET_ORDER = [big-release, security-audit]`。通常ランの四半期番号や固定トラックを進めない。既存定義の突破条件（大型: 当該戦の出荷90以上、監査: 負債40以下・品質50以上）、仕事量倍率・事故率倍率を使用する。時間切れは突破失敗。現在の2ボスの仕事量/事故率倍率はいずれも1。

各戦は共通のランダムタスク構成、Backlog流入、Coding枠4、集中力8、仕事36件、上限180 tick、最小完了tick 0。通常ボスの58件床・115 tick下限はこの短い比較では使わず、本番の所要時間は評価しない。ステージごとに `${seed}:battle:${stage}` で開始し、以後は消費後のRNG状態を保存する。同seedなら両ビルドの初期タスク抽選が一致し、その後の入力・確率結果による消費差は実simに従う。

| 戦間で保持 | 新しい戦でリセット |
| --- | --- |
| 負債、HP、士気、依存度、品質、テスト、文書、リテラシー、セキュリティ、AI有効、累積出荷 | タスク全体、進捗、炎上、手戻り回数、当該戦metrics・コンボ・イベント・タイムライン |
| 残予算、各戦の実費、回復実費、入力ログ、終了した戦の前後状態 | 集中力8、クールダウン、時限効果、手札山、tick 0 |
| 完成施策、残業号令使用済み、戦間回復使用済み | 新しい戦専用のRNG系列（途中再開時には再seedしない） |

HP・負債等の敗北は既存 RunEngine と同様に戦末で判定し、戦中の一時的なHP低下から自然回復する余地を残す。予算が0以下ならその入力で敗北し、赤字での続行を止める。勝利した初戦だけが `between` へ移り、`recover` / `skip` のどちらか一入力で次戦を開始する。回復は標準で800 centsを引いてHP+20（上限100）、それ以外の組織指標は保持。自然な戦間回復・返済・報酬はない。同入力の再送は新しい戦のフェーズで拒否し、回復・費用・戦番号を二重適用しない。回復予算が足りなければ全状態不変のまま拒否する。

各戦の開始時に `computeInfraCost(依存度, 0.1, 完成施策infraCostMul)` × 100 cents を一度課金し、進行した1 tickにつき5 centsを引く。`各戦実費の合計 + 戦間回復実費 = 初期予算 - 残予算`。失敗した戦・途中の資金枯渇も実費に含む。時間費と回復費は本番値ではない試作用係数。通常のショップ・ドラフト・ボスレリック報酬は発生しない。

## 比較結果

固定方針は、指定戦のtick 0に残業号令を試し、緊急な炎上なら鎮火、そうでなければReview 4件以上で割り込みレビューを試してから1 tick進行する。無効な試行は乱数・費用・ログを変えない。人間の状況判断や最適方針はモデル化しない。

標準条件。突破欄は `成功/到達`、総費用は初戦敗北も含む8 seedの平均（単位cents）。第2戦平均には到達者だけが含まれるため、生存者の偏りがある。

| ビルド | 切り札 | 回復 | 初戦突破 | 監査突破 | 連戦完走 | 平均総費用 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| speed | 初戦 | なし | 6/8 | 3/6 | 3/8 | 2052.500 |
| speed | 後半 | なし | 7/8 | 4/7 | 4/8 | 2208.750 |
| speed | 初戦 | あり | 6/8 | 4/6 | 4/8 | 2581.875 |
| speed | 後半 | あり | 7/8 | 5/7 | 5/8 | 2861.250 |
| resilient | 初戦 | なし | 8/8 | 6/8 | 6/8 | 2204.375 |
| resilient | 後半 | なし | 8/8 | 8/8 | 8/8 | 2246.250 |
| resilient | 初戦 | あり | 8/8 | 8/8 | 8/8 | 2940.000 |
| resilient | 後半 | あり | 8/8 | 8/8 | 8/8 | 2948.125 |

切り札後半・回復なしでは、speedの初戦は平均79 tick、resilientは84 tick。一方、初戦後HPは6.263対25.750、監査の平均出荷は532.571対615.125、監査後HPは1.914対6.588。speedは初戦時間の短さを連戦の消耗と交換するが、安定性・成果・総費用を横断した優位は示せていない。

resilientの初戦切り札は、標準条件で初戦出荷619.375（後半温存583.625）を得る一方、監査出荷596.000（温存615.125）、完走6/8（温存8/8）へ下がる。回復ありなら監査出荷621.625・完走8/8となるが、平均費用2940.000まで増える。切り札温存と有料回復の異なる代償を再現できた。

感度では、仕事48件でresilientの後半切り札・回復なしは8/8完走だが、回復ありは6/8となった。HPの違いがレビュー速度・以後の乱数消費を変え、回復が常に単調な成果改善になるとは限らない。回復量10ではspeedの初戦切り札・回復ありが3/8（標準4/8）。回復費1600では該当する回復実行分の予算が追加で800減る。時間費20ではspeedの後半切り札・回復ありが3/8（標準5/8）、resilientは8/8を維持するが平均費用5192.500。全条件の詳細はJSONを正本とする。

負債は本比較で初期22から変動しなかった。持越し契約は検証できたが、負債を作る方針と返済の判断は未評価。初戦敗北で監査へ届かないケースを、監査に向いたビルドの証拠として使わない。

## 保存・不正状態・通常記録との境界

専用 `mode` / `version` / `ruleset: ri267-sim-v1` を持つJSONに、全チェックポイント、各戦のRNG状態、setupと受理済み入力列を保存する。復元では固定プリセットから全入力を再実行し、全状態の一致を検証する。回復済みフラグ、予算、戦番号、RNG、成果、余分な報酬フィールドなどの改変は拒否する。無効入力を挿入しても拒否する。JSON 1 MB / 2000入力を上限とし、別rulesetは移行せず拒否する。現行simの挙動が変わった場合も一致しない旧試作保存は拒否し、再実行を求める。長期の保存互換や汎用リプレイ形式は提供しない。

戦中・戦間・回復直後・勝敗後のJSON往復とその続きが、RNGを含め一括実行と一致する。敗北後/勝利後の全操作は同じ状態を返す。結果の `rewardEligible: false`、`metaReward: 0`、`dailyReward: 0` は固定。RunEngine、通常persist、リプレイ、メタ保存への接続やストレージ書込みはないので、復元・再集計・決着操作を重ねても通常の全ボス実績・デイリー・レリック・報酬は増えない。通常セーブを渡すと形式/全状態照合で拒否する。

## 判断と次の終了条件

**再試作**。実simへの接続、固定持込み検証、費用/回復の一回適用、再開一致と報酬隔離の技術的境界は成立した。次に解く不確実性は「後半切り札・安全性ビルドへの固定化を避け、危機に応じて資源配分を変える余地があるか」。

次回は、取得費/完成までの投資を揃えた2ビルドで初戦/監査の得意不得意が分かれる条件と、実際に負債が増える入力を一つずつ追加する。比較前に成功基準を、少なくとも2つの危機条件で配分の有利不利が反転し、敗因と費用を説明できることとする。それを満たした後、短い操作可能な文脈で人間に選択理由・後続戦への温存意図・再挑戦で変える手を確認する。人間評価前はIssueを完了にせず、本番UI/タイトル導線・通常セーブ抽出・通常報酬統合には進めない。
