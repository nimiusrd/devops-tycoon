# #736 オフィスで編成・施策を選ぶ試作

評価は **再試作**。準備中に Coding と Review の人員を入れ替え、誰に AI を渡すか、予算を使って Review の滞留を減らすかを一つのオフィスで判断できるかを確かめる。判断の分かりやすさ、操作負担、会社への愛着は人間の比較プレイで判定する。

## 操作と比較条件

開発サーバの `/?rd=office-build` を開く。seed は `issue-736-office-build`、難易度は Normal。試作条件として担当チームにレビュー待ち10件・炎上1件を引き継がせる。初期予算45、Coding 2人（AI配布1人）、Review 1人、カード・進化・試練なし。担当の変更に伴う実装力・レビュー力・AI習熟の違いは既存の個人能力と編成ルールで決まる。試作への入力、予算、結果はブラウザ内の一時状態に置く。

- Coding・Review・控えの各欄からメンバーを選び、担当とAI配布を変更する。Reviewや控えに移すとAIが外れる。Review要員を増やせば実装に回る人が減り、AIを渡す相手を変えれば実装速度や手戻りのリスクも変わり得る。
- Review台で既存のチーム施策「レビュー応援(チーム)」を候補にすると、予算6を使い、対象チームの開始前のレビュー待ちを最大5件減らした場合の盤面と見込みを確認できる。この条件では予算45→39、引き継ぎ10→5件、炎上1件のまま。「変更を取り消す」で初期配置・AI配布・予算・引き継ぎに戻る。
- 「プランを適用して試走」で編成と施策を確定する。最初は tick 0 で止まり、手動で進める。見込みは通常の what-if と同じ乱数掃引、実測は同じスプリントseedの1回の実行。盤面のタスクは共有の Pixi/WebGL、メンバーと施策の操作は盤面に隣接したHTMLを使う。WebGLが使えない間は試走を進めず、再試行できる。

## 固定入力での試算と実測

いずれも試走開始後に介入せず、「最後まで進める」を選択した。見込みの範囲は各案24回の試算から得た。実測は同じ固定seedの1スプリントの結果。

| 入力 | 出荷の見込み | 延焼の見込み | 出荷の実測 | 延焼の実測 | Review待ち最大 | AI利用 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 初期配置・AI配布のまま、応援なし | 461〜687 | 0〜3 | 645 | 0 | 30件 | 32% |
| レンをReviewへ移し、レビュー応援を送る | 431〜588 | 0〜0 | 507 | 0 | 7件 | 0% |
| レンをReviewへ移し、アオイにAIを配り、レビュー応援を送る | 469〜662 | 0〜5 | 579 | 0 | 28件 | 74% |

この条件では、Reviewへ人員を移してAI配布なしで進める案は滞留が小さく、出荷も減った。残るコーダーにAIを配ると、出荷とReviewの最大滞留の両方が増えた。

## 既存実装との対応

#537 の会社の獲得状態や人物の表示、#680 の文化レリック掲示、#538 の期間進行・委任は既存または別試作の責務。本試作は、1チームの準備段階で編成と一回の施策操作を結ぶ。Review台は作用する工程を示す。場所による効果や新しい設備枠、処理経路、保存形式の追加は本番統合を判断する際に別途扱う。
