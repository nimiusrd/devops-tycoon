# RI-283 レビュー滞留に連動する音楽層

[個別 Issue #679](https://github.com/nimiusrd/devops-tycoon/issues/679) ・ [親 Issue #548](https://github.com/nimiusrd/devops-tycoon/issues/548)

## 仮説と試作の範囲

レビュー待ちが増えたとき、診断別 BGM に低域の揺らぎを重ねると、盤面全体に注意を割いていてもレビューへ視線を戻しやすくなる。一方、層が頻繁に出入りしたり危険 SFX を覆ったりすると、現行の音楽と盤面表示だけの方が判断しやすい。プレイヤーがレビューへの差配を優先するか、作業を続けるかを試聴時に比較する。

試作は既存のオーディオエンジンで診断別 BGM と SFX を再生する。進行中スプリントの盤面から現在のレビュー件数だけを読み、件数のピークや敗北条件とは独立した演出用の閾値を使う。[試作コード](../../src/prototypes/reviewMusic.ts)

| 項目 | 試作の固定条件 |
| --- | --- |
| 追加 | Review が 6 件以上の観測が 900 ms 続く |
| 解除 | Review が 3 件以下の観測が 1,400 ms 続き、250 ms かけて音量を下げて解放する |
| 観測中断 | サンプルの間隔が 500 ms を超えるか時刻が逆行したら、継続時間を数え直す |
| 停止 | スプリント終了、スプリント ID 変更、BGM off、dispose で層を即時停止する |
| ミュートと unlock | 既存エンジンの状態を共有し、unlock 成功後に再生する。再生拒否後の再試行は、次の滞留、ユーザー操作による unlock、またはミュート解除に限る |

追加する音は既存曲の拍や旋律から独立した 2 秒のループで、試作用コードから生成する PCM 16-bit mono（12 kHz、48,044 バイト）。生成するコードには MIT License、既存 BGM と SFX には CC BY 4.0 を適用する。試作音はメモリ内で WAV を合成し、Blob として再生する。再生中に追加で保持するメディア要素は 1 個で、音量更新はフェード中の 50 ms 間隔に限る。[素材ライセンス](../../ASSETS.md)

試作への入力は読み取り専用の盤面スナップショットと呼び出し側が渡す観測時刻。ユニットテストでは、seed `ri-283-audio-isolation` と難度 normal で 2 つのランを開始し、100 ms ごとの進行と `overtime` の入力を揃える。層をオンにする滞留は観測用コピーに与え、再生が拒否された場合も、各ランの盤面と差配の結果が一致することを確認する。試作の実行入口は計測スクリプトとユニットテストに限り、音声の状態は試作セッション内で保持する。

## 比較の再現方法

```sh
devcontainer exec --workspace-folder . npm test -- src/prototypes/reviewMusic.test.ts tests/unit/audio --maxWorkers=1
devcontainer exec --workspace-folder . node scripts/ri283-review-music-evaluation.mjs
```

ブラウザ比較では React や盤面のない同一ページを使い、どちらもブラウザへのポインタ入力で unlock し、cloudy BGM の再生とプリロードの待機後に測る。seed や資源で変動しない比較用の固定タスク列を与える。各行を 100 ms ごとに観測し、危険 SFX は 100、2,000、2,600 ms に発火する。

| 論理時刻 | Review 件数 | 想定 |
| --- | ---: | --- |
| 0〜500 ms | 6 / 5 が交互 | 層は開始せず、最初の SFX は既存 BGM と重なる |
| 600〜2,700 ms | 8 | 1,500 ms で開始し、後の 2 回の SFX と重なる |
| 2,800〜4,500 ms | 3 | 4,200 ms からフェードし、観測窓内で停止する |
| 4,600〜4,900 ms | 8 | 観測窓内では再始動しない |

計測用の 5 秒の入力列を各条件で 3 回ずつ再生し、CPU 負荷を比較する。試行ごとに独立したブラウザコンテキストを開き、現行→試作、試作→現行、現行→試作の順で測る。測定の開始と終了に存在する Chromium の各プロセスの CPU 時間を CDP から取得する。音声信号の比較では別に Chromium で音源を PCM にデコードし、既存 BGM 音量 0.35、危険 SFX 音量 0.70、試作層音量 0.09 で加算する。BGM の全尺を 0.25 秒刻み、層を 0.5 秒刻みで重ね、SFX が鳴る区間で混合ピークと最小の SFX 対音楽 RMS 比を測る。

## 計測結果

Node 24.16.0 の Dev Container（Linux arm64）で Chromium 158.0.8127.18 のヘッドレス版を使用。全試行で危険 SFX 3 回の再生と完了を確認した。層を追加した 3 試行では毎回、層の `play()` は 1 回で、危険 SFX のうち 2 回と重なった。いずれも観測窓内に層を停止して音源を解放した。

| 比較 | 現行の CPU 時間 / 実時間 | 試作の CPU 時間 / 実時間 |
| --- | --- | --- |
| 1 | 1,420 ms / 7,015 ms（20.2%） | 1,530 ms / 6,735 ms（22.7%） |
| 2 | 1,130 ms / 6,321 ms（17.9%） | 1,390 ms / 6,769 ms（20.5%） |
| 3 | 1,000 ms / 5,811 ms（17.2%） | 1,540 ms / 6,439 ms（23.9%） |

各値は AudioService を含む Chromium 5 プロセスの合計。計測窓の途中でプロセスの入れ替わりはなかった。3 組とも試作で実時間あたりの CPU 時間が増えた。通常のゲーム描画や他端末での負荷は次の比較で測る。

| 診断別 BGM | 混合ピーク（dBFS、現行 → 試作） | 危険 SFX 対音楽の最小 RMS 比（dB、現行 → 試作） |
| --- | ---: | ---: |
| bright | -12.44 → -12.05 | -11.11 → -11.24 |
| cloudy | -12.24 → -11.69 | -10.14 → -10.29 |
| tense | -12.60 → -12.27 | -9.89 → -10.17 |

測定した重ね方の最大混合ピークは -11.69 dBFS で、危険 SFX 対音楽の最小 RMS 比は 0.13〜0.28 dB 下がった。PCM の結果は音源の重なりを示す。聴取時の気付きやすさと聞き分けは次の試聴で評価する。

## 採否

**再試作。** 次は実際のプレイ中に層の有無を切り替え、同一の操作条件・seed で、レビュー滞留への気付きと危険 SFX の聞き取りを比較する。条件の順序は参加者間で入れ替え、bright・cloudy・tense を含める。各試行でレビューへ視線を戻すまでの時間、差配の選択、危険 SFX の聞き逃しと誤認を記録する。レビュー滞留への気付きが改善し、危険 SFX の見落としが増えず、低性能端末を含む通常プレイ中の負荷を確認した時点で採否を判断する。試聴と通常プレイでの端末別負荷は今回未測定。
