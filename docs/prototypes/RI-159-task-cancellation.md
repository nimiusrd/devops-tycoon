# RI-159: 不要な仕事の途中キャンセル

対象: #555 / 親: #548。結論: **投入量と残り期間によって中止判断が変わる仮説を採用、本番統合は保留**。人間のプレイ評価は未実施。

## 操作と終端状態

通常ランから隔離した純TS試作。RI-157の共通作業モデルを利用し、通常タスク1種に中止操作を追加する。seed `RI-159`、終了tick 5、作業枠1、Focus 1、信頼5。obsoleteは4工数・価値2、neededは3工数・価値8。価値低下を公開情報として固定し、obsoleteを1または3tick進めた同じ盤面から継続/中止を比較する。seedは識別に保持し、比較工数は固定する。

Coding中の未完了タスクだけをキャンセルできる。成功時はFocus 1を払い、tickは消費せず、作業対象から除外して`cancelled`終端履歴へ移す。理由・投入工数・残工数・元の価値・中止tickを残す。投入済み工数を返還せず、別仕事を同じ枠で次tickから進められる。Coding枠はactiveIdとして完了か中止まで占有し、待つだけでは解放しない。別仕事への無償切替は拒否するため、中止だけが不必要に劣る比較にしない。

未知ID・再キャンセル・空理由・Focus不足・炎上中・統合工程・Done・期末は無消費で拒否する。Coding待機の仕事もCoding残工数が正なら中止できる。契約対象IDは明示し、契約中止だけ信頼2を追加で払う。失敗時の信頼低下はない。炎上処理・契約交渉全体は対象外。

中止タスクは出荷台帳・Done数・価値に入らず、完了入力にも戻せない。通常ランのコンボ計算には接続しない。本番導入時も中止を完了イベントへ送らないことを契約とする。

## 同条件の比較

| 投入量 | 判断 | 期末価値 | Done | Focus残 | 廃棄工数 |
| --- | --- | ---: | ---: | ---: | ---: |
| 浅い1工数 | 継続 | 2 | 1 | 1 | 0 |
| 浅い1工数 | 中止 | 8 | 1 | 0 | 1 |
| 完了間近3工数 | 継続 | 2 | 1 | 1 | 0 |
| 完了間近3工数 | 中止 | 0 | 0 | 0 | 3 |

浅い投入ならneededをtick 4で完成でき、中止が有力。完了間近からneededへ移ると期末に1工数残り、継続が有力。投入済み時間そのものへの報酬ではなく、残り期間に代案が納まるかで選択が変わる。契約中止の追加費用と拒否条件は別のテストで検証する。

`task-cancellation-comparison.json` は比較開始時の全状態、操作列、廃棄理由、出荷時期、残作業・資源を保存し、テストで再生成する。中止履歴と完了履歴を区別し、消えた価値を成果として扱わない。

## 採否・次の評価・互換境界

仮説採用、本番統合保留。次は複数Focus、中止費用、契約比率、代案がなくても中止する状況、需要の予告時期を評価する。既存介入の説明改善 #536 と公開済み機能の廃止案83は対象外。

version 1のJSONは廃棄後の保存再開・入力再生が一致する。初期盤面の準備作業はboard.historyに、比較開始後の成功入力はinputsに保存する。拒否は状態を変えない。元状態も変更しない。外部JSONの検証付きロードUIは対象外。

通常のTask、保存、ruleset、SPEC、勝敗、固定トラック、WebGL停止契約は変更しない。本番採用時はcancelled終端型、工程ごとの判定、Coding枠・担当解除、完了コンボ除外、評価/履歴/保存移行とruleset更新を別Issueで設計する。
