# RI-206: 師匠1人・弟子1人のレビュー育成試作

対象: #602 / 親: #548。評価結論: **育成候補として仮説を採用**。本番統合は保留する。

## RI-151との接続方針

#538の「育成1種」の具体候補として扱う。別の人物関係システム、関係値、複数の指導網は作らない。`advanceMentorshipPeriod(state, teach, demand)` は一期間の処理と育成を一度確定する純関数で、#538の会社期間比較から対象チームに渡せる入口とする。#538全体の3チーム比較・直接介入・報酬は本PRでは実装せず、完了扱いにしない。

## 対象・費用・効果時期

既存の `createInitialRoster` からseed `RI-206` で生成した実在するシニアm2とジュニアm1を使う。弟子をレビュー配置とし、レビュー能力だけを育成する。残るメンバーは試作の対象外で更新しない。

処理能力は `floor(review / 10)` 工数/期間。師匠はレビュー64で6、弟子は32で3。育成すると師匠の通常処理3工数、弟子の通常処理1工数を譲り、期間末に弟子のレビュー能力を10増やす。効果は次期間から通常処理に表れる。育成は最大2回でレビュー52まで。一般の入力でも能力100を超えない。

`previewMentorship` は人物ID、能力、費用、次の能力増分、効果開始期間、残り育成回数、現在の実施可否を返す。休職・不在・スタミナ0・控え・実装配置では指定した育成は進まない。両者は別ID、師匠はシニア、最低の指導余力が必要。失敗した育成は費用・能力増分を付けず、稼働できる人物の通常処理だけ行う。弟子が100に達した場合も育成を終了する。

能力上限へ達した場合はプレビューの残り回数も0となる。同一IDを両役割へ指定しても、一人分の通常処理だけを計上し、弟子側の成長由来処理を付けない。

毎期間12工数の仕事が入り、未処理は持ち越す。師匠から通常処理し、残りを弟子が処理する。出荷は実際に処理した量だけ。育成・委任という操作、閲覧、未閲覧への報酬・罰は設けない。

## 採否と次の評価

残り期間で集中と育成の優劣が変わる仮説を採用する。固定モデルのため本番数値の妥当性は未確定。次は負荷不足で能力を使い切れない局面、期限までの危機、師匠の復帰時期、本人の既存トレイト・スタミナ消耗・自然成長と合わせて#538の会社期間比較を行う。今回の試作ではスタミナの自動消耗・回復、XP・昇格、AI習熟、予算、全社報酬は模擬しない。

通常ランのロスター・成長式・保存・ruleset・固定トラックは未変更。#537は表示の独立課題として進められる。JSON状態の `version: 1` は試作専用で、本番セーブへ混ぜない。同じseed・期間入力で再現し、途中のJSON保存から同じ人物ID・成長・通常処理へ再開する。採用時は保存形式・ルールセット・入力履歴を別Issueで設計する。
