# RI-292: 複数種類の自己ベスト

対象 #688 / 親 #548。結論: **勝利時の士気ベストは現行バランスでは見送り。記録契約は採用し、次の候補は勝利時のシニア余力で再評価**。本番の `MetaState` には接続しない。人間のプレイ評価は未実施。

## 記録の契約

通常のメタ保存から隔離した純TS試作。`recordAltBest(book, input, metric)` は1指標ずつ、既存の `bestScore`・メタ進行ポイント・デイリー記録とは別の記録帳に書く。

| 項目 | 契約 |
| --- | --- |
| 成功条件 | 勝利（`won`）かつ1スプリント以上完了。敗北・進行中・開始直後は `not-eligible` |
| 計測時点 | ラン決着時（ボス突破後）。最低シニア余力は各スプリント完了境界の最小値 |
| 条件の区別 | キーは指標・ラン種別・難易度・シナリオ・試練（順序を問わない）・ruleset 版・指紋。異なる条件は同じ枠に入らない |
| 旧保存 | ruleset 不明（`null`）は `not-eligible` |
| 欠測 | 値がない・非有限・境界の列が完了数と合わない場合は `missing`。0として採用しない |
| 同値 | 先の記録を残す（`tie`）。下回る記録は `lower` で変えない。上回る記録だけ置き換える |

記録は値・完了スプリント数・勝利種別を持つ。`bestScore`・ポイント・デイリー記録は従来の関数のまま更新され、記録帳の更新で巻き戻らない。

## 候補指標の評価

実エンジン（`RunEngine`、難易度 easy、シナリオ default、試練なし）で seed m0〜m119 を素の方針と熟練方針（`tests/unit/helpers/runFlow.ts` の `skilled`）で走らせた240ランのうち、勝利20件の決着値を固定データ `alt-best-wins.json` に保存した。勝利を順に記録したとき、記録が動いた回数と値の分布を数える。`not-eligible`（敗北・進行中・開始直後・ruleset 不明）は、値が測れても標本・分布・上限到達数・スプリント別平均に入れない。

| 指標 | 異なる値 | 範囲 | 上限到達 | 記録の動き | 完了スプリント数別の平均（12 / 18 / 24 / 30 / 36） |
| --- | ---: | --- | ---: | --- | --- |
| 勝利時の士気 | 1 | 100 | 20 / 20 | 初回1、同値19 | 100 / 100 / 100 / 100 / 100 |
| 勝利時のシニア余力 | 20 | 63.0〜100 | 1 / 20 | 初回1、更新2 | 83.9 / 92.3 / 84.4 / 82.9 / 94.1 |
| 最低シニア余力 | 20 | 2.3〜30.1 | 0 / 20 | 初回1、更新1 | 17.3 / 13.4 / 15.8 / 9.8 / 9.1 |
| 勝利時の予算残 | 16 | 2〜50 | — | 初回1、更新1、同値1 | 41.2 / 35.6 / 22 / 6.5 / 2 |

勝利時の士気は20件すべてが上限100で、最初の勝利の後は同値しか出ない。同じ240ランを各スプリント完了境界で測った最低士気も95.5以上だった（固定データには含めていない）。最小スコープどおり士気ベストを保存しても、勝ち方の違いを記録できない。自動プレイは残業・アンドンを使わないため、人間のプレイでは士気が下がりうる。ただし重い介入を使わなければ上限に届くので、「使わなかった」ことしか記録しない。

勝利時の予算残は短いランほど高く、最高記録は12スプリントの勝利だった。「最少コスト」として置くと、長く経営した勝利ほど不利になる。issue の指摘どおり、予算残は実利用費とは別の指標である。最低シニア余力は値が分かれるが、長いランほど低い（17.3→9.1）。

勝利時のシニア余力は値が分かれ、完了スプリント数に沿った低下が見られない。次の候補として仮説を採用する。ただし決着直前の休息だけで値を上げられるかは未確認で、本番化の前に確かめる。

## 判断

- 勝利時の士気ベスト: 現行バランスでは**見送り**。士気の上限か計測方法を変えるまで保存しない
- 勝利時の予算残: **保留**。ランの長さで補正するか、実利用費として測る方法を先に決める
- 最低シニア余力: **修正して再評価**。四半期ごとの最小値など、ランの長さに依存しない計測を検討する
- 勝利時のシニア余力: **次の候補**。決着直前の休息で上げられるかを確かめてから、`MetaState` への保存を別PRで行う
- 記録契約（成功条件・計測時点・条件別キー・欠測・同値・旧保存）: **採用**

## 本番境界と検証

本番化では `MetaState` に記録帳を足し、`normalizeMeta` での旧保存の補完、`applyRunReward` / `applyDailyRunReward` と同じ完了トランザクションでの保存、リザルト（`src/ui/RunResultScreen.tsx`）での表示を別PRに分割する。今回の試作は `src/state/meta.ts`・`metaPersistence.ts`・UI を変更しない。固定データは記録時のバランスを写したもので、以後のバランス変更でテストを壊さない。

Node 24で対象ユニット、型、lint、format:checkを検証。UI/Pixi変更なし。E2Eとgalleryは対象外。
