### RI-67 オンボーディングとシニア燃え尽きの断絶（優先度: 高）

Easy でも「素直に遊ぶ」と第1四半期スプリント2でシニア燃え尽き（`seniorBurnout`）敗北する。

同一 seed（`review-hell`・Easy）で、介入と編成を切り分けた統制実験の結果:

| プレイ方針 | 結果 |
| --- | --- |
| D 無介入（自動進行のみ） | Q1 sprint2 で `seniorBurnout` 敗北 |
| A 編成のみ（middle を review へ、介入なし） | それでも Q1 sprint2 で敗北 |
| B 介入のみ（緊急対応＋andon、編成そのまま） | 12スプリント以上を燃え尽きずに継続 |
| C 編成＋介入（B に編成変更を追加） | Q1 sprint2 で敗北 |

敗北条件は `org.seniorHp <= 1`（`src/sim/outcome.ts:57`）で、これはメンバー個別の stamina ではなく
**抽象的なグローバル値**である。`org.seniorHp` の主な減少要因は次の2つ:

- レビュー1件ごとの一律消費 `REVIEW_HP_COST`=1.6（`reviewOne`、`src/sim/sprint.ts:252`）。担当のランク・
  人数に関わらず同額を削る。
- 猶予切れの炎上を受動処理する**自動鎮火** `INCIDENT_HP_COST`=12（`advanceBurning`、`src/sim/sprint.ts:340`。
  リザルトの `シニアHP -12` の主因）。緊急対応（firefight）で先に鎮火すれば `FIREFIGHT_HP_COST`=2 で済む。

スプリントは全タスクが Done になるまで進む（`isDrained`、`src/sim/sprint.ts:480`）。実測では第1スプリントは
seed 固定 25 タスクを endTick 46〜71 で完了し、`maxTicks`=1500（`src/sim/scenarios.ts:46`）の打ち切りには
達しない。ただしレビュー**回数**はタスク数固定ではない: 手戻りタスクは Rework 経由で Review へ戻り
（`advanceRework`、`src/sim/sprint.ts:378`）、緊急対応で鎮火したタスクも Review へ戻る（`fire.lane='review'`、
`src/sim/actions.ts:151`）ため、レビュー試行数＝タスク数＋（手戻り・炎上の再レビュー）となり、手戻り率・炎上率に
応じて増減する。したがって**手戻り率**を下げる施策（品質・PR分割・AIスロットル。`reworkProbability` の quality・
`task.split`・aiAssisted・aiDependency 項）は再レビュー回数を減らし、`REVIEW_HP_COST` と炎上判定回数を**間接的に**
減らしうる。ただしこれは「レビュー1件あたりの点火率（`incidentProbability`）」を下げるのとは別で、点火率が参照するのは
testCoverage・`task.aiAssisted`・カード効果のみ（品質値・`task.split` は参照しない）。一方 `org.seniorHp` は
毎 tick `REVIEW_HP_REGEN`=0.7
（炎上中は `BURNING_REGEN_MUL`=0.5 で半減、`src/sim/sprint.ts:474`）で回復し、炎上確率 `incidentProbability` は
レビュー1件ごとに評価され**待ち行列長を入力に取らない**（`src/sim/model/process.ts`）。よって「待ち行列を短くすれば
点火が減る」は成り立たない（当初この所見が編成の待ち行列短縮を生存要因としていた点を、Codex レビューの指摘と
下記実測で訂正）。

第1スプリントの実測（同一 seed、条件別の自動鎮火回数と終了時 `org.seniorHp`）:

| 条件 | endTick | 自動鎮火(−12) | HP終値 |
| --- | --- | --- | --- |
| D 無介入 | 65 | 3 | 42 |
| A 編成のみ | 54 | 3 | 36 |
| 緊急対応のみ | 62 | 1 | 62 |
| B 緊急対応＋andon | 71 | 0 | 74 |
| C 編成＋介入 | 46 | 1 | 55 |

読み取れる実際の要因（直接測定できた範囲）:

- **HP を最も動かすのは自動鎮火（−12）の回数**で、これを直接減らすのが **緊急対応**（−12 になる前に −2 で鎮火。
  ただし鎮火後は Review へ戻り再レビュー1件ぶんの `REVIEW_HP_COST` は掛かる）。緊急対応のみで自動鎮火 3→1、
  HP 42→62 に改善し、これは条件を1つだけ変えた比較として最も確度が高い。andon はレビュー件数を減らすのではなく、
  流入を一時停止（`intake` の早期 return、`src/sim/sprint.ts:183`、通常 30 tick）して**既存キューを捌く猶予**を作り、
  同時炎上を抑えて緊急対応を間に合わせる補助（B で自動鎮火 0）。
- **編成（middle を Review へ）は単一要因ではない**。review 増員（`reviewCapacityMul`）だけでなく Coding 担当が減り、
  `foldFormationEffects`（`src/sim/member/roster.ts:251`）経由で `codingSpeedMul` / `codingSlotBonus` / `aiAdoptionShare`
  と AI 由来の確率補正が次スプリント生成に同時適用される。C（編成＋介入）が B（介入のみ）より早く燃え尽きた事実は
  確かだが、複数因子が連動するため B/C 差を「レビュー速度×回復」等の単一機序に帰属できない。確実に言えるのは、
  **編成変更はシニアHP保護の主手段ではなく（A は無介入と同じく即死）、燃え尽き回避を編成に頼らせるべきでない**こと。
  厳密な寄与分解には Coding 側を統制した比較が要る（RI-66 の統計検証と合わせて後追い）。
- AIスロットルは流入を止めず、新規タスクの `aiAssisted` を false にして AI 由来の手戻り・炎上確率
  （`reworkProbability` / `incidentProbability` の aiAssisted・aiDependency 項）を下げる。上記のとおり手戻り減は
  再レビュー減につながるため、HP 消費・炎上判定の**間接的な**緩和にはなる。

素直プレイが即死する構造は、シニア1人＝唯一のレビュアー（`src/data/members.ts` `STARTER_ARCHETYPES`）で
炎上が起きやすいうえ、チュートリアル（`src/ui/tutorial.ts`）が介入バー・レビュー渋滞・コンボの3点のみで、
**シニア体力（燃え尽き）と、燃え尽きを防ぐ主手段＝炎上を自動鎮火前に緊急対応で鎮火することを教えていない**ため。
Easy は導入難易度（「モダンなプロダクトチーム」）であり、この即死は体験を損なう。

改善方向（いずれか／組み合わせ）:

- チュートリアルに「シニア体力（燃え尽き）」と、それを防ぐ最大手段＝炎上を自動鎮火 −12 になる前に緊急対応で
  −2 鎮火することを追加する。補助として、andon（既存キューを捌く猶予）、AIスロットル（レビュー1件あたりの
  点火率と手戻り率を下げる）、品質・PR分割（手戻り率を下げて再レビューを減らす。点火率自体は下げない）も
  位置づける。編成での review 増員はスループット策であり燃え尽き回避の主手段ではない点を明確にする。
- `org.seniorHp` の収支（`REVIEW_HP_COST` / `INCIDENT_HP_COST` / `REVIEW_HP_REGEN`、`src/sim/model/process.ts` ほか）や、
  Easy 序盤の障害率を見直し、標準的な操作理解のプレイが2スプリントで即死しないようにする。
- 燃え尽きが近いときに盤面・HUD で明確に警告し、対処アクション（緊急対応・andon・スロットル）へ誘導する。

### RI-68 四半期レビュー Delivery KPI のスケール不整合（優先度: 高）

第2四半期レビューで **Delivery 目標20 に対し実績1693（約80倍超過）**、Quality/Morale/TechDebt も
すべて「超過」。目標生成（`src/sim/run/quarterReview.ts` の `deliveryTarget`、概ね1スプリント相当の
`minSprintDelivered` ベース）に対し、判定は四半期累計 `quarterTotals.delivered` を比較しているため、
看板KPIの「出荷ポイント＝勝利条件の進捗」が常に自明達成となり意味を失う。プレイヤーには
「目標20 → 実績1693 超過」が壊れて見える。

改善方向:

- `deliveryTarget` を四半期の実出力スケールに合わせて設定する、
  または判定・表示の単位（1スプリント平均 vs 四半期累計）を一致させる。
- 実際に効いている制約（Morale・Quality・Incident・燃え尽き）が勝敗条件として伝わる表示にする。

### RI-69 スプリント上部操作バーと盤面の重なり（優先度: 中）

デスクトップ幅（1440px、DOM レンダラ `?renderer=dom` で実測）で、上部の操作バー（`通常スプリント /
❚❚ / 1x-2x / 渋滞メーター / 炎上タイマー / COMBO`）が盤面領域の上端と重なり見切れる。1行への詰め込み過多。
DOM 経路の盤面は Pixi キャンバスではなく DOM 要素（`FlowArrows` / `TaskDot`）で描画されるため、これは
レンダラ非依存のヘッダ／盤面コンテナのレイアウト問題として扱う（Pixi レンダラでも別途再現確認する）。
対象: スプリント画面のヘッダ／盤面レイアウト（`src/ui/SprintScreen.tsx` 周辺）。

### RI-70 モバイルのスプリント操作性（優先度: 中）

390px 幅で横スクロール・崩れは無い（`documentElement.scrollWidth === innerWidth`）が、縦積みの
KPIカードの下に盤面とアクションバーが来るため、時限スプリント中に盤面のタスク流動と介入ボタンを
見るのにスクロールが必要。リアルタイム介入ゲームとして操作性が落ちる。
改善方向: 狭幅ではKPIを折り畳み／要約し、盤面＋アクションバーを一画面に収める。

### RI-71 favicon 未設定による 404（優先度: 低）

`index.html` に favicon 宣言が無く `public/` にも実体が無いため、`/favicon.ico → 404` が毎ロード時に
コンソールへ出る（`curl` で 404 を確認）。ブラウザタブのアイコンも空。`<link rel="icon">` の追加と
アイコン配置で解消できる。

### RI-83 介入が結果の分散を下げない（優先度: 中 / F-5）

> **この節の結論は撤回済み。現行の判定は第2回の [RI-83](#ri-83-条件を揃えると介入の寄与がほぼ消える優先度-高--f-5) を参照する。**
>
> ここでは「分散は抑えていないが**期待値は押し上げている**」としているが、これは
> 介入と同時に進化・カード・採用が変わっている条件で比較していたためだった。
> 介入だけを外した統制条件 `noInterventionCtl` を立てると 11勝 vs `skilledNoHire` 15勝で、
> **期待値への寄与もほとんど無い**。分散の測り方（同一スプリント番号ごとの CV）も改めている。
>
> 末尾の「対応の方向は2つあり、どちらを取るかは設計判断」も解決済みで、
> **実装を定義へ寄せる**（介入に下振れを潰す性質を持たせる）と決定した（2026-07-26）。
> SPEC 第19.1 F-5 に明記してある。以下は経緯として残す。

SPEC 第19.1 F-5 は「無介入は損ではなく不安定。介入の価値は期待値の底上げよりも**結果の偏差を抑えること**」と
定義している。ラン長の差が混入しない指標で測ると、この関係が成立していない。

easy の出荷の変動係数（CV）:

| 方針 | 1スプリントあたり出荷 CV | 第1スプリント出荷 CV |
| --- | --- | --- |
| `idle`（完全放置） | 26.6% | 10.6% |
| `passive`（無介入） | 23.4% | 10.6% |
| `naive`（初見相当） | 20.0% | 11.3% |
| `skilledNoHire`（上級者相当） | 23.7% | **12.7%** |
| `onlyFirefight` | 22.0% | 9.7% |

easy では、全ランが到達する第1スプリントで見ると**介入する方針ほど分散がわずかに大きい**
（`skilledNoHire` 12.7% が最大）。1スプリントあたり出荷でも 26.6% → 20.0〜23.7% と差はごく小さい。

normal / hard では向きが逆になる。第1スプリント出荷 CV は
normal で `idle` 11.1% → `skilledNoHire` 8.9%、hard で `idle` 7.9% → `skilledNoHire` 6.3% /
`onlyFirefight` 4.9% と下がる。一方、1スプリントあたり出荷 CV は
normal `idle` 26.8% → `skilledNoHire` 28.5%、hard `idle` 20.9% → `skilledNoHire` 26.7% と**上がる**。

つまり指標と難易度によって向きが変わり、**一貫した分散抑制は観測できない**。

一方で勝率は改善している（RI-72 の表）。つまり現状の介入は**期待値を押し上げる手段**であって、
F-5 が想定する**不確実性を抑える手段**にはなっていない。

なお第1回の集計では累計出荷の CV が 57.9% → 38.6% と下がることを根拠に F-5 成立としていたが、
これは早期敗北したランほど累計出荷が機械的に小さくなるためで、
組織出力の安定性ではなくラン長の差を見ていた（Codex レビューの指摘により訂正）。

対応の方向は2つあり、どちらを取るかは設計判断である。

1. ~~F-5 の定義を実装に合わせる（介入は期待値を上げる手段と位置づけ直す）。~~ **不採用**
2. **実装を F-5 に合わせる（介入に下振れを潰す性質を持たせ、無介入の分散を大きくする）。← 採用**

受入条件（現行のものは第2回 RI-83 を参照）:

- ~~F-5 の定義と実装のどちらを動かすかを決め、SPEC 第19.1 に反映する。~~
  **決定済み（2026-07-26）。実装側を動かす。SPEC 第19.1 F-5 に記載。**
- 無介入と介入で 1スプリントあたり出荷・第1スプリント出荷の変動係数に有意な差が出る。

# プレイテスト所見 第2回（2026-07-26）— 面白さ定義に基づく判定

[SPEC 第19.1「面白さの定義と判定基準」](../SPEC.md)を先に定義し、その F-1〜F-12 に照らして
全難易度を回した記録。実行可能な項目は[remaining-issues.md](./remaining-issues.md)へ
`RI-72`〜`RI-85` として登録した。

## 検証条件

- 対象: `main`（`8629f5f`）
- 方法: `npm run playtest`（`tests/playtest/harness.ts`）→ `npm run playtest:report`
- 母数: **4難易度 × 31方針 × seed `pt-1`〜`pt-10` = 1,240ラン**
- 本書とバックログに書いた**方針別の勝利数は `npm run playtest:check` で実測と突き合わせている**
  （`scripts/check-findings.mjs`）。再計測のたびに手で追うと必ず取りこぼすため
  （実際、方針を1つ足しただけの回で概要と詳細表がずれ、レビューで指摘された）
- 出力（`playtest-out/runs.json`）には**どのコホートを回したか**を一緒に書き出しており、
  絞り込み実行（`PT_DIFFS=easy` など）の結果は `playtest:check` が「未計測」として降りる。
  40ランを前提にした数値と10ランの出力を突き合わせると偽陽性が出るためである。
  また `npm run playtest` は**走り始める前に旧出力を消す**。途中で落ちた実行のあとに
  前回の成功結果を最新値として集計してしまうのを防ぐ
- **メタ進行は初見相当**（`PT_META=fresh`）。`game.startRun` と同じく既定解放分のみをドラフト候補にする
- 壁時計換算は実装の `MS_PER_TICK_1X`（`src/ui/sprintTempo.ts`）から読む

### 統制の考え方

方針は**介入・カード・進化順・ドラフト選好・採用・目標修正**を独立に指定できる。
ある要素の寄与を見るときは、他を揃えた条件同士を比較する。

| 方針 | 内容 |
| --- | --- |
| `idle` | 介入もカードも進化も使わない完全放置 |
| `passive` | 介入・進化なし、カードのみ |
| `noInterventionCtl` | **F-5 用の統制**。`skilledNoHire` から介入だけを外し、カード・進化・採用は揃える |
| `naive` | 初見想定。異常が目立ってから反応、**約4.1秒ごとに判断**（6 tick）。進化はツリー表示順 |
| `skilled` | 上級者想定。閾値低め＋andon＋差配、**約2.0秒ごとに判断**（3 tick）、採用あり（専用フェーズ・ショップ・休息・即時採用イベントすべて）。進化はレビュー容量優先 |
| `skilledNoHire` / `skilledNoCards` / `skilledSelectiveCards` | `skilled` から採用を外した条件／さらにカードも外した条件／カードを状況選択にした条件 |
| `skilledSelectiveHire` | **採用の第3条件**。欠員（休職者あり／実働2名以下）があり、採用後も予算が残るときだけ採る |
| `skilledShopBuy` | **ショップ投資の統制**。`skilledNoHire` に加えてショップでレリック→カードを購入する |
| `skilledRestRepay` / `skilledRestUpgrade` | **休息の選択肢の統制**。負債50以上なら返済／常にカード強化。統制先は常に回復する `skilledNoHire` |
| `onlyXxx`（8種） | 単一介入だけを打ち続ける。進化順とビート選択は `skilledNoHire` と揃える |
| `aiFullBet` / `noAi` / `reviewHeavy` | AI 全配布＋AI 進化＋AI カード優先 / AI 解除＋品質進化＋品質カード優先 / レビュー寄せ編成 |
| `adj*`（6種） | 目標修正だけを固定して選ぶ（全6選択肢） |
| `probe` | 全8種の介入を 1 tick ごとに試行。**上限測定ではない**（順に発動するため先行手が後続の機会を消す） |

### 計測モデルの前提と限界

方針は人間の操作を模したものだが、**閾値や重みは実測から導いたものではなく、こちらで決めた値**である。
以下は結果に効くため、数値を読むときの前提として明記する。

| 箇所 | 決めた内容 | 影響 |
| --- | --- | --- |
| 介入の発動閾値 | `naive` は炎上2件以上／レビュー12件以上、`skilled` は炎上1件以上／レビュー6件以上／andon はレビュー10件以上 | 介入回数と勝率。閾値を変えれば方針の強さは変わる |
| カードの `selective` 条件 | 集中力6割以上、レビュー6件未満、炎上0 のときだけ発動 | RI-77 の `skilledSelectiveCards`（11/40）の位置づけ |
| ビート `stateAware` の評価式 | 出荷 ×0.05、予算・シニアHP・士気・**信頼**は残量が少ないほど重く（`1+(100-現在値)/50` 倍）、負債 ×-0.4、レリック +4。**適用後に敗北条件へ入る選択肢は除外する**（予算0・シニアHP1以下・士気1以下・負債90以上・**信頼10以下**）。信頼が危機域（15以下）へ踏み込む場合は -6 | RI-84 の decision 由来の敗北件数、`trustExhausted` の件数 |
| ベンチ配置 | レビュー適性 ≧ 実装適性なら review、それ以外は coding | 採用・復職の効果 |
| 方針固有の編成の再適用 | ベンチ配置と同じタイミング（`sprint` 以外の全フェーズ）で `spec.ai` / `spec.formation` を掛け直す | 復職者の AI 配布・編成。RI-76 の AI 統制と F-10 のビルド比較 |
| 高負荷スプリントを受ける条件 | シニアHPと士気の低い方が45を上回るぶんを出荷機会（×0.15）、下回るぶんをリスクとして評価し、技術的負債ぶんを引く（×4）。負荷倍率は `ELITE_TASK_MUL`（=1.6）から読む | `elite-offer` の選択。高負荷スプリントの発生数と F-4 の帯判定 |
| 選択的採用の「欠員」 | 休職者がいる、または実働が2名以下。かつ**採用費を引いた残額**が `RECRUIT_COST`（=25）以上 | `skilledSelectiveHire` の結果 |
| ショップ購入 | レリック優先、次に安いカードから。残す予算は**採用方針で変える**（採用する方針は次の採用機会のため `RECRUIT_COST`＝25、採用しない方針は四半期レビューの危機条件 `budget<=5` に対する余裕として10）。`skilledShopBuy` は `recruit: 'skip'` なので後者 | `skilledShopBuy` の結果 |
| 休息の返済閾値 | 技術的負債50以上で `repay`、それ以外は `heal` | `skilledRestRepay` の結果 |
| F-11 の標本 | 代表4方針（`naive` / `skilledNoHire` / `aiFullBet` / `noAi`）に固定 | RI-85 の分位点 |
| F-4 の標本 | 代表3方針（`naive` / `skilledNoHire` / `noInterventionCtl`）に固定 | RI-74 の帯外率 |
| 進化の解放順 | 初見はツリー表示順、熟練はレビュー容量優先、AI ビルドは AI 優先、品質ビルドは品質優先 | ビルド差分と F-11 |
| ドラフト選好 | AI ビルドは `copilot` / `claude-code` / `devin` / `ai-guideline`、品質ビルドは `auto-test` / `pr-size-limit` / `docs` / `review-bot` / `hire-senior` を優先 | ビルド差分 |
| F-11 の主要指標 | **Q1 で解放できるノード数**（方針に依らないので、これは決めた閾値ではなく実測）。ブランチの偏りは方針の `evolve` が決めるため成立判定に使わない | RI-85 の成立可否 |
| F-7 の判定方針 | 初見相当は `naive`（介入は炎上2件以上／レビュー12件以上、約4.1秒ごとに判断、進化はツリー表示順） | RI-72 の成立可否 |
| `noAi` の位置づけ | **ビルド差分の方針であって AI の統制条件ではない。** `skilledNoHire` に対し AI 配布のほか andon の有無・進化ブランチ（`qualityFirst`）・ドラフト選好（`quality`）・採用（`hire`）まで違う | AI の因果は `noAiCtl`（AI だけを外す）で見る |
| 反応間隔の換算 | `stepMs` は壁時計ではなくシミュレーション時間。`stepMs/100` tick、1 tick が 1x で 680ms（`MS_PER_TICK_1X`）。`skilled`=3 tick=約2.0秒、`naive`=6 tick=約4.1秒 | F-4 の「介入が間に合うか」の読み方 |

**閾値の変更で順位が入れ替わりうる結論**（`naive` と `skilled` の優劣、カードの `selective` の効果、
`skilledSelectiveHire` の「欠員」の定義、ショップの購入順）と、
**閾値に依らない結論**（Nightmare の第1スプリント全敗、ボスの規定下限割れ、勝利種別が実質2種、
`reviewFreeze` が全294件 judgment ビートで確定すること）を区別して読む必要がある。
後者は方針をどう定義しても変わらない。

とくに `skilledSelectiveHire` の閾値は一度直している。当初は「採用後も `RECRUIT_COST` の
2倍が残る」条件にしていたが、これは採用時点で予算75を要求する一方**実測の予算は最大68**で、
一度も成立せず `skilledNoHire` と40ラン全部が同一のランになっていた（何も測っていなかった）。
到達可能な水準（採用費を引いた残額が `RECRUIT_COST` 以上）へ下げた結果、40ラン中4ランで
実際に採用が発生して経過が分かれ、そのうえで勝敗は 14/40 で `skilledNoHire` と同じだった。
つまり「発火しなかったから同じ」ではなく、**発火しても勝敗が変わらない**。
ただし閾値をさらに緩めれば `skilled`（無差別採用、8勝）へ近づくので、
言える範囲は「採用が有利になる設定はこの範囲には無い」までである。

## 結論の要約

**成立している基準**:

- **F-9 のうち進行速度と決着位置は成立している**（**F-9 全体の成立ではない**。下記の限界を参照）。
  難易度別の p50 は `aiDependency` 1 / `moraleCollapse` 2 / `seniorBurnout` 3 / `reviewFreeze` 8 /
  `techDebt` 10 / `budgetExhausted` 11 / `reorgRequired` 18 / `trustExhausted` 24 と明確に分かれ、
  決着するフェーズも敗因ごとに違う（RI-84）。

  同一難易度・同一方針内でも `reviewFreeze` はおおむね一貫する。easy / normal / hard の
  `naive` / `skilledNoHire` / `onlyFirefight` / `noInterventionCtl` の11層のうち**8層で p50=8**。
  ただし**例外が3つある**。

  | 層 | n | p50 |
  | --- | --- | --- |
  | `normal` / `noInterventionCtl` | 4 | **15** |
  | `hard` / `onlyFirefight` | 4 | **15** |
  | `hard` / `noInterventionCtl` | 3 | **2** |

  介入しない条件では他の敗因（`seniorBurnout`・`techDebt`）が先に来るため、
  `reviewFreeze` へ至るランが偏る。hard では早期に凍結した3ランだけが残って p50 が短くなり、
  normal では逆に長く粘ったランが残って伸びる。
  いずれも n=3〜4 の小標本で断定はできないが、**「すべてで完全に一貫」とは言えない**。

  > **この一貫性の判定は計測条件の変更で容易に動く。** 直近3回の再計測で例外は
  > 2層 → 1層 → 3層と変わり、今回は `onlyFirefight`（介入する方針）にも例外が出て、
  > 「介入しない条件だけがずれる」という前回までの整理も崩れた。層あたり n=1〜5 しかない。
  > **層別化から言えるのは「完全には一貫しない」までで、ずれの向きや原因は特定できていない。**

  一方 `seniorBurnout` は同じ層別化で p50 が 3〜22 とばらつく。こちらは層あたり n=1〜4 しかなく、
  **方針差なのか標本の小ささなのかを区別できない**。層別化で確認できたのは
  `reviewFreeze` の「介入する4方針では p50=8 で一貫し、介入しない条件だけがずれる」までである。

  **未検証の部分**: F-9 は進行速度に加えて「その時点で**打てた手**が敗因ごとに異なる」ことも
  要求するが、これは測れていない。`SprintLog.attempts` に残るのは各方針が**実際に試した**
  アクションの結果だけで、危険域で**利用可能だった**手の全体ではないためである。
  `applyAction`（`src/sim/actions.ts`）の対象有無の判定は効果関数を実行しないと分からず、
  実行すると盤面が変わるので、読み取り専用では再現できない（集中力とクールダウンだけは
  スナップショットから読めるが、それだけでは「打てた手」を網羅できない）。
  したがって現状の根拠は**進行速度と決着位置の差**までであり、
  「進行速度だけが違って対処法は同じ」という可能性は排除できていない。

**成立していない基準**:

| 基準 | 未充足の内容 | 対応 |
| --- | --- | --- |
| F-1 | アンドン単独19/40・緊急対応単独16/40 が全31方針中トップ。逆に無差別採用は一貫して勝率を下げる（10/40 vs 14/40） | RI-72 |
| F-2 | **カード層は成立**（使う14 vs 使わない7）。ショップ購入と休息の選択は 13〜14/40 で、無投資14との差は0〜1しか無い。第4層（目標修正）も共通コホートで初回修正の次四半期まで生存 68.8〜81.3% | RI-77・RI-82 |
| F-4 | 代表方針で easy の通常スプリントは 65.4% が絶対下限30秒を割る。ボスは全難易度が規定下限割れ | RI-74 |
| F-5 | 条件を揃えると介入の寄与が期待値・分散ともほぼ消える | RI-83 |
| F-6 | 敗北時の教訓が敗因ではなく組織診断4種に紐づき、その敗因への次の一手にならない | RI-81 |
| F-7 | 初見相当（`naive`・メタ解放 fresh）の勝率が easy 50% / normal 50% / hard 10% / nightmare 0%。20%前後に当たる難易度が無い | RI-72 |
| F-8 | Nightmare は255ランが第1スプリントで敗北し、打つ機会が一度も無い。ただし「何スプリント前から選択肢が消えたか」は未計測（RI-88 と同じ観測手段の不足） | RI-73・RI-88 |
| F-9 | 進行速度と決着位置は敗因ごとに違うが、「打てた手」の差は測れていない | RI-88 |
| F-10 | 勝利種別が実質2種。方針で分岐はするが「重アクションを使ったか」でしか分かれない | RI-75 |
| F-11 | Q1 の入手ポイント p50=45 に対しツリー総コストは26。代表方針の69.4% が Q1 で全解放し、方向を選ぶ構造が無い | RI-85 |
| F-12 | ドラフトのマリガンが無い | RI-80 |

## 課題一覧

### RI-72 難易度カーブと、常に正解／常に不正解な手がある構造（優先度: 高 / F-1・F-7）

**F-7 は初見相当の方針（`naive`）の勝率で判定する。** 全方針の平均は使わない。
`adj*` の統制群や `onlyXxx` のような実験用方針を足し引きするだけで、ゲームも初見プレイも
変わっていないのに平均が動いてしまうためである（実際 `skilledBase` の複製である `adj*` を
6本追加したときに easy の平均が動いた）。

| 難易度 | **`naive`（初見相当・判定に使う）** | 目標との差 |
| --- | --- | --- |
| easy | **5/10（50%）** | 20% に対し過大 |
| normal | **5/10（50%）** | 20% に対し過大 |
| hard | **1/10（10%）** | 20% に対しやや過小 |
| nightmare | **0/10（0%）** | 20% に対し過小 |

判定はメタ解放も初見相当（`PT_META=fresh`）に限る。全解放の結果を初見の勝率として
読むとドラフト候補の違いが混ざるため、レポートは `fresh` のランだけで集計する。

**F-7（初見相当の勝率20%前後）に合う難易度が無い**。easy と normal は初見でも半分勝ててしまい、
hard は 10%、nightmare は全敗する（RI-73）。50% から 10% へ一段で落ちており、
中間の 20% 前後に当たる難易度が存在しない。「初見は負けて学ぶ」というカーブが、
導入難易度側にも中間にも無い。

参考として他方針の内訳（**実験用統制群を含むため、この平均は成立判定に使わない**）:

| 難易度 | 全方針平均 | `idle` | `passive` | `naive` | `skilled` | `onlyFirefight` |
| --- | --- | --- | --- | --- | --- | --- |
| easy | 72.3%（224/310） | 5/10 | 6/10 | 5/10 | 7/10 | **10/10** |
| normal | 39.7%（123/310） | 0/10 | 0/10 | 5/10 | 3/10 | **5/10** |
| hard | 7.4%（23/310） | 0/10 | 0/10 | 1/10 | 0/10 | **1/10** |
| nightmare | 0%（0/310） | 0/10 | 0/10 | 0/10 | 0/10 | 0/10 |

easy は完全放置（`idle`）でも 5/10 勝てる。これは方針を増減しても動かない事実なので、
F-7 の補強として読める。

**F-1 の違反は2方向にある**。単一介入群は進化順（`reviewFirst`）とビート選択（`stateAware`）を
`skilledNoHire` と揃えてあるため、差は介入構成のみに帰属できる。

目標修正を固定する `adj*` 6方針は別条件（RI-82）なので、この表からは除く。

| 方針 | 40ラン中の勝利 |
| --- | --- |
| `onlyAndon`（アンドンのみ） | **19** |
| `onlyFirefight`（緊急対応のみ） | **16** |
| **`skilledNoHire`（採用なし）** / `skilledShopBuy` / `skilledRestRepay` | **14** |
| `aiFullBet` / `skilledSelectiveHire` / `skilledRestUpgrade` | 13 |
| `onlySplit` | 12 |
| `naive` / `onlyOvertime` / `onlyAssign` / `noAi` / `noInterventionCtl` / `skilledSelectiveCards` | 11 |
| **`skilled`（無差別採用あり）** / `onlyPair` / `onlyThrottle` / `noAiCtl` / `probe`（全部撃つ） | **10** |
| `onlyInterrupt` | 9 |
| `reviewHeavy` | 8 |
| **`skilledNoCards`（カード不使用）** | **7** |
| `passive` | 6 |
| `idle` | 5 |

- **アンドンと緊急対応は「常に打てば得」**。アンドン単独 19/40・緊急対応単独 16/40 が
  全方針中の1位・2位で、複合方針（14/40）を上回る。
- **無差別採用は「常に見送るのが正解」**。`skilled` 10/40 に対し採用を外した `skilledNoHire` は 14/40。
  採用方針を全経路（専用フェーズ・ショップ・休息・即時採用イベント）に適用し、さらに
  **採ったメンバーを能力に応じて実働レーン（review / coding）へ配置した上での結果**である。
  当初はハーネスが採用メンバーをベンチに残していたため疑いがあったが、採用・復職の双方を
  実働へ戻しても差は残った（10 vs 14）。`budgetExhausted` 敗北は1,240ラン中14件。
- **「必要なときだけ採る」も見送りと同じ**。欠員（休職者あり／実働2名以下）があり予算にも
  余裕があるときだけ採る `skilledSelectiveHire` は **13/40** で、採らない `skilledNoHire`
  14/40 をわずかに下回る（難易度別 8/4/1/0 対 8/5/1/0）。採用を無差別にすると大きく損をし、
  選択的にしても得にならない。
  採用という層に、状況によって正解が入れ替わる構造が無い。

どちらも状況によって正解が入れ替わらず、F-1 の「固定の強手が存在しない」を満たさない。

### RI-73 Nightmare は AI 依存を意識しない方針で第1スプリント敗北が確定する（優先度: 高 / F-8）

nightmare は **31方針310ランすべて敗北**し、うち **255ランが `aiDependency`**。
敗北条件は `org.aiDependency >= 95 && org.aiLiteracy <= 30`（`src/sim/outcome.ts:63-65`）で、
nightmare の初期値 `aiDependencyBase`=55 / `aiLiteracy`=25 はリテラシー側を最初から満たしている。

**回避経路は2種類ある**。依存度を下げる経路と、**リテラシーを上げて敗北条件そのものを外す経路**である。
とくに `onlyPair`（ペアレビュー連打）は**依存度100のまま**リテラシーを 25→62 へ上げて回避する。
`pairReview` の説明は「詰まったPRをペアで処理。AI Literacy が上がる」で、
SPEC 第19章の「AI は強い。しかし雑に使うと壊れる」に最も合致する対処である。

問題は回避不能なことではなく、**回避に必要な方針が事前知識を要し、外すと第1スプリントで終わる**こと。
初手で終わるため「負けて学ぶ」が成立しない。リテラシー経路はチュートリアルにもリザルトにも現れない。

### RI-74 スプリントが規定帯をほぼ全面的に下回る（優先度: 高 / F-4・第3.1）

SPEC 第3.1 の規定は**通常60〜120秒（絶対下限30秒）・ボス90〜180秒**。
高負荷スプリント（`elite`）も「スプリント1本」の目標が要るため通常帯で判定した。

**標本は固定した代表3方針**（`naive` / `skilledNoHire` / `noInterventionCtl`）に限る。
難易度内の全方針を連結すると、方針の構成と生存長がそのまま規定帯の割合の重みになり、
同じ `skilledBase` の複製を足すだけで値が動いてしまう。

| 難易度 | 種別 | n | p50 | p50 帯判定 | 下回り | 上回り | 絶対下限30秒未満 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| easy | 通常 | 179 | 23.1秒 | **帯外** | **100%** | 0% | **65.4%** |
| easy | 高負荷 | 13 | 29.9秒 | 帯外 | 100% | 0% | 53.8% |
| easy | ボス | 34 | 32.6秒 | **帯外** | **100%** | 0% | — |
| normal | 通常 | 237 | 32.0秒 | 帯外 | 95.8% | 0% | 46.4% |
| normal | 高負荷 | 18 | 53.0秒 | 帯外 | 72.2% | 0% | 5.6% |
| normal | ボス | 43 | 39.4秒 | 帯外 | **100%** | 0% | — |
| hard | 通常 | 226 | 45.6秒 | 帯外 | 78.8% | 0.4% | 19.0% |
| hard | 高負荷 | 14 | 102.0秒 | **帯内** | 0% | 35.7% | 0% |
| hard | ボス | 34 | 39.4秒 | 帯外 | 94.1% | 0% | — |
| nightmare | 通常 | 30 | 115.6秒 | **帯内** | 0% | 43.3% | 0% |

**ボススプリントは easy 100% / normal 100% / hard 94.1% が規定下限（90秒）を下回る**。
山場であるはずのボスが、通常スプリントとほぼ同じ長さで終わっている。

通常スプリントも easy で 100% が規定下限（60秒）を下回り、**65.4% は絶対下限の30秒すら割る**。
規定帯に p50 が入るのは hard の高負荷スプリントと nightmare だけで、
**初見が最初に触れる easy が最も規定から外れている**。

既存のペーシング回帰テスト（`tests/unit/sprintTempo.test.ts`）は無介入経路で通常スプリントの
絶対下限・p50・p90 を検査しているが、対象は normal のみ。ボスは上限しか検査しておらず、
下限（90秒）と高負荷スプリントは未検査。

### RI-75 勝利種別が実質2種で、「重アクションを使ったか」でしか分岐しない（優先度: 高 / F-10）

1,240ラン中370勝の内訳は `healthy` 186（50%）/ `noDamage` 183（49%）/ `happiness` 1。
`aiSuccess` / `management` / `chaos` / `normal` は**0件**で、`happiness` も1件しか出ない。
実質的に `healthy` と `noDamage` の2種である。

方針別に見ると分布は変わるが、分かれ方は一様である。

| 方針 | 勝利種別 |
| --- | --- |
| `onlyAndon` | `healthy` 18 / `noDamage` **0** |
| `skilledNoCards` | `healthy` 8 / `noDamage` **0** |
| `onlyFirefight` | `noDamage` 16 / `healthy` 1 |
| `aiFullBet` | `noDamage` 12 / `healthy` 1 |
| `noAi` | `noDamage` 11 / `healthy` **0** |

`evaluateWinType`（`src/sim/outcome.ts:103-118`）の先頭判定が
`!usedHeavyActions && totals.spread === 0` のため、**残業・アンドンを使ったかどうかだけ**で
`healthy` と `noDamage` が入れ替わる。AI 全ベットと AI 解除という正反対のビルドが
どちらも `noDamage` 一色になることが、この構造を端的に示している。

一方、**組織診断はビルドで明確に分かれる**（進化ブランチとドラフト選好を分岐させた結果）。

| 方針 | 組織診断 |
| --- | --- |
| `aiFullBet` | `reviewHell` 14 / `seniorSacrifice` 26 |
| `noAi` | `documentationKingdom` 10 / `reviewHell` 11 / `healthyAcceleration` 5 / `seniorSacrifice` 13 / `reworkSpiral` 1 |

つまり**ビルドの違いは組織診断には出ているが、勝利種別には反映されていない**。
F-10 が求めるのは後者なので、勝利種別の判定側を直す余地がある。

### RI-76 AI 導入が既定 ON で、既定のまま進むのが有利（優先度: 高 / F-1・F-2・F-10）

初期ロスターは `aiAssigned: arch.preferred === 'coding'`（`src/sim/member/roster.ts:135`）で、
コーダー志向のメンバーには最初から AI が配られている。既定プレイの AI 利用率は 74〜86%、
最終 AI 依存度は 100 に張り付く。

選択の入口は存在する（`SetupScreen`「編成 — スプリント開始前に配置とAIを決める」、
`FormationScreen.tsx:172` の「🤖 AI配布中」ボタン）。課題は次の3点である。

1. **既定が ON で、既定のまま進むのが有利**。`aiFullBet` は既定とほぼ同じ結果で、選び直す動機が無い。
2. **解除側の代償が一方的に大きい**。AI 配布だけを外した統制条件 `noAiCtl` は 10/40 で、
   `skilledNoHire` 14/40 に届かない（easy 8→7 / normal 5→2 / hard 1→1 / nightmare 0→0）。
   ビルドごと品質寄りに揃えた `noAi` でも 11/40、`aiFullBet` は 13/40。
3. **段階が無い**。導入は編成画面の on/off だけで、四半期を通じて問い直す機会が無い。

#### AI の因果は効いているが、効き方は「出荷が増える」ではない

比較には **`noAiCtl`**（`skilledNoHire` から `setMemberAi` だけを false にした統制条件）を使う。
ビルド差分の `noAi` は AI に加えて andon の有無・進化ブランチ・ドラフト選好・採用まで
同時に違うため、差を AI へ帰属できない。

出荷は**同一 seed の同一スプリント番号**で対応を取る（方針で到達スプリント数が違うので、
到達スプリントを平均するだけでは生存者の構成差が出荷差に化ける）:

| 難易度 | S1 | S2 | S3 |
| --- | --- | --- | --- |
| easy | 278.3 → **307.1** | 307.3 → **357.1** | 349.9 → 347.2 |
| normal | 277.5 → **353.2** | 291.5 → **378.8** | 395.7 → **428.8** |
| hard | 265.9 → **334.3** | 311.4 → **394.0** | 421.4 → **451.3** |
| nightmare | 269.7 → **304.6** | 共通到達なし | 共通到達なし |

（`skilledNoHire` → `noAiCtl`。各セル共通 n=8〜10）

**AI を切ると1スプリントの出荷はむしろ増える**。比較できた10セル中9セルで上回り、
残る1セル（easy S3）もほぼ同等で、明確に下回るセルは無い。にもかかわらず勝率は 14→10 に下がる。
つまり実装上、AI の寄与は出荷ではない。

敗因の構成は入れ替わる。`skilledNoHire` の `aiDependency` 10件が消える代わりに、
`seniorBurnout` 6→9・`reviewFreeze` 9→13 が増え、`trustExhausted` 3件・`reorgRequired` 4件が
新たに出る。敗北ランの長さも 6.8→13.9スプリントへ伸び、**長く粘って結局負ける**形になる。
Nightmare では AI を切ると第1スプリント即死（RI-73）を回避でき、平均 1.0→6.6スプリントまで
延びるが、勝利には至らない。

一方で四半期目標の未達回数は AI なしの方が多い（1四半期あたり 0.67→1.13、
達成〈met+exceeded〉は 33%→14%）。**1スプリントの出荷が多いのに四半期目標の達成率は下がる**という
食い違いがあり、原因は特定できていない（RI-68 の Delivery KPI のスケール不整合が絡む可能性がある）。

> **この統制条件にも残差がある。** `spec.ai` が変えるのはロスターの `aiAssigned` だけで、
> そこから決まるのは intake の AI 採用率（`aiAdoptionShare`）である。`org.aiEnabled` は
> true のままなので、`assignTask` 介入が `defaultAssignee` 経由で個別タスクを AI へ回す
> 経路が残る（実測で482スプリント中6件、最大4%）。**AI 配布ゼロ＝AI 利用ゼロではない**。
> 残差は小さく上の結論を動かさないが、「AI を完全に断つ」条件を測るには
> `org.aiEnabled` 側も落とす別の統制が要る。

> **以前の記述は誤りだった。** 「AI 配布を切ると出荷 334.5→291.4」を因果の根拠にしていたが、
> これは統制条件ではない `noAi` の値で、しかも現在は向きが逆である。
> 「AI で出荷が増える」は実務感覚とも一致するぶん、**実装がそうなっていないことが問題**である。

開始時 AI の全面撤廃ではなく、既定値の誘導・解除側の代償・導入の段階化に加えて、
**AI が何を良くして何を悪くするのかを出荷の増減として体感できるようにすること**を対象にすべきである。

### RI-77 スプリント間投資のうち、ショップと休息の選択が結果を変えない（優先度: 高 / F-2）

採用条件を揃えた3条件（いずれも `recruit: 'skip'`、進化は `reviewFirst`）:

| 条件 | カードの使い方 | 40ラン中の勝利 | easy / normal / hard |
| --- | --- | --- | --- |
| `skilledNoHire` | 無差別に発動 | **14** | 8 / 5 / 1 |
| `skilledSelectiveCards` | 集中力6割以上・渋滞も炎上も無いときだけ発動 | 11 | 7 / 4 / 0 |
| `skilledNoCards` | 使わない | **7** | 6 / 1 / 0 |

**カードは寄与している。** 使う条件が使わない条件を **14 対 7** で上回り、向きは
easy（8対6）/ normal（5対1）/ hard（1対0）の3難易度すべてで一致する。

しかも**カードを外すと介入回数はむしろ増える**（集中力の競合が消えるため。easy の成立数
200→285、normal 314→530）。介入を多く打てるようになっても勝率は下がるので、
**カードに払う集中力は、その分の介入より価値がある**という交換が成立している。
これは F-1・F-2 が求める「代償のある選択」そのものである。

> **この結論は前回まで逆だった**（「カードは集中力を消費するだけで結果に寄与しない」）。
> 原因はハーネス側の欠陥で、同じ tick 内で複数の介入を試すとき `when` の判定に
> ループ開始時点の盤面を使い続けていた。先行の介入がレーンを変えても後続がそれを見ないため、
> 撃つべきときに見送り、不要なときに撃っていた。各 `dispatch` の直前に盤面を取り直すよう
> 直したところ、カード条件の差が 3勝ぶん → 5勝ぶん → **7勝ぶん**（復職者の配置漏れも直した後）
> へ広がり、向きも全難易度で揃った。Codex レビューの指摘による訂正。

一方**ショップ投資と休息の選択は、結果を変えているとは言えない**。

| 条件 | スプリント間の投資 | 40ラン中の勝利 | easy / normal / hard |
| --- | --- | --- | --- |
| `skilledNoHire` | 何も買わず、休息は常に回復 | **14** | 8 / 5 / 1 |
| `skilledShopBuy` | ショップでレリック優先→安いカードから購入 | 14 | 7 / 6 / 1 |
| `skilledRestRepay` | 負債50以上なら休息で返済 | 14 | 8 / 5 / 1 |
| `skilledRestUpgrade` | 休息でレベルが最も低いカードを強化 | 13 | 8 / 4 / 1 |

**差は0〜1しか無い。** ショップ購入と負債返済は無投資と**完全に同数**で、カード強化だけが
1つ下回る。カード層で見られた「全難易度で向きが一致し、差が7勝ぶん」という関係とは質が違い、
seed 差と区別できない。SPEC 第19.1 F-2 が求める「スプリント間の投資が結果を変える」は、
**カード層では成立するが、ショップ層と休息の選択では成立を確認できない**。

> **この層の順位は計測条件の変更で容易に入れ替わる。** 直近3回の再計測で
> `skilledRestUpgrade` は 13→15→13、`skilledShopBuy` は 14→13→14 と動き、
> そのたびに無投資を上回る方針が入れ替わっている。n=40 で±1〜2の揺れが出る以上、
> **この層については「差が無い」以上のことを主張すべきではない**。順位を結論に使わないこと。

> **ショップの予約額は一度直している。** 当初はどの方針も `RECRUIT_COST`（=25）を残していたが、
> `skilledShopBuy` は `recruit: 'skip'` なので次の採用に備える必要がない。予算30で8のカードが
> 出ても買えず（買っても22残り、四半期レビューの危機条件5には十分余裕がある）、
> 「ショップへ投資する」条件が実際には多くの機会を見送る保守方針になっていた。
> 採用しない方針の予約を10へ下げたが、結論は変わらなかった。

介入の機会自体は足りている。全8種を 1 tick ごとに撃つ `probe` の成立数は
easy p50=7 / hard p50=8 で、第3.1 の「1スプリントあたり 3〜8回」の帯に入る
（ただし順序バイアスを含むため上限としては読まない）。

**対象不足はアクションによって大きく異なる**（単一介入方針で測った `no-target` 率）:

| `firefight` | 89.5% | 86.9% | 82.2% | 50.5% |
| `assignTask` | 78.9% | 90.2% | **94.9%** | **98.2%** |

`assignTask` は難易度が上がるほど空振りし、`firefight` も easy で約9割が空振りする。

### RI-78 敗因ラベルが3種類の原因を1つに潰す（優先度: 中 / F-6・F-8）

`trustExhausted` は四半期 outcome の `missed_crisis` と `shutdown` の**両方**から作られる
（`loseReasonForOutcome`、`src/sim/run/quarterReview.ts:464`）。発火条件を分解すると:

| outcome | 発火条件 | 件数 |
| --- | --- | --- |
| `missed_crisis` | `trust<=15` | 22 |
| `missed_crisis` | `budget<=5` | **1** |
| `shutdown` | `seniorHp<=5` かつ `missedCount>=2` | **3** |
| `shutdown` | `trust<=10` | 1 |

`trustExhausted` 27件のうち信頼由来は23件で、残り4件は**予算切れ（1件）とシニア枯渇（3件）**。
予算由来が6件から1件へ減ったのは、ビート評価に予算を入れて即敗北する選択肢を外したため

また `budgetExhausted` / `trustExhausted` / `reorgRequired` は直前スプリントの

### RI-79 評価が無介入と熟練を区別しない（優先度: 中 / 第4.6）

> **これは F-6 の根拠ではない。** SPEC 第19.1 F-6 は「敗北画面・リザルト・組織診断から
> 具体的な次の一手と現場への示唆が読み取れるか」を要求する基準で、スプリント評価の
> 中央値とは別物である。評価が一致しても敗北時の説明品質は分からないし、分かれても
> F-6 の成立は確認できない。F-6 の判定は RI-81（敗北画面の提示内容）で行う。
> ここで見るのは「操作の巧拙がスプリント評価に反映されるか」だけである。

1,240ラン・9,448スプリントの評価分布は
**S 5529（58.5%）/ A 2503（26.5%）/ B 754（8.0%）/ C 363（3.8%）/ D 299（3.2%）**。
S と A で 85.0% を占める。

比較は**両方針が到達した seed だけ**で行う。到達率が違うまま生存ランを独立に集めると、
早期敗北した低評価 seed が片方からだけ脱落し、生存者バイアスで優劣が反転しうるためである。

同一難易度・同一スプリント番号での中央値比較（無介入 `passive` vs 熟練 `skilledNoHire`）:

| 条件 | 共通 n | `passive` | `skilledNoHire` | 差 |
| --- | --- | --- | --- | --- |
| easy S1 | 10 | S | S | 一致 |
| easy S2 | 9 | A | S | 1段階 |
| easy S3 | 9 | S | S | 一致 |
| normal S1 | 10 | A | A | 一致 |
| normal S2 | 9 | B | B | 一致 |
| normal S3 | 8 | A | S | 1段階 |
| hard S1 | 10 | C | B | 1段階 |
| hard S2 | 9 | B | B | 一致 |
| hard S3 | 5 | C | A | **2段階** |
| nightmare S1 | 10 | D | D | 一致 |

（nightmare S2・S3 は両方針が到達した seed が無く未計測。）

### RI-81 敗北画面に「次の一手」が無い（優先度: 中 / F-6）

`RunResultScreen` が敗北時に示すのは敗因ラベル＋一文の説明、組織タイプ診断、メタ進行ポイント。

### RI-82 目標修正の選択が結果をほとんど変えない（優先度: 中 / F-2 第4層）

目標修正だけを固定する統制方針（**全6選択肢**、各40ラン）。目標修正フェーズ自体は
1,240ラン中514ラン（41.5%）で発生しており、選択機会は足りている。

比較は**共通コホート**に限る。`availableAdjustments` は各選択肢の適用後状態で候補を絞るため、
方針ごとに「提示され選べたラン」が異なり、そのまま勝率を並べると選択の効果と選抜条件を
分離できない。そこで**同一メタ・同一難易度・同一 seed で6方針すべてが同じ四半期に自分の修正を適用できた
組**だけを残した（16組）。キーにメタ解放を含めないと `fresh` と `full` の同一 seed が衝突する。adj* 6方針は `goalAdjustment` 以外すべて同一なので、
最初の修正までは同一 seed の6ランが完全に同じ経過をたどる。実際、コホート内の修正時期は
**全方針で Q1** に揃っており、事前状態は同一である。

**主指標は「初回修正の次四半期まで生存したか」にする。** ラン全体の勝敗を主指標に置くと、
初回選択の効果を測れない。共通コホートで揃うのは最初の修正までで、その後の修正は方針間で
統制されていないためである（同じ seed でも、ある方針は `request_budget` を2回選んだ後に
`cut_scope` を3回選び、別の方針は1回で終わる）。ラン全体の勝敗にはその後続選択がすべて乗る。
初回修正の四半期を Q とすると、Q+1 の四半期レビューまでなら後続の修正はまだ1回しか挟まらない。

| 選択 | n | **初回修正の次四半期まで生存** | 参考: ラン全体の勝率 | 参考: 総スプリント 平均 |
| --- | --- | --- | --- | --- |
| `request_budget`（予算要求） | 16 | 68.8% | 37.5% | 14.8 |
| `pause_ai_rollout`（AI 展開の一時停止） | 16 | 68.8% | 43.8% | 16.3 |
| `cut_scope`（スコープ削減） | 16 | 75.0% | 37.5% | 14.7 |
| `extend_deadline`（期限延長） | 16 | 75.0% | 43.8% | 14.6 |
| `quality_pivot`（品質ピボット） | 16 | 75.0% | 56.3% | 13.4 |
| `reorg_teams`（組織再編） | 16 | **81.3%** | 50.0% | 14.3 |

効果がまったく異なる選択肢（スコープ削減 / 予算追加 / AI 停止 / 組織リセット）を
**同一の事前状態から**選ばせても、生存率は 68.8〜81.3% に収まる。
最大差は16ラン中2ランぶん（11 vs 13）で、n=16 では有意と言い切れない。

参考値のラン全体の勝率も 37.5〜56.3% と近い幅に収まるが、こちらは上記の理由で
初回選択へ帰属できないため、成立判定には使わない。

なお統制前（方針ごとの「提示され選べたラン」をそのまま使った集計）では
勝率が 52.9〜76.5% というより高い値になっていたが、これは選抜条件の差を含んでいた。

### RI-83 条件を揃えると介入の寄与がほぼ消える（優先度: 高 / F-5）

`noInterventionCtl`（`skilledNoHire` から**介入だけ**を外し、カード・進化・採用を揃えた統制）との比較:

| 方針 | easy | normal | hard | 全40ラン |
| --- | --- | --- | --- | --- |
| `noInterventionCtl`（介入なし） | 7/10 | 4/10 | 0/10 | **11** |
| `naive`（初見の介入） | 5/10 | 5/10 | 1/10 | 11 |
| `skilledNoHire`（熟練の介入） | 8/10 | 5/10 | 1/10 | 14 |

**介入なしと初見の介入は同点（11）**、熟練の介入との差は **+3**。
`skilledNoHire` の伸びの大半はカードとの相互作用である（RI-77）。
介入だけを外した `noInterventionCtl` と初見の介入 `naive` は同点にとどまる。
**「初見の介入には価値が無い」という関係が残っている。**

分散も同様で、同一スプリント番号の出荷 CV に方針間の一貫した差は出ない。
**3方針すべてが到達した seed のスプリントだけ**で比べた第1スプリント出荷 CV:

| 難易度 | 共通 n | `noInterventionCtl` | `naive` | `skilledNoHire` |
| --- | --- | --- | --- | --- |
| easy | 10 | 10.6% | 11.3% | 12.7% |
| normal | 10 | 11.1% | 10.8% | 9.3% |
| hard | 10 | 7.9% | 7.2% | 9.8% |
| nightmare | 10 | 13.4% | 11.3% | 8.2% |

介入する方針の CV が最小になるのは normal と nightmare だけで、easy と hard では
**介入なしより大きい**。F-5 が求める「介入が下振れを潰す」向きは観測できない。

> CV は**メタ解放プロファイルごとに分けて集計する**。共通コホートのキーに `meta` を含めれば
> 対応は取れるが、CV は対応差ではなく周辺分布の分散なので、`fresh` と `full` を同じ配列へ
> 入れるとメタ解放による平均・分散の差が介入効果へ混入する。上記は `fresh` の値である
> （今回のランは全て `fresh`）。

以前「介入は勝率を改善している（完全放置 7 → 熟練 16）」としていたが、これは
**進化・カード・採用が同時に変わっていた**ためだった。介入だけを統制すると、
期待値でも分散でも寄与がほとんど無い。

SPEC 第19.1 F-5 は「無介入は損ではなく不安定。介入の価値は結果の偏差を抑えること」と
定義しているが、実装は期待値も分散も動かしていない。**実装を定義へ寄せる**方針で決着済み
（2026-07-26。SPEC 第19.1 F-5 に記載）。

### RI-84 レビュー凍結は選択不能な判定イベントでしか確定しない（優先度: 高 / F-4）

> **これは F-8 の直接の根拠にはならない。** SPEC 第19.1 F-8 の観測条件は
> 「敗北が確定する**何スプリント前から**実質的な選択肢が消えていたか」であり、
> 最終イベントが選択不能であることだけでは満たせない。直前まで有効な回避策があり、
> 最後だけ judgment で決着するランも同じ形になるためである。
> 各時点で利用可能だった回避手段の記録が要る（RI-88 と同じ観測手段の不足）。
>
> ここで言えるのは「**決着の瞬間に操作の余地が無い**」までで、
> それが「詰みが早くから確定していた」ことを意味するかは未検証である。

敗北を確定させたフェーズを、ビートについては **judgment（選択不能な判定）** と
**decision（プレイヤーが選ぶ）** に分けて記録した。全870敗の内訳:

| 決着フェーズ | 件数 | 割合 |
| --- | --- | --- |
| `beat:judgment`（選択不能な判定イベント） | 459 | 53% |
| `sprint`（スプリント終了時） | 331 | 38% |
| `quarterReview` | 41 | 5% |
| `beat:decision`（選択イベント） | 33 | 4% |
| `shop` / `rest` / `recruit` | 6 | 1% |

なお `beat:decision` は、ビート選択の統制を進めた結果 90件（12%）→ 40件（5%）→ **33件（4%）**
と段階的に減った。最初は `firstChoice` が `urgent-demo` のようにシニアHPを削る先頭選択肢を
無条件に取っていた分、次は評価に予算が入っておらず `postmortem-culture` で予算0＝即敗北を
自分から選んでいた分である。**選択イベントで負けるランの多くは、盤面を見て選べば避けられる**。
残る33件がプレイヤーの選択を経た敗北の実数に近い。

敗因ごとに見ると、決着位置は明確に分かれる。

| 敗因 | 決着フェーズ | 敗北を確定させたイベント |
| --- | --- | --- |
| **`reviewFreeze`**（294件） | `beat:judgment` **100%** | `review-freeze`(judgment) |
| `seniorBurnout`（212件） | judgment / **decision** / sprint が混在 | `senior-burnout`(judgment)、`giant-ai-pr-judgment`(judgment)、`giant-pr`(decision) |
| `aiDependency`（255件） | `sprint` 100% | — |
| `techDebt`（39件） / `moraleCollapse`（15件） | `sprint` が大半 | — |
| `budgetExhausted` | `beat:decision` が大半 | `postmortem-culture`(decision) |
| `trustExhausted` / `reorgRequired` | `quarterReview` 100% | — |

**`reviewFreeze` だけが、盤面で対処する機会のないまま判定イベントで確定する**。
294件（敗因全体の34%）が該当し、プレイヤーはスプリントを走り切った直後に、
操作の余地がない画面で敗北を告げられる。しかも全294件が例外なく `review-freeze`(judgment) で
決着しており、他の決着経路が1件も無い。

一方 `seniorBurnout` は相当数が**プレイヤーの選択（`giant-pr` など）を経て確定**しており、
「操作の余地がない」とは言えない。`aiDependency`（255件）/ `techDebt` / `moraleCollapse` は
スプリント中に決まる。

（当初この所見は敗北の大半が「操作の余地がない画面」で確定するとしていたが、これは
ハーネスがビートの選択肢を常に先頭で取っていたためだった。`urgent-demo` の先頭は
`seniorHp -10 / morale -15` で、他の選択肢ならその消耗を避けられる。状態を見て選ぶ方針へ変え、
judgment と decision を分けて記録した結果、対象は `reviewFreeze` に絞られた。
Codex レビューの指摘による訂正。）

受入条件:

- `reviewFreeze` の敗北が、スプリント中に予兆と対処の機会を伴って決着する。
  または判定イベントで確定する前のスプリントで、明確な警告が出る。
- 敗因ごとの決着フェーズ分布（judgment / decision / sprint / quarterReview）を
  `npm run playtest` で検証し、回帰を検知する。

## 計測方法の訂正（経緯）

自動レビューの指摘により、以下の測定上の誤りを順次修正した。

> **本節に書かれた数値は「その修正を入れた直後に観測した値」であり、現在値ではない。**
> 各修正の効果（どれだけ動いたか、向きは何か）を残すための記録なので、後続の修正で
> 母集団や方針構成が変わっても遡って書き換えない。**現在値は本節より上の各節を参照すること。**
> 例えば 29 の `skilledRestRepay` や 34 の Q1 入手 p50 は、その後の修正で値が動いている。

1. **解放コンテンツが実プレイと違った** — `setUnlockedContent` 相当を適用し初見相当へ揃えた。
2. **進化ポイントを使い切っていなかった** — 「介入は投入するほど勝率が下がる」という誤結論の原因。
3. **介入の失敗理由を測っていなかった** — 「介入すべき状況が盤面に現れない」という誤結論の原因。
4. **採用方針が専用フェーズにしか効いていなかった** — ショップ・休息・即時採用イベントにも適用。
5. **初見と熟練で進化順が同じだった** — 初見はツリー表示順、熟練はレビュー容量優先に分離。
6. **単一介入群の進化順が比較対象と違った** — 揃えて F-1 の判定を介入構成に帰属できるようにした。
7. **ビルド方針で進化ブランチとドラフトが分岐していなかった** — AI／品質へ分岐させた。
8. **無介入群の進化・カード・採用が比較対象と違った** — `noInterventionCtl` を追加。これにより
   F-5 の判定が「介入は勝率を改善している」から「寄与がほぼ無い」へ変わった（RI-83）。
9. **分散比較にラン長が混入していた** — 同一スプリント番号ごとの CV へ変更。
10. **目標修正の比較に非統制ランが混入し、対象も3種類だけだった** — 全6種の統制方針へ。
11. **敗北直前の状態を敗北フェーズで区別していなかった** — 区別した結果 RI-84 が判明した。
12. **採用したメンバーをベンチに残していた** — `recruitMember` は採用直後を必ず `bench` に置くが、
    ハーネスが再配置していなかったため、採用が予算を払うだけになっていた。能力に応じて
    review / coding へ配置した結果、採用が勝率を下げる傾向は**変わらなかった**（10→9 と 16→17）。
13. **ビートの選択肢を常に先頭で取っていた** — `urgent-demo` の先頭は `seniorHp -10 / morale -15` で、
    イベント定義の並び順による自滅が敗因分布に混入していた。状態を見て選ぶ方針へ変え、
    judgment と decision を分けて記録した結果、RI-84 の対象が `reviewFreeze` に絞られた。

15. **F-11 の分子が「Q1 に1ノード解放」だった** — 複数ブランチへ均等投資したランも

21. **ショップのカード・レリックを一度も買っていなかった** — F-2 のスプリント間投資のうち

    出しうる。`fresh` のランだけで判定するようにした。
31. **目標修正コホートのキーにメタ解放が無かった** — `fresh` と `full` の同一 seed が衝突する。
32. **評価中央値を到達ラン独立で比較していた** — 到達率が違うと生存者バイアスで優劣が反転しうる。
    両方針が到達した seed だけの共通コホートへ変更した。
33. **F-11 の標本が方針構成に依存していた** — 全ランを母数にすると方針を足し引きするだけで
    分位点が動く。代表4方針へ固定し、構造的事実（総コスト26 vs Q1 入手 p50=43）を主指標にした。
34. **ボススプリントの進化ポイントを加算していた** — `resolveSprint()` のボス分岐は四半期
    レビューへ遷移して `return` するため、実際にはポイントが入らない。Q1 入手 p50 が
    53 → **43** へ下がり、「ツリーを丸ごと買える」は「約1.6倍」が正しい。
35. **選択的採用の予算条件が採用費控除前で判定されていた** — 文書は「採用後も残る」と
    書いているのに、控除前の額で見ていた。控除後で判定するよう直したところ、
    当初の閾値（`RECRUIT_COST` の2倍＝採用時点で75必要）は**実測の予算 p50=45 / 最大68 に対して
    到達不能**で、`skilledSelectiveHire` が `skilledNoHire` と40ラン全部同一になっていた。
    到達可能な水準（控除後に `RECRUIT_COST` 以上）へ下げ、実際に採用が発生する条件にした
    （40ラン中4ランで経過が分かれ、勝敗の集計は 14/40 のまま）。
36. **F-5 の方針間 CV を各方針の到達ランで独立に集計していた** — 到達率が違うと seed の
    選抜差が混ざる。RI-83 の比較を共通到達 seed のコホートへ変更した。
37. **敗北したスプリントの進化ポイントを加算していた** — `resolveSprint()` は結果を記録して
    `sprintsPlayed` を増やした後に敗北判定し、敗北なら加算前に `return` する。ボスと同じ理由で
    実際には得られない。除外すると1点も得ないランが標本から外れ、Q1 入手の p10 が 7→21、
    p50 が 43→**45** になる。
38. **F-4 のペーシング標本が方針構成に依存していた** — 難易度内の全方針を連結していたため、
    方針を足し引きするだけで帯外率が動く。代表3方針へ固定した（easy 通常の絶対下限割れは
    61.6% → **64.0%**）。
39. **復職直後のメンバーを欠員として数えていた** — 復職者は `onLeave=false` でも次の `setup`
    まで `assignment='bench'` のままで、その間の採用判定で戦力から漏れていた。休職していない
    メンバーを数えるよう直した（当時の1,200ランでは勝敗に変化なし）。
40. **即時採用イベントの安全判定に採用費が入っていなかった** — `grantRecruit` は解決時に
    `tryRecruit` が `RECRUIT_COST` を引くため、予算がちょうど25のとき outcome 上は差分0でも
    実際には予算0＝`budgetExhausted` になる。採用費を引いた後の予算で評価するよう直した。
41. **安全判定に落ちた採用肢が候補集合へ戻っていた** — 上で弾いた選択肢を、後続のフィルタが
    `takeRecruit` だけを理由に再び通していた。除外を一貫させた。
42. **同一 tick 内で盤面を取り直していなかった（影響大）** — 複数の介入を試すとき、`when` の
    判定にループ開始時点の盤面を使い続けていた。先行の介入がレーンを変えても後続がそれを
    見ないため、撃つべきときに見送り不要なときに撃っていた。各 `dispatch` の直前に取り直した
    ところ、**RI-77 のカードの結論が逆転した**（使う14 vs 使わない9。以前は 14 vs 11 で
    「寄与しない」としていた）。ほかに easy 全体 210→219勝、hard 25→19勝、
    `reviewFreeze` 288→268件、`techDebt` 30→40件。
43. **休息の強化対象が常に先頭カードだった** — ドラフトやショップで後から入ったカードが
    一度も強化候補にならなかった。レベルが最も低いカードを選ぶよう変えた（12/40）。
44. **ペーシングの規定帯をレポート側で複製していた** — `src/ui/sprintTempo.ts` の
    `SPRINT_WALL_SEC` / `BOSS_WALL_SEC` から読むようにした。秒換算だけが実装へ追随して
    帯判定が旧値のまま残る、という食い違いを防ぐ。
45. **固定標本の指標が代表方針の欠けを検査していなかった** — `PT_POLICIES` で絞り込むと、
    1方針だけの値を「代表N方針（固定）」として成立判定に出しうる。欠けている方針を明示して
    未計測にするようにした。
46. **spec-mapping のリンク先が旧見出しのままだった** — RI-73 / RI-74 は改名済みで、
    対応表からバックログへ辿れなくなっていた。
47. **ショップ購入の予算予約が採用方針を無視していた** — どの方針も `RECRUIT_COST`（=25）を
    残していたが、`skilledShopBuy` は `recruit: 'skip'` なので次の採用に備える必要がない。
    予算30で8のカードが出ても買えず（買っても22残り、四半期レビューの危機条件5には十分
    余裕がある）、「ショップへ投資する」条件が実際には多くの機会を見送る保守方針だった。
    採用しない方針の予約を10へ下げたところ 13→14 になったが、`skilledNoHire` 15 は
    上回らず**結論は変わらない**。
48. **RI-79（スプリント評価の分布）を F-6 の根拠にしていた** — F-6 は「敗北画面・リザルト・
    組織診断から次の一手が読み取れるか」の基準で、評価中央値とは別物である。評価が一致しても
    敗北時の説明品質は分からない。F-6 の判定は RI-81 へ移した。
49. **RI-84（判定イベントでの決着）を F-8 の根拠にしていた** — F-8 の観測条件は「敗北が
    確定する何スプリント前から実質的な選択肢が消えていたか」で、最終イベントが選択不能で
    あることだけでは満たせない（直前まで回避策があり最後だけ judgment で決着するランも
    同じ形になる）。言えるのは「決着の瞬間に操作の余地が無い」までで、これは RI-88 と
    同じ観測手段の不足である。
50. **目標修正の効果をラン全体の勝率で測っていた** — 共通コホートで揃うのは最初の修正までで、
    その後の修正は方針間で統制されていない。ラン全体の勝敗には後続選択がすべて乗るため
    初回選択へ帰属できない。主指標を「初回修正の次四半期まで生存」へ変えた
    （68.8〜81.3%。勝率は参考値へ）。
51. **CV をメタプロファイル横断で集計していた** — 共通コホートのキーに `meta` を含めれば
    対応は取れるが、CV は対応差ではなく周辺分布の分散なので、`fresh` と `full` を同じ配列へ
    入れるとメタ解放による平均・分散の差が介入効果へ混入する。メタ別に分けた。
52. **訂正履歴の数値を現在値であるかのように書いていた** — 「本節の数値はすべて修正後のもの」
    としていたが、各項目の値はその修正の直後に観測したものであり、後続の修正で母集団や
    方針構成が変われば動く（実際 29 と 34 は現在値とずれている）。但し書きを入れた。
53. **AI の因果を統制していない方針で測っていた（影響大）** — 「AI 配布を切ると出荷が
    334.5→291.4」を RI-76 の因果の根拠にしていたが、`noAi` は AI 配布のほか andon の有無・
    進化ブランチ・ドラフト選好・採用まで `skilledNoHire` と違い、差を AI へ帰属できない。
    AI 配布だけを外した `noAiCtl` を立てて同一 seed・同一スプリント番号で比べたところ、
    **向きが逆だった**。AI を切ると1スプリントの出荷はむしろ増え（12セル中6セルで上回り、
    下回るセルは無い）、それでも勝率は 15→10 に下がる。「AI で出荷が増える」という
    実務感覚と実装が食い違っていることになり、RI-76 の未充足として書き直した。
54. **ビート評価が遷移先スプリントの負荷を見ていなかった（影響大）** — `stateAware` は選択肢の
    `outcome` だけを採点し `leadsTo` を認識しなかった。`elite-offer` は高負荷側の `outcome` が
    空（=0点）、通常側が信頼-4（=負点）なので、組織がどれだけ消耗していても**常に高負荷側**
    （タスク量 `ELITE_TASK_MUL`=1.6倍）を選んでいた。体力（シニアHPと士気の低い方）と
    技術的負債から遷移先の負荷を評価するよう直したところ、高負荷スプリントの発生が
    代表方針で easy 13→9・normal 18→10・hard 16→9 件へ減り、勝率が多くの方針で±1〜2動いた
    （`skilledNoHire` 15→14、`skilledRestUpgrade` 13→15、`noInterventionCtl` 11→12、
    `onlyPair` 10→12）。**RI-77 のショップ・休息層の順位が入れ替わった**ため、その節は
    順位ではなく「差が±1で方向も揃わない」ことを結論とする書き方へ改めた。
55. **復職者に方針固有の編成が再適用されていなかった** — `applySetup` は `setup` フェーズでしか
    呼ばれず、`resolveBeat()` は `setup` を通らない。ベンチ配置と同じタイミングで
    `spec.ai` / `spec.formation` も掛け直すようにした。**ただしこの修正で動いた数値は無い。**
    指摘の根拠とされた「`noAiCtl` に AI 利用が残る」「`aiFullBet` が100%に届かない」は、
    調べた結果いずれも別の理由だった（下記56）。復職経路の穴自体は実在するので修正は残す。
56. **AI 統制条件の残差を「復職者の設定漏れ」と誤認しかけた** — 実際は2つとも別の原因である。
    `aiFullBet` の AI 利用率が最大97%なのは `AI_ADOPTION`（=0.85）の確率抽選のばらつきで、
    仕様どおり。`noAiCtl` に4%残るのは `assignTask` 介入が `defaultAssignee` 経由で
    個別タスクを AI へ回すためで、`spec.ai` が変えるのはロスターの `aiAssigned`（intake の
    採用率）だけ、`org.aiEnabled` は true のままだからである。**AI 配布ゼロ＝AI 利用ゼロでは
    ない**ことを RI-76 に明記した。
57. **ビート評価に信頼の残量が入っていなかった** — 予算・シニアHP・士気・負債は「適用後に
    敗北条件へ入る選択肢を除外する」判定があるのに、**信頼だけ守られていなかった**。
    信頼低下は残量に関係なく固定の重み（×0.2）で採点されるため、たとえば `urgent-demo` の
    「延期を交渉する」はレリック加点が勝って、management 信頼が11でも信頼-8を選び、
    次の四半期レビューで `minTrust <= 10` の `shutdown` を確定させていた。`BeatCtx` に
    `stakeholderTrust` を渡し、適用後10以下を除外、減少は残量で重み付け、危機域（15以下）へ
    踏み込む場合はさらに減点するようにした。`trustExhausted` が 32→27件へ減った。
58. **勝利数の突き合わせを場当たりの grep でやっていた（影響大）** — 表の形が少しでも違うと
    引っかからず、方針を1つ足しただけの回で「概要は更新したが詳細表が旧値のまま」という
    食い違いを3か所残してレビューで指摘された。`npm run playtest:check`
    （`scripts/check-findings.mjs`）で機械的に検査するようにした。**導入直後の再計測で
    即座に18件の取りこぼしを検出しており**、手作業では追い切れていなかったことがはっきりした。
59. **信頼の修正で多くの結論がまた動いた** — `onlyAndon` 17→19、`skilledRestUpgrade` 15→13、
    `skilledShopBuy` 13→14、`skilledSelectiveCards` 12→11、`skilledNoCards` 8→7、
    `noInterventionCtl` 12→11、`skilled` 9→10。結果として RI-77 のショップ・休息層は
    **無投資と完全に同数**（14対14対14、カード強化のみ13）になり、RI-83 の介入なしと初見の介入も
    同点（11対11）へ戻った。F-9 の層別一貫性は例外が1層→3層へ増え、今回は介入する方針
    （`hard` / `onlyFirefight`）にも例外が出て「介入しない条件だけがずれる」という整理も崩れた。
    **n=40（層別では n=3〜5）の指標は、ハーネスの一手を直すたびにこの幅で動く。**
60. **失敗した実行のあとに旧出力が残っていた** — `runMatrix` が例外を投げたり終端未到達の
    assertion で落ちたりすると `playtest-out/runs.json` に一度も触れないため、前回の成功結果が
    そのまま残る。続けて `playtest:report` / `playtest:check` を回すと**旧コードの結果を
    最新値として集計してしまう**。走り始める前に旧出力を消すようにした。
61. **絞り込み実行の出力を検査に使えてしまった** — `playtest:check` は入力の全ランを無条件に
    方針別集計していたので、`PT_DIFFS=easy` の出力（10ラン）を40ラン前提の文書と突き合わせて
    全件を不一致として報告しうる（`onlyAndon` なら実測9勝 対 文書19勝）。出力へコホート情報
    （難易度・seed・方針数・メタ・既定かどうか）を書き出し、既定でなければ**未計測として
    降りる**ようにした。レポートも先頭でコホートを表示する。
