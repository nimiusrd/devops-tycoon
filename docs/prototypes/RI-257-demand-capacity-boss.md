# RI-257: 需要予測と容量確保を判断するアクセス急増ボス

対象 [#653](https://github.com/nimiusrd/devops-tycoon/issues/653)、親 [#548](https://github.com/nimiusrd/devops-tycoon/issues/548)。結論は **最小の費用・停止比較を成立させ、本番採用は保留**。人間のプレイ評価は未実施。初手の設計・試作はこの文書と比較JSONで完了し、通常ランへの導入や面白さの証明とは扱わない。

プレイヤーの判断は「確定していない需要帯を読み、通常開発へ残す予算と、容量不足による停止リスクを交換する」。既存ボスの説明改善ではなく、容量という新しい資源の検証である。既存の他ボス試作と同じく、純TSモデル・対象ユニット・個別文書・再現JSONだけで構成する。

## 局面・情報・操作

| 局面 | 情報と進行 | 操作 |
| --- | --- | --- |
| 準備（tick 0） | 開始の予測帯4〜6、ピークの予測帯7〜14。実需要は未確定として表示 | 小容量または大容量へ1回投資するか、そのまま進む |
| 開始（tick 1） | 次の進行で最初の10分区間を観測する | 増強または進む |
| ピーク（tick 2〜4） | 経過した区間の実需要・処理量・未処理量・費用を見る | 増強または進む |
| 結果（tick 5） | 全4区間の確定済み観測、容量費、余剰費、等価停止秒、通常開発へ残る予算 | 操作終了 |

`advance` は時計の進行であり、無操作方針はこれだけを入力する。投資・増強自体は時計を進めない。増強は **容量+5の1種類を1回だけ**、開始以後に行え、次の進行で処理する区間から効く。機能制限・自動縮小・追加の介入は初手に含めない。開始前の増強、準備後の投資、重複操作、予算不足、結果後の操作は拒否し、拒否で費用・時計・入力履歴を変えない。

内部では既存のseed付きPRNGを使い、作成時に将来の4区間を一度だけ固定する。最初の乱数で低需要／高需要を等確率に選び、開始はどちらも整数4〜6、ピークは低需要で7〜9、高需要で12〜14から区間ごとに生成する。この区別は評価者向けで、プレイヤー向けに公開しない。**同じ予測帯でも異なる実需要になる**。帯はこの試作の生成範囲であり、統計的な信頼区間や本番の需要予測精度を表さない。

`viewDemandCapacityBoss` はseed・内部の需要列・未経過区間の実需要・内部未来を使った最終得点プレビューを返さない。公開するのは予測帯、操作の既知の価格、現在の容量と予算、確定済み観測だけ。比較方針もこの公開モデルだけを読む。ピーク最初の不足を見てから増強する方針は、すでに発生した停止を消せない。再表示や閲覧入力で未来を引き直さず、返した予測・観測を変更しても内部状態は変わらない。ローカルTS内部保存の解析によるカンニングを防ぐ仕組みは対象外。

## 容量費と停止の定義

全seed・全方針で初期予算100、基礎容量6、4区間を共通にする。容量の単位は架空の同時処理枠、費用の単位は架空の予算であり、外部負荷試験・クラウド料金の再現ではない。

| 確保 | 追加容量 | 初期費 | 1区間の追加リース費 |
| --- | ---: | ---: | ---: |
| 基礎運用（常に継続） | 6 | 0 | 3 |
| 小容量投資 | +3 | 8 | 3 |
| 大容量投資 | +8 | 22 | 8 |
| 稼働中の増強 | +5 | 12 | 10 |

容量費の計上先は試作専用の `prototype-capacity-operations`。初期費と区間リース費を分けて計上し、既存ツール維持費には一切加算しない。**通常開発へ残せる予算 = 100 − 支払済み容量費 − 未経過区間の契約済みリース費**。将来のリースも予約するため、増強可能かを現在の現金残だけで判定しない。通常開発そのものは実行せず、残せる予算を機会費用として示す。結果では未経過費用0となり、小容量の費用32／残予算68、大容量の費用66／残予算34になる。

各区間の処理量は `min(実需要, 容量)`、未処理量はその差。**等価停止秒 = ceil(600 × 未処理量 / 実需要)**。部分的な未処理を完全停止相当へ換算した指標であり、実際にサービス全体が停止した秒数ではない。区間ごとに切り上げて合算する。未処理の持ち越しやデータ消失はモデル化しない。

余剰費用 `unusedCapacityLease` は未使用の **追加容量** の区間リース費だけで、初期費や基礎運用費を含めない。基礎→予約投資→高価な稼働中増強の順で処理に使うものとし、未使用の増強枠には1枠あたり2、投資枠には1を計上する。これは容量費の内訳であり、容量費から再び引かない。停止と余剰費を別々に残す。

基礎容量でも開始区間は全量を処理し、ピークで容量を超えても毎区間6は処理し続ける。無操作・入力が遅いだけの即敗北やゲームオーバーは設けない。

## 同条件比較と感度

低需要のseed `RI-257-5`（実需要4,7,7,9）と `RI-257-9`（4,7,8,9）、高需要のseed `RI-257-1`（6,12,14,14）と `RI-257-2`（6,14,12,12）を比較する。4つは低／高各2例を残すために選んだ例示で、母集団の勝率推定ではない。全例で「無操作」「小容量」「大容量」「小容量＋観測した不足後に1回増強」の同じ4方針を適用する。

| seed | 方針 | 容量費 | 開発へ残る予算 | 等価停止秒 | 余剰リース費 |
| --- | --- | ---: | ---: | ---: | ---: |
| 5 / 9（低） | 無操作 | 12 | 88 | 372 / 436 | 0 / 0 |
| 5 / 9（低） | 小容量 | 32 | 68 | 0 / 0 | 7 / 6 |
| 5 / 9（低） | 大容量 | 66 | 34 | 0 / 0 | 27 / 26 |
| 5 / 9（低） | 小容量＋反応増強 | 32 | 68 | 0 / 0 | 7 / 6 |
| 1 / 2（高） | 無操作 | 12 | 88 | 986 / 943 | 0 / 0 |
| 1 / 2（高） | 小容量 | 32 | 68 | 580 / 515 | 3 / 3 |
| 1 / 2（高） | 大容量 | 66 | 34 | 0 / 0 | 10 / 12 |
| 1 / 2（高） | 小容量＋反応増強 | 64 | 36 | 150 / 215 | 3 / 11 |

大容量は停止を防ぐ一方、小容量より予算34を追加消費する。低需要では小容量も停止0で、大容量は余剰費用を増やす。高需要の反応増強は小容量より停止を減らすが費用32を追加消費し、最初のピークの損失を残す。

比較用に `開発へ残る予算 − 等価停止秒 × 評価単価` を併記する。停止損失を実予算へ課金するルールではなく、将来の本番得点・勝利種別でもない。基準単価0.1では低需要で小容量68 > 大容量34、高需要で大容量34 > 小容量10 / 16.5になる。反応増強は高需要で21 / 14.5となり、seed 2では小容量16.5にも劣る。増強した事実そのものを有利と扱わない。

単価を0.05に下げると高需要でも小容量39 / 42.25 > 大容量34に逆転する。0.15では大容量34 > 小容量−19 / −9.25である。この感度をJSONに残し、停止の重みや費用の設定次第で順位が変わることを確認する。大容量を常勝にする値を本番値とせず、停止と費用の生データを判断の正本にする。費用・需要帯そのものの感度や、広いseed集合の統計評価は未実施。

## 再現・保存・検証

`demand-capacity-comparison.json` はversion 1の信頼済み内部データで、各seed・方針の初期状態（非公開の需要列を含む）、全入力列、確定観測、費用・停止・単価感度を保存する。毎入力でJSON保存再開した状態、最初から入力を再生した状態、間に閲覧を挿入した状態の一致を対象テストで確認する。通常保存形式への互換、外部JSONの入力検証、通常ランのリプレイは対象外。以下を専用worktreeのルートで実行する。

```sh
devcontainer exec --workspace-folder . node --version
devcontainer exec --workspace-folder . npm test -- src/prototypes/demandCapacityBoss.test.ts --maxWorkers=1
devcontainer exec --workspace-folder . npx tsc -b
devcontainer exec --workspace-folder . npm run lint
devcontainer exec --workspace-folder . npm run format:check
```

比較JSONの再生成:

```sh
devcontainer exec --workspace-folder . node --input-type=module <<'JS'
import { createServer } from 'vite';
import { writeFileSync } from 'node:fs';
const server = await createServer({ configFile: false, server: { middlewareMode: true }, optimizeDeps: { noDiscovery: true }, appType: 'custom' });
try {
  const { compareDemandCapacityBoss } = await server.ssrLoadModule('/src/prototypes/demandCapacityBoss.ts');
  const seeds = ['RI-257-5', 'RI-257-9', 'RI-257-1', 'RI-257-2'];
  writeFileSync('docs/prototypes/demand-capacity-comparison.json', JSON.stringify({ version: 1, seeds, results: compareDemandCapacityBoss(seeds) }, null, 2) + '\n');
} finally { await server.close(); }
JS
devcontainer exec --workspace-folder . npx prettier --write docs/prototypes/demand-capacity-comparison.json
```

UI、ユーザー向け既存文言、HTML/Pixi描画、visual tokenを変更しないため、HTML/WebGL E2E・視覚回帰・galleryは対象外。

## 本番境界と保留を解く条件

通常RunEngine、既存ボスの抽選・突破条件、ツール維持費、通常保存・ruleset・SPEC・固定トラック・勝利種別・WebGL準備中の停止契約は変更しない。試作のPRマージは本番採用を意味しない。既存のアクセス量・需要調査の試作とも統合せず、外部サービスを呼ばない。

現時点で確認できたのは、固定方針による費用と停止の交換、および決定論だけ。共通の広い予測帯と開始区間の観測は低／高を識別する手掛かりを持たず、**人間の先読みや予測を読む楽しさをこの計算で証明していない**。

次に人間のプレイ評価へ進む条件は、通常ランから隔離した操作用画面で予測帯・確定観測・操作費・残予算・停止を区別できること、追加容量を選ばずに進めること、上記の入力再生を維持すること。予測が広い／狭い条件も追加して、最低5人が低／高を伏せた複数seedを遊び、選択理由、予測の読み違い、費用と停止の納得、次に方針を変えたいかを記録する。その評価と費用／需要帯の感度で判断が変わる根拠が得られてから採否を再判定する。人間評価の実施日・結果はまだ存在しない。

本番採用する場合は別Issueで容量の予算勘定、通常開発への機会費用、停止の意味、ボスIDと抽選率、rulesetの版と古い保存の既定値、HTML要約／Pixi描画と操作の受入条件を確定する。既存維持費へ混ぜる、現在の定数を無検証で本番化する、試作の高需要seedをプレイヤーへ事前表示する変更は含めない。
