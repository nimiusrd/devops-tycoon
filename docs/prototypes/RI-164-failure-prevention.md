# RI-164: 同じ失敗への免疫

対象 #560 / 親 #548。結論: **原因に合う限定的な再発防止の仮説を採用、本番統合は保留**。人間のプレイ評価は未実施。

## 原因・投資・代償

通常ランから隔離した純TS試作。原因はspec-omission（仕様漏れ）とmigration-failure（移行失敗）。能動対策は仕様チェックリスト1種のみ。現在の点火source=review/spreadを置換せず、架空の仕事に開始前から原因を持たせ、実装完了時の失敗判定でその値を事故台帳へ記録する。結果表示時に原因を推測しない。

seed `RI-164`、12工数、3仕事、各実装2工数・修復完了後の価値8。最初は全方針共通の仕様漏れ仕事（2工数で失敗→修復2工数）。残り2仕事は同種または異種で、開始前に判明している。全仕事は固定の失敗を持つため、これは事故確率・通常ランの難易度のモデルではない。

未対策の失敗は損失4・修復2工数。原因が確認された後、次の仕事開始前に2工数と投資費2を払ってチェックリストを採用できる。上限1で再投資は無消費で拒否。同種の損失1・修復1に軽減するが、異種は4・2のまま。同種でも残存損失があり完全な免疫ではない。進行中/修復中の投資を拒否する。

損失は失敗時に計上し、成果は修復完了時に計上する。期末未完了にも既に発生した損失は残る。故意の仕様漏れ事故操作は成果ゼロ・損失4・2工数で、対策レベルを増やさない。事故ログにinducedとjobId=nullを記録し、通常の仕事事故と区別する。既に対策済みでも故意の事故費用は軽減しない。

共通の最初の事故後の判断を比較。同種が続けば限定軽減の価値があり、異種なら時間を次の機能へ回す方が有利。事故を増やしても上限1の効果は伸びず、工数と損失だけが増える。これは限定盤面の比較であり全戦略の最適性を主張しない。事故を故意に作って初回対策の資格を早く得る場合も対象テストで比較する。

`failure-prevention-comparison.json` は初期状態・入力列・仕事の原因・発生済み損失・残工数を保持。毎入力のJSON保存再開と再生、実際の原因と対策の対応、異種への非適用、対策上限、資源不足/途中操作の拒否を検証する。

## 採否・次の評価・本番境界

仮説採用、本番統合保留。次は原因の予告精度、発生頻度、対策の軽減率と維持費、対策資格の早期獲得を狙う事故、複数原因の仕事、失敗しなかった仕事での機会費用、人間の判断負荷を比較する。本番では分類を失敗判定時に生成・保存し、過去の点火sourceから細分類を捏造しない。既存のランに事故を強制するルールは追加しない。
