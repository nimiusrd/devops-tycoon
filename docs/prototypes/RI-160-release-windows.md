# RI-160: リリース便

対象 #556 / 親 #548。結論: **便を待つ判断がリスクで変わる仮説を採用、本番統合は保留**。人間のプレイ評価は未実施。

## 固定盤面と判断

通常ランから隔離した純TS試作。seed `RI-160` は盤面識別子で、乱数は使わない。tick 1にレビュー完了した1仕事、比較開始tick 1、確認枠1、終了tick 6、便はtick 2と5。レビュー完了は出荷へ計上せず、公開待ちから便の終端で公開済みに移す。確認作業を先に処理するので便当日の確認完了も有効。公開時だけ価値と期待損失を確定し、公開後の再計上や確認を拒否する。

各tickの入力は確認対象（任意）と今回保留するID一覧。未知ID、重複保留、確認完了済み・公開済み対象、期末以降は無消費で拒否する。入力はコピーして記録し元状態を変更しない。保留はそのtickだけ有効。最終便を逃した仕事は公開待ちのまま繰越一覧に残し、今期出荷・価値に加えない。次期の進行は未実装。

両リスク盤面とも期限tick 2までの価値10、遅延価値6、追加確認2工数。低リスクの期待損失2、高リスク8を判断前に公開する。確認は2工数完了時だけ損失を0にする。実事故の乱数判定、予算、体力、他の作業機会はこの試作では扱わない。価値−期待損失を比較指標とし、損失を実際に起きた事故と解釈しない。

`release-windows-comparison.json` に初期状態、成功入力、公開台帳相当の全タスクと結果を保存。テストで再生成結果を照合し、各tickのJSON保存再開と入力再生を確認する。version 1の信頼済み試作JSONが対象で、外部JSONの検証付き読み込みは対象外。

## 採否と統合境界

限定した比較仮説を採用、本番統合保留。次は確認枠の競合、締切・事故損失・便時刻、確認失敗、初便当日のレビュー完了順序、人間の操作負荷を評価する。大型リリース段階戦 #648 は段階の攻略、本件は便に載せる時期を扱い、コード依存はない。

通常TaskのDone、SPEC、保存、ruleset、勝敗、固定トラック、WebGL停止契約は変更しない。本番採用時はレビュー完了と公開の工程分離、コンボ/評価の計上、期末繰越と保存移行、連続入力リプレイ、ruleset更新を別Issueで設計する。試作の状態を本番保存に混ぜない。
