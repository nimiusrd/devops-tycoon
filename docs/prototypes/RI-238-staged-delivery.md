# RI-238: 一括納品と核の先行納品を比べる

対象 #634 / 親 #548。初期試作は PR #849 でマージ済み。結論: **限定比較の仮説採用、本番統合保留**。確認費用・核の必要作業の感度比較を追加した。人間のプレイ評価は未実施で、試作のマージを本番採用と扱わない。

## 固定案件

通常ランから隔離した純TS試作。seed `RI-238` は盤面識別子で乱数は使わない。案件は核と追加の2機能だけである。核の必要作業は4、価値は12。追加の必要作業は4、価値は8。余力は4で、1期間に1機能が完成する。納品の確認費用は1回3。RI-228 の完成判定を使い、余った作業はもう一方へ移さない。契約管理の画面は作らない。敗北状態にはしない。

方式は着手前に一度だけ選ぶ。一括は核と追加が両方完成したときだけ、価値20から確認3を引いて17を一度払う。段階は完成した部品ごとに払う。核は12から3を引いた9、追加は8から3を引いた5で、核の9は追加の納品時に足さない。未完成の核へ納品しても報酬は0のままである。

期間は二つ。余裕は2期間で、両方を完成できる。短い期限は1期間で、核だけが完成し、追加の残り4は次期へ残る。

閲覧は必要作業、価値、確認費用、核を最初に納品できる時点（1期間目の完了後）、現在の残りと納品済みを示す。閲覧では作業も報酬も動かない。

## 同条件比較

成果は、納品価値から確認費用を引いた額である。

| 期限 | 一括の成果 | 一括の確認 | 一括の持越し | 段階の成果 | 段階の確認 | 段階の持越し |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2期間 | 17 | 1 | 0 | 14 | 2 | 0 |
| 1期間 | 0 | 0 | 4 | 9 | 1 | 4 |

2期間では両方完成する。確認が1回の一括17が、確認2回の段階14を上回る。1期間では一括は核が完成しても追加を待てず成果0、追加4を持ち越す。段階は核の9を確保し、追加4は同じように持ち越す。核の報酬は一度だけで、段階の最終額は14であり、核を二度数えた26にはならない。

固定2期限の仮説比較であり、本番の契約交渉の証明ではない。

## 係数感度（2026-11-17）

`staged-delivery-sensitivity.json` に26条件・52実行を記録した。seedは引き続き `RI-238` で乱数はない。各条件で一括/段階は同一の初期状態を共有する。確認費用 `c` を `[0, 3, 8, 10, 12, 13, 20, 21]`、核の必要作業 `n` を `[3, 4, 5, 8, 9]` に一要因ずつ変え、もう一方は初期値（3、4）に固定する。両要因を同時に動かす探索ではない。余力4、追加作業4、核価値12、追加価値8、期限1/2期間は固定する。

固定戦略は、着手前に方式を選び、核→追加の順で期限内に作業する。一括は両方完成後に1回、段階は各部品の完成直後に1回ずつ納品する。確認は作業期間を消費せず、期限の最後の作業で完成した部品もその直後に納品できる。差引が0以下でも納品する戦略なので、費用に応じて納品を取りやめる適応戦略や最適戦略の比較ではない。

成果は納品済みの総価値 `grossValue` から `reviewSpend` を引いた `value`。優劣はこの差引成果のみで判定し、同点でも確認回数や納品済み状態が同じとは限らない。`additionalReviewSpend` は段階から一括を引いた追加費用。`carry` は核と追加の未完成作業の合計であり、`coreCarry` / `extraCarry` で内訳も残す。完成したが未納品の部品は未完成作業に数えず、完成/納品済みフラグで区別する。翌期の作業・確認・報酬は実行しない。

### 確認費用と同点・赤字境界

| 確認費用 c | 2期間: 一括 / 段階 | 1期間: 一括 / 段階 |
| ---: | ---: | ---: |
| 0 | 20 / 20 | 0 / 12 |
| 3 | 17 / 14 | 0 / 9 |
| 8 | 12 / 4 | 0 / 4 |
| 10 | 10 / 0 | 0 / 2 |
| 12 | 8 / −4 | 0 / 0 |
| 13 | 7 / −6 | 0 / −1 |
| 20 | 0 / −20 | 0 / −8 |
| 21 | −1 / −22 | 0 / −9 |

2期間では両方完成し、一括 `20−c`、段階 `20−2c`、段階−一括は `−c`。費用0で同点、正の費用では一括が上回る。確認は1回/2回、費用は `c` / `2c`、追加確認費用は `c`。持越しは両方式0で、費用だけでは変わらない。段階の差引成果は `c=10`、一括は `c=20` で0となり、それを超えると赤字になる。追加部品だけの差引は `8−c` なので `c=8` で0、それを超えると追加納品が累積成果を減らす。固定戦略はその場合も納品を実行する。

1期間では一括は未納品0、段階は核だけの `12−c`。`c<12` で段階が上回り、`c=12` で同点、`c>12` で未納品の一括0が上回る。確認は0回/1回、追加確認費用は `c`、持越しは両方式とも核0・追加4。費用12で同点でも段階は核を納品して確認12を払い、一括は完成した核も未納品のままである。この固定戦略内の反転は、人間が赤字納品を選ぶ証拠ではない。

### 核の必要作業と成果成立境界

| 核作業 n | 核の最短完成期間 | 2期間: 一括 / 段階 | 2期間: 核 / 追加の持越し | 1期間: 一括 / 段階 | 1期間: 核 / 追加の持越し |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 3 | 1 | 17 / 14 | 0 / 0 | 0 / 9 | 0 / 4 |
| 4 | 1 | 17 / 14 | 0 / 0 | 0 / 9 | 0 / 4 |
| 5 | 2 | 0 / 9 | 0 / 4 | 0 / 0 | 1 / 4 |
| 8 | 2 | 0 / 9 | 0 / 4 | 0 / 0 | 4 / 4 |
| 9 | 3 | 0 / 0 | 1 / 4 | 0 / 0 | 5 / 4 |

余剰を次の機能へ渡さないため、核に必要な期間は `ceil(n/4)`、両方にはさらに1期間必要となる。核が完成する条件は `ceil(n/4) <= 期限`、一括が成立する条件は `ceil(n/4)+1 <= 期限`。未完成の核から総価値も差引成果も得ない。

2期間では `n<=4` で一括17が段階14を上回り、`5<=n<=8` で段階9が一括0を上回り、`n>=9` では両方式0の同点となる。確認費用3では、核が完成すれば段階の差引成果は正となる。確認は順に1回/2回、0回/1回、0回/0回で、追加確認費用は3、3、0。1期間では `n<=4` で段階9が一括0を上回り、`n>=5` で両方式0。確認は0回/1回から0回/0回へ変わる。どの条件でも両方式の持越し差は0であり、段階方式そのものが残作業を減らすわけではない。核が未完成の境界でもその残りを持越しから落とさない。

## 採否と次の評価条件

この範囲では、期限内に完成する部品の違いと確認費用によって固定方式の優劣が変わる仮説を維持する。係数感度の計算比較は完了した。次は、部品ごとの納品を見送れる最小のプレイ文脈で、プレイヤーが成果・追加費用・残作業を説明し、期限や費用を変えたときに判断を変えられるかを人間評価する。評価の前提として任意納品の方針と未納品の約束の扱いを設計し、判断理由と迷った箇所を記録する。固定戦略の数値を面白さ・操作の分かりやすさ・継続意欲の証明には使わない。

本番統合はこの人間評価と、目標修正との責務分割、保存/ruleset/リプレイの設計が決まるまで保留する。#634 は判断材料と未評価範囲を追跡するため open を維持し、本PRは `Refs #634` とする。

## 本番境界と検証

通常ランの納品、目標修正、自動勝利、SPEC、保存、ruleset、固定トラック、WebGL停止契約へ接続しない。ランの分岐ルートは足さない。閲覧順で結果は変わらない。本番採用時は、核と追加の完成、納品済み、確認回数、持越しを保存する別Issueに分割する。version 1の信頼済み内部JSONに比較の初期状態、入力列、成果を含める。外部入力検証と通常保存互換は対象外。

`staged-delivery-comparison.json` の初期比較は維持する。感度JSONには比較係数、方式共通の初期状態、各方式の全入力列、総価値・差引成果・確認回数/費用・持越し内訳・完成/納品フラグと優劣を記録した。対象ユニットで初期比較との整合、独立した式による境界、毎入力のJSON保存再開と入力再生の全状態一致、閲覧不変、期限後の作業拒否と一度だけの納品を確認する。型チェック、lint、format:checkも実行する。UI/Pixiの変更はなく、E2Eとgalleryは対象外。
