### RI-104 バランスパラメータSSoTの導入

調整対象の値が工程モデル、タスク生成、メンバー、介入、ラン進行、KPI、粗粒度モデル、ペーシング、メタ進行へ分散し、ゲーム・確率モデル文書・グラフ・プレイテスト補助スクリプトが同じ値を共有できていない。[balance-ssot-plan.md](./balance-ssot-plan.md)を設計正本とし、型付きの分割レジストリと既存`src/data/`定義から、ゲーム実行値、生成文書、ルールセット識別子を導出する。

完了条件:

- 調整対象の基本値に安定ID、値、単位、許容範囲、説明、タグがあり、派生値を別の基本値として重複保持しない。
- ゲームと生成パラメータ表・代表曲線が同じ定義を参照し、`balance:check`が定義違反と生成差分を検出する。
- 値の移動だけを行うPRは乱数消費順と同一seed・同一入力の結果を変えず、値を調整するPRと分離する。
- ルールセットの版と指紋をセーブ、リプレイ、デイリー、診断情報へ記録し、旧データと不一致時の扱いをテストで固定する。
- 外部設定サービス、実行時上書き、管理画面、数式DSLは導入しない。

実装順は RI-106 → RI-107 → RI-108〜114・RI-120・RI-122・RI-124 → RI-115 → RI-123 → RI-116 → RI-117 → RI-118 → RI-121 を基本とする。RI-105で対象境界、互換方針、生成物管理、多数seed実行方式は確定済みであり、後続RIは[balance-ssot-plan.md](./balance-ssot-plan.md)を実装契約とする。RI-119はRI-116完了後に着手する調整支援であり、親エピックの完了を妨げない独立課題とする。RI-73／RI-76完了後の現行値と再計測結果を移行前ベースラインとし、SSoTへの移動PRでは値を変更しない。AI依存モデルの意味変更は値の移動ではないため、本エピックには含めず別課題として扱う。

### RI-116 バランスルールセットの版と指紋

手動更新する`BALANCE_RULESET_VERSION`と、バランスレジストリおよびRI-115のコンテンツカタログから決定論的指紋を追加する。レジストリは安定IDとゲームが参照する実行値だけへ射影し、表示・検証専用メタデータを入力から除外する。意味のないオブジェクトキー順だけを正規化し、抽選・評価に使う配列順は指紋へ保持する。指紋計算はブラウザとNodeの双方で同じ結果になる方式にする。

受入条件:

- `BALANCE_RULESET_VERSION`を`1`から始める単調増加整数として追加し、結果へ影響する値、式、分岐、丸め、乱数消費順、コンテンツ、配列順、指紋方式の変更で直前の版から1増やす規則を文書とテストで固定する。
- 意味を持たないオブジェクトキー順の違いでは指紋が変わらず、ゲーム結果へ影響する値・ID・重み・配列順の変更では指紋が変わる。
- `label`、`description`、`unit`、`allowedRange`、`tags`、`derived`など表示・検証専用メタデータだけの変更では指紋が変わらない。
- 検証メタデータ、表示専用値、テスト条件、生成整形だけの変更では版を増やさず、版の更新規則と指紋対象を生成文書へ表示する。
- seedや入力列を指紋へ混ぜず、ルールセット識別と実行識別を分離する。

### RI-117 セーブへのルールセット記録と互換判定

受入条件:

- 新規セーブがルールセット情報を往復し、一致時だけ再開できる。
- 不一致またはルールセット情報のない旧セーブは自動削除せず、要約、再開不可の理由、明示的な破棄導線をタイトルへ表示する。
- 構造破損・未対応スキーマとルールセット不一致を区別し、途中セーブの破棄でメタ進行、完了済みデイリー、リプレイを無効化しない。

### RI-118 リプレイへのルールセット記録と表示

受入条件:

- リプレイがseedとルールセットを組で提示し、旧リプレイも方針どおりに読める。
- 新規リプレイは参照するカード・レリックなどの表示用定義を保存し、リプレイUIが現行`getCard()`／`getRelic()`より記録時スナップショットを優先する。
- ルールセット情報のない旧リプレイをread-onlyキーフレームとして保持し、「ルールセット不明」と表示する。
- スナップショットのない旧リプレイは互換ID定義へ解決し、削除・改名済みで解決できないIDもプレースホルダー表示してキーフレーム状態から落とさない。
- ルールセット変更前後のリプレイを同一結果として誤表示しない。

### RI-119 バランス差分・多数seedレポート

RI-116完了後、同一seedペアでパラメータ変更前後を比較し、勝率、分位点、Delivery、Incident、Reworkと主要パラメータの感度を出力する。通常PR CIからは外し、手動実行と週次`main`実行にする。開発用閲覧画面は必要性が確認できるまで対象外とする。

受入条件:

- ルールセット版・指紋とコホート条件を記録した再現可能なレポートを生成する。
- 設定値の差分と結果分布の差分を分け、既存`npm run playtest`の判定を重複実装しない。
- サンプル数、seed集合、比較対象、欠損ランの扱いをテストまたは固定fixtureで検証する。
- `workflow_dispatch`と毎週月曜00:00 UTCの`main`定期実行を追加し、結果をGit管理せず30日保持のGitHub Actions artifactとして保存する。

### RI-120 タスク分布・スプリント評価パラメータの移行

`src/sim/sprint.ts`のタスク種別重み、高価値率、完了時の状態変化、評価ペナルティ、評価境界、称号・診断閾値を`balance/sprint.ts`へ移す。`src/sim/run/engine.ts`の粗粒度補正に複製された定型タスク比も同じ重みの安定IDへ置き換え、配列順、乱数消費順、フォールバックを維持する。

受入条件:

- タスク分布、評価、称号の調整値を安定IDから参照し、合計1の分布を検証する。
- 詳細側のタスク抽選と粗粒度側の`scenarioRoutine`補正が同じ定型タスク比を参照する。
- タスク列、粗粒度チーム出荷、評価・称号境界、代表seed結果が移行前後で一致する。
- 詳細工程式の移行や値調整を同じPRへ含めない。

### RI-121 デイリー・診断情報へのルールセット伝播

デイリーランのseed・記録と、不具合再現に使う公開診断情報へルールセット版・指紋を伝播する。デイリーはUTC日付とルールセットの組を比較・報酬単位にし、旧日付記録は不明ルールとして保持する。

受入条件:

- デイリー識別子がUTC日付、版、指紋を含み、同日・同ルールセットの決定論を維持する。
- スコアと報酬受領状態をルールセット単位で分離し、同日でも異なるルールセットなら各ルールセットで報酬を取得できる。
- 診断情報がseed、版、指紋を組で提示し、再現条件をコピーできる。
- 旧日付キーのデイリー記録を「ルールセット不明」として保持し、既存メタ進行を失わない。

### RI-122 カード実行ルールのパラメータ移行

`src/sim/cards.ts`の手札枚数、ドラフト候補数、強化倍率、集中力下限、優先ドラフト重み、効果`clamp`境界など、カード定義そのものではない共通実行ルールを`balance/cards.ts`へ移す。`src/sim/run/engine.ts`の通常ドラフト、引き直し、ショップに直書きされた候補数と、引き直しの最大再試行回数も同じ領域の安定IDへ置き換える。

受入条件:

- カードID、価格、効果値は既存`src/data/cards.ts`を正本のまま維持し、実行ルールだけを安定ID化する。
- `drawDraft`の既定値と通常ドラフト・引き直し・ショップの全呼び出しが同じ候補数を参照する。
- 引き直しの最大再試行回数を安定IDから参照し、元候補と同じ集合が連続する固定fixtureで派生seedと最終候補を回帰する。
- 候補列と乱数消費順を変えず、ドロー、強化、発動コスト、効果合成、優先ドラフトの境界テストと代表seed結果が一致する。

### RI-123 代表確率曲線のSSoT生成

RI-108で移行した値と純粋な計算関数から代表確率曲線SVGを決定論的に生成し、`probability-model.md`の現行値スナップショットを生成物へ置き換える。AI依存モデルの候補曲線は現行値と明確に分離する。

受入条件:

- `balance:docs`がMarkdown表と代表曲線を同じレジストリから生成する。
- SVGをGit管理し、生成が冪等で、定義変更時だけ`balance:check`に差分が出る。
- 曲線生成のためにゲーム式を複製せず、モデル変更を同じPRへ含めない。

### RI-124 メタ進行・デイリー条件パラメータの移行

`src/state/meta.ts`のデイリー難易度・試練、優先カード上限、ラン報酬係数など、ゲーム結果や進行へ影響する値を`balance/meta.ts`へ移す。永続化スキーマの履歴値と表示専用値は対象外として理由を残す。

受入条件:

- メタ進行・デイリー条件の調整値を安定IDから参照し、RI-116の指紋入力へ含める。
- デイリー条件、アンロック、ラン報酬、優先カード上限の境界と代表seed結果が移行前後で一致する。
- 旧メタ進行データの互換処理と値調整を同じPRへ含めず、既存exportが必要な場合は互換別名を維持する。

### 第23章の残拡張（旧RI-34）

第23章の残拡張は RI-34 から次の個別IDへ切り出した。開始レシピ共有（RI-127）、診断・KPI時系列（RI-128）、四半期レビューのOKRテンプレート（RI-129）は完了。RI-130〜131 は設計選択の確定後に着手する。外部API・共有バックエンド、社内LT／経営プレゼンモードは対象外のままとする。途中セーブやリプレイのファイル共有は開始レシピ（RI-127）とは別課題であり、本切り出しには含めない。

### RI-130 ステークホルダー別交渉

現行の目標修正7種は `trustDelta` だけでなく、予算、次期目標、組織状態、次期予算上限、次四半期の物理効果を変え、`availableAdjustments()` は予算不足や修正後の継続不能も除外する。既存の信頼差だけでは、スコープ削減・期限延長・組織再編が既に経営・顧客・チームで結果が違う。相手ごとの対話・条件提示・分岐を足すか、既存7択へステークホルダー固有の操作を足すかを決める。

受入条件（方針確定後）:

- 既存の `trustDelta` 差だけでは満たせない、ステークホルダー固有の操作または提示条件を追加する。
- 既存7種の全効果（信頼、予算、次期目標、組織状態、次期予算上限、次四半期物理）と、`availableAdjustments()` の提示条件を維持する。
- 信頼下限による除外と、既存オートプレイseedの到達可能性を壊さない。
- 複数四半期約束（RI-131）や完了済みの OKR テンプレート表示（RI-129）を同じPRへ含めない。

### RI-131 複数四半期ロードマップ

目標修正の物理キャリーは次の1四半期だけ（`goalCarryoverQuarter` / `nextQuarterEffects`）である。表示専用の見通しにするか、Q+2 / Q+3 の拘束力ある約束にするかで、勝敗と信頼の契約が変わる。

受入条件（方針確定後）:

- プレイヤーが今四半期より先の目標または制約を、四半期レビューから確認できる。
- 拘束力ある約束にする場合は、1期だけのキャリー契約を明示的に拡張し、代表seedと継続不能判定を回帰する。新しい複数期状態は途中セーブへ記録し、旧セーブ補完と再開往復を同じPRで固定する。
- 表示専用にする場合は sim 契約と保存スキーマを変えず、UIとテストだけに閉じる。
- 完了済みの OKR テンプレート（RI-129）と交渉UI（RI-130）を同じPRへ含めない。

## 2. 確定した判断

- Zustandは要件ではない。`RunEngine`を状態の正本とし、決定論、保存、リプレイ、UI同期を満たせばよい。
- 巨大組織は表示用の合成チームではなく、独立状態を持つ複数チームとして扱う。
- カード、レリック、進化ノードのSPEC内の具体例は方向性であり、実装データとの差を許容する。
- カードはラン外のコレクション画面で一覧・解放状況を確認できるようにする。
- 診断・KPI時系列（RI-128）は四半期境界でセーブへ明示永続化し、業界ランキングの自社趨勢だけ実履歴化する。他社趨勢は演出値のままとする。

## 4. バックログ運用

- IDは`RI-NN`の連番とし、欠番を再利用しない。
- ミューテーション改善はエピック`RI-{N}`（再ベースラインごと）と実装単位`RI-{N}-{GROUP}{SEQ}`（1PR = 1 GitHub Issue）に分ける。採番・進捗の正本はGitHub Issueとし、本ファイルへ番号予約や状態台帳を置かない。方針は[mutation-remediation.md](./mutation-remediation.md)を参照する。
- 状態は`未着手`、`進行中`、`保留（要判断）`、`完了`を使う。
- 1項目は原則1PRで完了できる大きさに分割する。エピックは受入条件と分割順を記載する。
- 完了時は個別節を削除し、上の完了要約と[spec-mapping.md](./spec-mapping.md)を更新する。
