# RI-161: 有限のCI枠

対象 #557 / 親 #548。結論: **CI容量と流入を選ぶ仮説を採用、本番統合は保留**。人間のプレイ評価は未実施。

## 工程・投入・再実行

通常ランから隔離した固定仕事3件a/b/c、seed `RI-161`、終了tick 6、予算20。seedは識別子で乱数を使わない。各仕事の価値8、CIは2tick。bだけ初回CI失敗、その後1工数の修正を経て再投入する。失敗条件は固定盤面の公開情報で、実際のCIサービスへ接続しない。

各tickは修正1枠、レビュー1枠、投入、FIFO開始、CI処理、終端確定の順。レビュー済みの仕事はCI待ちへ移り、単調増加の投入番号で開始順を決める。処理中は容量1または2以内、待ち行列に上限は設けない。初回失敗はDoneにならず、再投入時に新しい番号を受けて末尾へ並ぶ。再実行は同じ2工数で成功。成功だけDoneと完了tickを持ち、価値はDoneの仕事を一度ずつ集計する。

allは全レビュー済み仕事を投入する。pacedは待ち＋処理中が容量未満のときだけ投入し、残りは上流に保持する。FIFOは投入済み仕事の契約で、上流仕事の順序は配列順。このためpacedでは修正済みbが未投入cより先に入る場合があり、同じ仕事群でも出荷内訳が異なる。レビューと修正は独立した各1枠。レビュー混雑盤面では各仕事3工数、CI混雑盤面ではレビュー完了状態から開始する。

契約容量1枠あたり毎tick予算1を払い、空き枠も費用を消費する。期末や予算不足で無消費停止。未完了仕事はstageと残工数を保持し、今期価値に含めない。次期への進行は未実装。待ち時間は各tickのCI開始後の待ち件数を積算し、上流保持は別の指標にする。

CI混雑なら追加容量で再実行も期内に終わる。レビュー混雑では容量投資は完了を増やさず費用だけ増やす。流入抑制は待ち場所を上流へ移すだけで、総待ちを減らした成功とは扱わない。修正済み仕事の出荷優先が変わる可能性も示す。全仕事同価値であるため、優先順位の良し悪しは未評価。

`ci-capacity-comparison.json` に全初期状態・入力列・未完了・試行数・成果と費用を保存し、テストで再生成結果を照合する。各tickのJSON保存再開と入力再生が一致する。version 1の信頼済み試作JSONを対象とし、外部JSONの検証付きロードは対象外。
