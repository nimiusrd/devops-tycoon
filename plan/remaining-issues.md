### RI-67 オンボーディングとシニア燃え尽きの断絶

Easy でも無介入・素直プレイだと第1四半期スプリント2でシニア燃え尽き（`seniorBurnout`）敗北する。敗北条件は抽象値 `org.seniorHp <= 1`（`src/sim/outcome.ts:57`）で、メンバー個別 stamina ではない。`org.seniorHp` は毎 tick `REVIEW_HP_REGEN`=0.7（炎上中は半減）で回復し、主な減少要因はレビュー1件ごとの一律消費 `REVIEW_HP_COST`=1.6（`reviewOne`、`src/sim/sprint.ts:252`）と、猶予切れ炎上の自動鎮火 `INCIDENT_HP_COST`=12（`advanceBurning`、`src/sim/sprint.ts:340`）。スプリントは `isDrained` まで進むが、手戻り・鎮火タスクは Review へ再投入されるためレビュー回数はタスク数固定ではなく手戻り・炎上率で増減する。第1スプリント実測（同一 seed）では、自動鎮火回数と HP 終値が 無介入 3回/42、緊急対応のみ 1回/62、緊急対応＋andon 0回/74、編成＋介入 1回/55。最も確度の高い（単一条件変更の）要因は**炎上を自動鎮火 −12 の前に緊急対応 −2 で鎮火すること**。andon は流入を一時停止して既存キューを捌く猶予を作る補助。AIスロットルはレビュー1件あたりの点火率と手戻り率を下げ、品質・PR分割は手戻り率のみ下げて再レビューを減らす（点火率 `incidentProbability` は testCoverage・aiAssisted・カード効果のみ参照し品質値・`task.split` は参照しない）。編成（review 増員）は review 容量だけでなく Coding 担当減で `foldFormationEffects` の複数因子が連動するため単一機序に帰属できないが、A（編成のみ）は無介入と同じく即死しており燃え尽き回避の主手段ではない。チュートリアル（`src/ui/tutorial.ts`）は介入バー・レビュー渋滞・コンボのみで、燃え尽き回避の主手段を教えない。実測と経緯は[playtest-findings.md](./playtest-findings.md)参照。

受入条件:

- 初見プレイヤーがシニア燃え尽きを回避する最大手段（炎上を自動鎮火前に緊急対応で鎮火）へ導かれる。andon は既存キューを捌く猶予、AIスロットルは点火率と手戻り率を下げる、品質・PR分割は手戻り率のみ下げて再レビューを減らす、編成はスループット策であり燃え尽き回避の主手段ではない、と位置づけを区別する。
- チュートリアルまたは盤面・HUD の警告で、抽象値としてのシニア体力と燃え尽きリスクを事前に伝える。
- Easy の序盤（第1四半期）で、標準的な操作理解のプレイが2スプリントで即敗北しない。
- 難易度別の `org.seniorHp` 収支・レビュー負荷の妥当性を自動操作モデルまたはユニットテストで検証する。

### RI-73 難易度カーブと、常に正解／常に不正解な手がある構造

F-7 は**初見相当の方針（`naive`）の勝率**で判定する。全方針の平均は使わない（`adj*` の統制群や `onlyXxx` のような実験用方針を足し引きするだけで、ゲームも初見プレイも変わっていないのに平均が動くため）。`naive`（メタ解放も初見相当の `fresh`）の勝率は easy 5/10（50%）/ normal 5/10（50%）/ hard 1/10（10%）/ nightmare 0/10（0%）。SPEC 第19.1 F-7 が目標とする「初勝利5ラン前後＝勝率20%前後」に**合う難易度が無い**。easy と normal は初見でも半分勝ててしまい、hard は 10%、nightmare は全敗する。50% から 10% へ一段で落ちており、中間の 20% 前後に当たる難易度が存在しない。easy は完全放置（介入もカードも使わない `idle`）でも 5/10 勝てる。nightmare は310ラン全敗（RI-74）。参考値として全方針平均は easy 72.3% / normal 40.0% / hard 11.0% / nightmare 0% だが、これは実験用統制群を含むため成立判定には使わない。

F-1 の違反は2方向にある。**アンドン単独（`onlyAndon`）18/40 と緊急対応単独（`onlyFirefight`）16/40 が首位**（全難易度合計）だが、複合方針 `skilledNoHire` 15/40 との差は**1〜3勝**しかない。`onlyFirefight` は難易度別でも easy 10/10 と、複合方針（8/10）を上回る。**この差はビート評価を直すたびに縮んでおり**（19/16 対 14 → 18/17 対 16 → 18/16 対 15）、「単一介入が複合を明確に上回る」という当初の根拠は弱まっている。F-1 の違反として残すかどうかは再検証が要る。無差別採用側（`skilled` 11/40 対 `skilledNoHire` 15/40）の差は保っている。単一介入群は進化順（`reviewFirst`）とビート選択（`stateAware`）を `skilledNoHire` と揃えてあるため、差は介入構成のみに帰属できる。緊急対応は「打てるときに打てば得」で状況によって正解が入れ替わらず、他の介入を選ぶ理由が薄い。なお全介入を 1 tick ごとに撃つ `probe` は 10/40 と弱く、乱打が損になる関係自体は成立している。介入の反応間隔は `skilled` が約2.0秒、`naive` が約4.1秒（1x 換算）である。

統制実験（同一 seed、条件を1つずつ外す）では、**無差別採用が一貫して勝率を下げる**（全40ランで `skilled` 11 vs `skilledNoHire` 15。難易度別は easy 7/8、normal 4/5、hard 0/2）。採用方針を全経路（専用フェーズ・ショップ・休息・即時採用イベント）へ適用し、採用・復職の双方でベンチのメンバーを実働レーンへ配置した上での結果である。`budgetExhausted` 敗北は1,240ラン中14件。

さらに**「必要なときだけ採る」も見送りと同じ**だった。欠員（休職者あり／実働2名以下）があり、かつ**採用費を引いた残額**が `RECRUIT_COST`（=25）以上あるときだけ採る `skilledSelectiveHire` は **15/40** で、採らない `skilledNoHire` 15/40 と**完全に同数**である（難易度別も 8/5/2/0 で一致）。無差別に採ると大きく損をし、選択的に採っても得にならない。F-1 の観点では、緊急対応が「常に打てば得」であるのと対称に、**採用が「常に見送るのが正解」**になっている。

一方**カードは寄与している**（無差別 15 / 状況選択 11 / 不使用 8。向きは easy 8対6・normal 5対1・hard 2対1 の3難易度で一致）。ショップ投資と休息の選択は、差が0〜1しか無く寄与を確認できない（`skilledShopBuy` 15/40・`skilledRestUpgrade` 16/40・`skilledRestRepay` 16/40 と `skilledNoHire` 15/40）。詳細は RI-78。

受入条件:

- 初見相当（`naive`）の勝率が概ね 20% 前後になる難易度が、導入難易度（easy / normal）側に存在する。
- 完全放置（介入もカードも使わない）で勝ち越せる難易度が無い。
- 単一介入だけを繰り返す方針が、状況に応じて介入を選ぶ方針を上回らない。緊急対応にも
  不利になる状況（打つべきでない盤面）が存在し、同一難易度の中で有利／不利が共存する。
- 採用が**離職・休職のリスクを下げる方向**で作用する。人数を増やすことでレビュー負荷と
  スタミナ消耗が分散し、`onLeave` や燃え尽きの発生率が下がる。単なる出力の上積みではなく、
  「今の人数で回し続けるか、コストを払って壊れにくくするか」という選択にする（方針決定 2026-07-26）。
- 各手段のコスト（採用の予算・カードの集中力）は F-1 の求める代償として維持する。求めるのは
  代償の消去ではなく、**代償に見合う状況が特定できること**である。
- 難易度別の勝率レンジと、上記の「有利／不利になる条件」の両立を `npm run playtest` で検証し、回帰を検知する。

### RI-74 Nightmare は AI 依存を意識しない方針で第1スプリント敗北が確定する

nightmare は31方針310ランすべて敗北し、うち255ランが `aiDependency`。敗北までのスプリント数 p50 は 1 で、他の敗因（2〜24）と比べて突出して短い。回避経路は2種類ある。依存度を下げる経路（`onlyThrottle` / `noAi`）と、**リテラシーを上げて敗北条件そのものを外す経路**（`onlyPair` は依存度100のまま最終リテラシー 62 で `aiDependency` 敗北 0/10）である。とくに `pairReview`（「詰まったPRをペアで処理。AI Literacy が上がる」）による回避は SPEC 第19章の主題に最も合致する。それ以外の方針は最終リテラシー 25.0・依存度 100 で 10/10 が第1スプリント敗北する。回避経路はいずれも勝率 0/10。敗北条件は `org.aiDependency >= 95 && org.aiLiteracy <= 30`（`src/sim/outcome.ts:63-65`）で、nightmare の初期値 `aiDependencyBase`=55 / `aiLiteracy`=25（`src/data/difficulties.ts`）はリテラシー側を最初から満たしている。`aiDependency` は AI 割当タスク1件ごとに `AI_DEP_PER_TASK`=2.2 加算され（`src/sim/sprint.ts:193`）、`taskCountMul`=1.2 のタスク量で第1スプリント中に 95 へ到達する。問題は回避不能なことではなく、**回避に必要な方針が事前知識を要し、外すと第1スプリントで終わる**こと。SPEC 第19.1 F-8（詰みの確定を作らない）違反であり、初手で終わるため「負けて学ぶ」も成立しない。

依存度を下げる手段は既に存在する（カード `ai-guideline` の `aiDependencyAdd: -10`、レバー `aiGuideline` / `teamAiThrottle` の `aiDependencyDelta: -10`、`aiThrottleDept` の -8）。一方で AI を抑えない方針の最終依存度は全難易度で上限に張り付く。カードはドラフトの引き次第、レバーは四半期予算を消費するため、既定方針では低下手段が実質機能しない。リテラシー経路（ペアレビュー）も、チュートリアルにもリザルトにも現れず発見の手掛かりが無い。したがって不足しているのは手段の有無ではなく、既存手段の効果量・入手機会・発見性である。

受入条件:

- Nightmare で、事前知識のない方針が第1スプリントで敗北しない。
- AI 依存敗北の回避経路（依存度を下げる／リテラシーを上げる）がプレイ中に発見できる。とくに `pairReview` によるリテラシー上昇が敗北条件を外すことを、チュートリアルまたは敗北時の提示で伝える。
- 既存の依存度低下手段（`ai-guideline` カード・AI 系レバー）の効果量・入手機会・発見性を、1スプリントあたりの上昇量と釣り合う水準へ見直す。新規手段の追加はこの見直しで足りない場合に限る。
- 通常プレイで `aiDependency` が上限に張り付かず、意思決定の入力として機能する。
- AI 依存敗北が、盤面・HUD で数スプリント前から予兆として見える。
- 難易度別の `aiDependency` 推移と敗北到達スプリントをユニットテストで検証する。

### RI-75 スプリントが規定帯をほぼ全面的に下回る

SPEC 第3.1 の規定は通常60〜120秒（絶対下限30秒）・ボス90〜180秒。高負荷スプリント（`elite`）も「スプリント1本」の目標が要るため通常帯で判定した。標本は固定した代表3方針（`naive` / `skilledNoHire` / `noInterventionCtl`）に限る（全方針を連結すると方針構成と生存長が重みになり、方針を足し引きするだけで値が動くため）。**ボススプリントは easy 100% / normal 100% / hard 94.1% が規定下限（90秒）を下回り**、p50 は easy 32.6秒 / normal 39.4秒 / hard 39.4秒。山場であるはずのボスが通常スプリントとほぼ同じ長さで終わっている。通常スプリントも easy で 100% が規定下限（60秒）を下回り、**65.4% は絶対下限の30秒すら割る**（p50 23.1秒、p10 10.9秒）。normal は 95.8% が下回り 46.4% が30秒未満、hard は 78.8% / 19.0%。p50 が規定帯に入るのは hard の高負荷スプリント（102.0秒）と nightmare（115.6秒）だけで、**初見が最初に触れる easy が最も規定から外れている**。既存のペーシング回帰テスト（`tests/unit/sprintTempo.test.ts`）は無介入経路で通常スプリントの絶対下限・p50・p90 を検査しているが、対象は normal のみ。ボスは上限しか検査しておらず、下限（90秒）と高負荷スプリントは未検査。

受入条件:

- 全難易度で通常スプリントの p50 が第3.1 の 60〜120秒帯に入り、絶対下限30秒未満が生じない。
- ボススプリントの p50 が 90〜180秒帯に入る。通常スプリントより明確に長い。
- 高負荷スプリント（`elite`）も時間目標の対象として検証する。
- ペーシング統計検証（RI-66）を全難易度・全スプリント種別・下限と上限の両方へ拡張する。

### RI-76 勝利種別が実質2種で、最も受動的なプレイが最上位勝利を取る

1,240ラン中382勝の内訳は `healthy` 200（52%）/ `noDamage` 181（47%）/ `happiness` 1 で、`aiSuccess` / `management` / `chaos` / `normal` は0件、`happiness` も1件しかなく実質2種である。`evaluateWinType`（`src/sim/outcome.ts:103-118`）が固定の優先順ラダーで、先頭の判定が `!usedHeavyActions && totals.spread === 0` のため、残業もアンドンも使わない受動的なプレイほど「やり込み枠」であるはずのノーダメージ勝利になる。実測でも勝利種別は「重アクションを使ったか」だけで分岐している。組織診断も同様に偏る（`seniorSacrifice` 764 / `reviewHell` 395 / `documentationKingdom` 40 / `aiOverproduction` 26 / `healthyAcceleration` 14 / `reworkSpiral` 1）。ただしビルド方針ごとに見ると診断は明確に分かれており（`noAi` は `documentationKingdom` 10 / `healthyAcceleration` 5、`aiFullBet` は `reviewHell` 14 / `seniorSacrifice` 26）、内部状態は分岐しているのに勝利種別へ反映されていない。SPEC 第19.1 F-10 が求める「ビルドによって目指す勝ち筋が変わる」が成立していない。

受入条件:

- **勝利種別は自動判定のまま維持する**（プレイヤーによる宣言制は採らない。方針決定 2026-07-26）。
  直すのは判定側で、`evaluateWinType` の固定優先順ラダーがビルドの違いを潰している点。
- ノーダメージ勝利が、受動的なプレイでは到達しない難度になる。
- 組織診断がビルドで分かれている（`noAi` は `documentationKingdom`、`aiFullBet` は `reviewHell` 中心）
  のに勝利種別が2種へ潰れている状態を解消する。診断とビルド指標を判定へ反映させる。

### RI-77 AI 導入が既定 ON で、既定のまま進むのが有利

初期ロスターは `aiAssigned: arch.preferred === 'coding'`（`src/sim/member/roster.ts:135`）でコーダーに最初から AI が配られており、既定プレイの AI 利用率は 81.8%、最終 AI 依存度は 100。明示的な「AI 全配布」方針（`aiFullBet`）は既定とほぼ同じ結果になる。

**AI の効き方は実務感覚と逆向きである。** AI 配布だけを外した統制条件 `noAiCtl`（`skilledNoHire` から `setMemberAi` だけを false にしたもの）と比べると、勝率は 16/40→10/40 に下がる一方、**1スプリントの出荷はむしろ増える**。同一 seed・同一スプリント番号で対応を取った10セル中9セルで AI なしが上回り、残る1セルもほぼ同等で明確に下回るセルは無い（easy S2 307.3→357.1、normal S2 291.5→378.8、hard S2 311.4→394.0）。敗因の構成も入れ替わり、`aiDependency` 10件が消える代わりに `seniorBurnout` 5→9・`reviewFreeze` 9→15 が増え、`trustExhausted` 3件・`reorgRequired` 2件が新たに出る。敗北ランの長さは 5.0→14.2スプリントへ伸びる。四半期目標の未達回数は AI なしの方が多い（0.60→1.10）にもかかわらず1スプリントの出荷は多いという食い違いがあり、原因は特定できていない（RI-68 が絡む可能性がある）。

なおこの統制条件にも残差がある。`spec.ai` が変えるのはロスターの `aiAssigned` だけで、そこから決まるのは intake の AI 採用率（`aiAdoptionShare`）である。`org.aiEnabled` は true のままなので、`assignTask` 介入が `defaultAssignee` 経由で個別タスクを AI へ回す経路が残る（実測で492スプリント中5件、最大4%）。残差は小さく上の結論を動かさないが、「AI を完全に断つ」条件を測るには `org.aiEnabled` 側も落とす別の統制が要る。

AI の on/off が状態へ伝播していること自体は正しい（AI 利用率 0%、最終 AI 依存度 100→46.9）。問題は、「AI を入れると出荷が増え、その代償として別の何かが悪化する」という因果が出荷の増減として体感できないことである。なお以前この節は「AI 配布を全解除すると出荷 334.5→291.4」を因果の根拠にしていたが、これは統制条件ではない `noAi`（AI に加えて andon・進化ブランチ・ドラフト選好・採用まで違う）の値で、しかも現在は向きが逆である。

選択の入口は存在する。新規ランは第1スプリント前に必ず `SetupScreen`（見出し「編成 — スプリント開始前に配置とAIを決める」）を通り、`FormationScreen.tsx:172` の「🤖 AI配布中」ボタンから `setMemberAi` で解除できる。したがって課題は場の不在ではなく次の3点である。(1) 既定が ON で、既定のまま進むのが有利なため、選び直す動機が無い。(2) 解除側の代償が一方的に大きい。`noAi` は全難易度合計 11/40 で、`budgetExhausted` 敗北14件のうち**11件**を占める。AI で稼げないぶん予算を維持できず、AI 導入が実質必須になっている。(3) 導入が編成画面の on/off だけで段階が無く、「どこまで広げるか」を四半期を通じて問い直す機会が無い。

受入条件:

- 開始時の既定値が、そのまま進めるだけで有利な状態でなくなる（既定のまま／解除の双方に成立条件がある）。
- AI を入れない選択が、目標未達による敗北へ一直線に繋がらない（別の勝ち筋が成立する）。
- AI の導入度合い（誰に配るか・どこまで広げるか）が、ラン中に複数回問い直される段階的な意思決定になる。
- 開始時 AI の全面撤廃は取らない。`SetupScreen` / `FormationScreen` の既存の編成上の意思決定を重複して作り直さない。
- AI あり／なしの結果差が代表 seed で検証されている（`tests/unit/helpers/aiAdoptionSeeds.ts` の枠組みを利用する）。

### RI-78 スプリント間投資のうち、ショップと休息の選択が結果を変えない

当初「介入すべき状況が盤面に現れない」としていたが、これは誤りだった。毎 tick 全8種の介入を試す `probe` 方針の成立回数は easy p50=7 / hard p50=8 / nightmare p50=8 で、SPEC 第3.1 の「1スプリントあたり 3〜8回」の帯に収まる。介入の機会自体は足りている。

ただしこの値は**発動可能回数の上限ではない**。`probe` は8種を順に実際に発動するため、先行アクションが集中力を消費し、キューや炎上を変えて後続の機会を消す。上限を測るには盤面を変更しない発動可否判定が要る（RI-89 と同じ観測手段の不足）。ここでの値は「全介入を撃ち続けた場合の成立数」として読むこと。

**カード層は成立している。** カードだけを外す統制条件（`skilledNoHire` → `skilledNoCards`。採用条件は両方 `skip` で揃えてある）では、集中力不足による介入失敗（`no-focus`）が完全に消えて介入成立数が大きく増える。にもかかわらず**勝率は下がる**（全40ランで 16 → 8。向きは easy 8対6・normal 5対1・hard 3対1 の3難易度で一致）。状況に応じて発動を選ぶ `skilledSelectiveCards` は 11。つまり「カードに払う集中力は、その分の介入より価値がある」という交換が成立しており、F-1・F-2 が求める代償のある選択になっている。

なおこの結論は当初逆だった（「カードは集中力を消費するだけで寄与しない」）。ハーネスが同一 tick 内で複数介入を試すとき `when` の判定にループ開始時点の盤面を使い続けていたためで、各 `dispatch` の直前に盤面を取り直すよう直したところ差が 3勝ぶん→5勝ぶんへ広がり向きも揃った。

**残る未充足はショップ層と休息の選択である。** ショップでレリック→カードを買う `skilledShopBuy` は 15/40 で、何も投資しない `skilledNoHire` 15/40 と**完全に同数**である。休息の選択を回復以外へ振る `skilledRestUpgrade` / `skilledRestRepay` はいずれも 16/40 で1つ上回るだけである。カード層のような全難易度で一致する7勝ぶんの差とは質が違い、seed 差と区別できない。**直近5回の再計測で `skilledRestUpgrade` は 13→15→13→16→16、`skilledShopBuy` は 14→13→14→16→15、`skilledRestRepay` は 15→16 と動き、そのたびに順位が入れ替わっており、この層については「差が無い」以上を主張すべきではない。** SPEC 第19.1 F-2 が求める「スプリント間の投資が結果を変える」は、**ショップ層と休息の選択で成立を確認できない**。

対象不足（`no-target`）はアクションによって大きく異なる（単一介入方針で測った、試行のうち `no-target` で失敗した割合）。`firefight` は easy 約9割 / normal 約85% / hard 約77%、`assignTask` は難易度が上がるほど空振りし hard で9割超。`interruptReview` と `splitPr` はおおむね4〜6割。一方 `overtime` / `andon` / `pairReview` / `aiThrottle` は対象を要さず 0%。とくに `assignTask` は難易度が上がるほど空振りし、`firefight` は easy で約9割が空振りする。

受入条件:

- ショップでのカード・レリック購入と、休息での負債返済・カード強化が勝率・組織状態に有意な差を生む
  （`skilledShopBuy` / `skilledRestRepay` / `skilledRestUpgrade` と `skilledNoHire` の比較で確認できる）。
- カードの発動が勝率へ寄与する関係（16 vs 8）を回帰させない。
- カードと介入が集中力を共有する構造を残す場合、どちらを取るかの正解が難易度で固定されない。
  共有をやめる場合は、カード専用のコスト資源を導入して介入の集中力予算と切り離す。
- 対象を要する4種（`firefight` / `assignTask` / `interruptReview` / `splitPr`）について、対象の発生頻度と撃ちたくなる頻度が釣り合う。とくに `assignTask` が高難易度でほぼ空振りする状態を解消する。
- 上記を `npm run playtest` の統制方針（`skilledNoCards` 等）で検証し、回帰を検知する。

### RI-79 予算枯渇・信頼枯渇が予兆なく終わり、敗因ラベルが実態と一致しない

敗因ごとの進行速度は明確に異なり（敗北までのスプリント数 p50 が `aiDependency` 1 / `moraleCollapse` 2 / `seniorBurnout` 3 / `reviewFreeze` 8 / `techDebt` 13 / `budgetExhausted` 11 / `reorgRequired` 18 / `trustExhausted` 24）、この点は F-9 として良い。問題は予兆とラベルの2点である。

  プレイヤーが実際の原因を特定できる。

### RI-81 ドラフトのマリガンが無い

`DraftScreen` の選択肢は「3枚から1枚選ぶ」か「スキップ」のみで、コストを払って引き直す手段が無い。カードプールも9枚（`src/data/cards.ts`）で、うち4枚はメタ解放が必要なため初期プールは実質5枚。SPEC 第19.1 F-12 が求める「事故で負けた」→「コストを払ってでも引き直すか」への変換が成立していない。カードは結果に寄与しているので（RI-78。使う14 vs 使わない9）、どの3枚を引くかには意味がある。マリガンはその「引きの事故」を緩和する手段として単独で導入する価値がある。

### RI-82 敗北画面に「次の一手」が無い

`RunResultScreen` が敗北時に示すのは敗因ラベル＋一文の説明（`LOSE_LABEL`、`src/ui/RunResultScreen.tsx:26-52`）、組織タイプ診断、メタ進行ポイントで、次のランで何を変えるかは提示されない。教訓文（`FAILURE_LESSONS`、`src/sim/diagnosis.ts:64-81`）は初回敗北でも表示される（`recordIfFinished` が `applyRunReward` 経由で失敗診断を `collectedDiagnoses` へ加えてから画面を更新するため、`failureInCollection` は初回時点で true）。問題は対応範囲と粒度で、教訓は敗因（`LoseReason` 10種）ではなく組織タイプ診断に紐づき、しかも `FAILURE_LESSONS` が対応するのは失敗診断4種のみ。診断が `healthyAcceleration` / `documentationKingdom` のまま敗北すると `failureEntry` が存在せず教訓が一切出ない。また `budgetExhausted` / `trustExhausted` / `aiDependency` / `reorgRequired` で負けても表示は診断由来の一般論で、その敗因に対する次の一手にならない。SPEC 第19.1 F-6 は「初見は負けて学ぶ」の前提条件であり、学びが敗因に噛み合っていない。

### RI-83 目標修正の選択が結果を変えない

目標修正だけを固定する統制方針（**全6選択肢**、各40ラン）を、**共通コホート**で比較した。`availableAdjustments` は各選択肢の適用後状態で候補を絞るため、方針ごとに「提示され選べたラン」が異なり、そのまま勝率を並べると選択の効果と選抜条件を分離できない。そこで同一メタ・同一難易度・同一 seed で6方針すべてが同じ四半期に自分の修正を適用できた組だけを残した（16組）。adj* 6方針は `goalAdjustment` 以外すべて同一なので最初の修正までは同一 seed の6ランが完全に同じ経過をたどり、実際コホート内の修正時期は全方針で Q1 に揃っている。

**主指標は「初回修正の次四半期まで生存したか」にする。** ラン全体の勝敗では初回選択の効果を測れない。共通コホートで揃うのは最初の修正までで、その後の修正は方針間で統制されていないため、ラン全体の勝敗には後続選択がすべて乗る。初回修正の四半期を Q とすると、Q+1 の四半期レビューまでなら後続の修正はまだ1回しか挟まらない。

共通コホート（16組）での「初回修正の次四半期まで生存」は `request_budget` 68.8% / `pause_ai_rollout` 68.8% / `cut_scope` 75.0% / `extend_deadline` 75.0% / `quality_pivot` 75.0% / `reorg_teams` 81.3%。効果がまったく異なる選択肢（スコープ削減 / 予算追加 / AI 停止 / 組織リセット）を**同一の事前状態から**選ばせても 68.8〜81.3%（最大差は16ラン中2ランぶん）に収まり、n=16 では有意と言い切れない。参考値のラン全体の勝率も `extend_deadline` 37.5% 〜 `quality_pivot` 56.3% と近い幅だが、上記の理由で初回選択へ帰属できないため成立判定には使わない。目標修正フェーズ自体は1,240ラン中514ラン（41.5%）で発生しており選択機会は十分にある。SPEC 第19.1 F-2 が求める「四半期レビューの目標修正でジレンマが成立する」を満たさない。

なお当初の集計では `quality_pivot` の勝率を 83.3% としていたが、これは統制していない方針のランが提示順の先頭である `cut_scope` 群へ大量に混入した結果のアーティファクトだった。次に「到達四半期」に終端の `quarterNumber` を使っていたため、修正を選んだ時期ではなく後続のラン長を見ていた。さらに方針ごとに「提示され選べたラン」で絞っていたため選抜条件の差が残っていた（この段階の値は 52.9〜76.5%）。最後に、統制済みでもラン全体の勝率を主指標にしていたため、統制されていない後続の修正の効果を初回選択へ帰属させていた。いずれも訂正した。

受入条件:

- 目標修正の選択肢ごとに、後続四半期の進み方（勝率・到達四半期・組織状態）が有意に分かれる。
- 各選択肢に、それが有利になる局面と不利になる局面がそれぞれ特定できる（F-1）。
- 選んだ代償が次四半期以降に現れることが、プレイヤーに追跡できる形で提示される。
- 統制方針での比較を `npm run playtest` で検証し、回帰を検知する。

### RI-84 条件を揃えると介入の寄与がほぼ消える

`noInterventionCtl`（`skilledNoHire` から介入だけを外し、カード・進化・採用を揃えた統制条件）との比較で、勝率は easy 7/10・normal 4/10・hard 0/10（全40ランで11）。対する `naive` は 5/5/1（11）、`skilledNoHire` は 8/5/3（16）。**介入なしと初見の介入は同点**で、熟練の介入との差は +5。`skilledNoHire` の伸びの大半はカードとの相互作用である（RI-78）。分散も同様で、同一スプリント番号の出荷 CV に方針間の一貫した差は出ない。

当初「介入は勝率を改善している（完全放置 7 → 熟練 16）」としていたのは、進化・カード・採用が同時に変わっていたためだった。介入だけを統制すると期待値でも分散でも寄与がほとんど無い。SPEC 第19.1 F-5 は「無介入は損ではなく不安定。介入の価値は結果の偏差を抑えること」と定義しているが、実装は期待値も分散も動かしていない。

受入条件:

- **実装を定義に寄せる**（F-5 の定義は変えない。方針決定 2026-07-26）。介入に下振れを潰す性質を
  持たせ、無介入の分散を大きくする。介入は期待値の底上げではなく不確実性の抑制として設計する。
- `noInterventionCtl` と介入方針の間に、同一スプリント番号の出荷 CV で有意な差が出る
  （介入側が明確に低い）。
- 介入しない方が勝つ難易度が無い。
- 判定を `npm run playtest` の統制方針で検証し、回帰を検知する。

### RI-85 レビュー凍結が選択不能な判定イベントでしか確定しない

**これは F-8 の直接の根拠にはならない。** SPEC 第19.1 F-8 の観測条件は「敗北が確定する**何スプリント前から**実質的な選択肢が消えていたか」であり、最終イベントが選択不能であることだけでは満たせない（直前まで回避策があり最後だけ judgment で決着するランも同じ形になる）。各時点で利用可能だった回避手段の記録が要る（RI-89 と同じ観測手段の不足）。ここで言えるのは「決着の瞬間に操作の余地が無い」までである。

敗北を確定させたフェーズを、ビートについては judgment（選択不能な判定）と decision（プレイヤーが選ぶ）に分けて記録した。

敗因ごとに決着位置は分かれる。**`reviewFreeze`（295件）は例外なく100%が `review-freeze`(judgment) で確定**し、盤面で対処する機会がない。プレイヤーはスプリントを走り切った直後に、操作の余地がない画面で敗北を告げられる。一方 `seniorBurnout`（206件）は judgment / **decision** / sprint が混在し、選択を経て確定するものが相当数ある。`aiDependency`（255件）・`techDebt`（31件）・`moraleCollapse`（15件）はスプリント中、`trustExhausted`（24件）・`reorgRequired`（13件）は四半期レビューで決まる。

全858敗の決着フェーズは `beat:judgment` 455（53%）/ `sprint` 327（38%）/ `quarterReview` 37（4%）/ `beat:decision` 33（4%）/ `shop`・`rest`・`recruit` 6（1%）。`beat:decision` はビート選択の統制を進めた結果 90件（12%）→ 40件（5%）→ 33件（4%）と段階的に減った。最初は `firstChoice` が `urgent-demo` のようにシニアHPを削る先頭選択肢を無条件に取っていた分、次は評価に予算が入っておらず `postmortem-culture` で予算0＝即敗北を自分から選んでいた分である。**選択イベントで負けるランの多くは盤面を見て選べば避けられる**一方、`reviewFreeze` にはその余地が無い。

当初この所見は敗北の大半が「操作の余地がない画面」で確定するとしていたが、これはハーネスがビートの選択肢を常に先頭で取っていたためだった（`urgent-demo` の先頭は `seniorHp -10 / morale -15`）。状態を見て選ぶ方針へ変え、judgment と decision を分けて記録した結果、対象は `reviewFreeze` に絞られた。

受入条件:

- `reviewFreeze` の敗北が、スプリント中に予兆と対処の機会を伴って決着する。または判定イベントで確定する前のスプリントで明確な警告が出る。
- 敗因ごとの決着フェーズ分布（judgment / decision / sprint / quarterReview）を `npm run playtest` で検証し、回帰を検知する。

### RI-86 Q1 で進化ツリーを取り切れてしまい、ビルドの方向という概念が成立しない

SPEC 第19.1 F-11 は「どの方向で回すかが Q1 の途中で見え、以降はその方向を伸ばすか曲げるかの判断になる」ことを求める。判定には**構造的事実と、標本を固定した実測**を使う。進化ツリーは**15ノード / 総コスト26**、1スプリントの入手ポイントは `1 + floor(出荷/40)`（高負荷は +1。`RunEngine.evoPointsFor`）。代表4方針（`naive` / `skilledNoHire` / `aiFullBet` / `noAi`、n=160）で測ると、**Q1 で入手する総ポイントの p50 は 43** でツリー総コスト26の約1.7倍、Q1 解放数の p10/p50/p90 は 13/**15**/15、**Q1 中にツリーを取り切ったランは 111/160（69.4%）**。なお全160ランのうち30件は Q1 の入手が0点で、**すべて nightmare の第1スプリント敗北**である（そもそも方向を選ぶ局面に到達していない）。この30件を除いた条件付き分布では p10/p50/p90 が 22/**45**/55 になる。どちらで見ても総コスト26を大きく超えるため結論は変わらないが、**0点を除いた値を n=160 の実測として書かない**こと。なお**実際に入手できるポイントだけを数えている**。`resolveSprint()` はボス分岐でも敗北時でも四半期レビュー／敗北へ遷移して `return` し、通常スプリント用の加算へ到達しないため、ボスと「スプリント終了時に敗北したランの最後のスプリント」は0点である。第1四半期のうちに木を丸ごと買ってなお余るポイントが入り、「どのブランチへ寄せるか」という選択がそもそも発生しない。F-11 が前提とする「方向を選ぶ＝他を諦める」構造が無い。標本を代表4方針に固定しているのは、全ランを母数にすると `evolve: 'none'` の方針や `skilledBase` の複製を増減するだけで分位点が動くためである。

ブランチの偏りでは判定できない。ハーネスの解放順は方針の `evolve` 設定で固定されており盤面に応じて選んでいないため（全方針で最初の2ノードが必ず同一ブランチになる）、「同一ブランチへ寄っているか」を数えると基準の緩さ次第で 1.1%（Q1 全体の最終構成比）から 92.9%（最初に条件を満たした時点）まで動く。どちらもハーネスの設定を測っているだけである。方向の確定時期を測るには、盤面に応じてブランチを選ぶ方針をハーネスへ追加する必要がある。

当初この所見は F-11 を成立としていた（「Q1 に1ノードでも解放すれば方向が決まった」と数えていた）。その後「Q1 全体の最終構成比」で判定して未充足へ反転し、さらに「最初に確定した時点」で判定すると 92.9% と再反転した。いずれもハーネス側の解放順を測っていたため、方針に依らない「Q1 で取り切れるノード数」を主要指標へ切り替えた。

受入条件:

- Q1 で入手する進化ポイントが、ツリー総コスト（26）に対して十分小さく、選択が発生する。
- ブランチを選ぶことが、選ばなかったブランチを諦めることを意味する（コストか排他性）。
- Q1 の入手ポイントと解放ノード数の分布を `npm run playtest` で検証し、回帰を検知する。
- 盤面に応じてブランチを選ぶ方針をハーネスへ追加し、方向の確定時期を測れるようにする。

### RI-87 セキュリティ軸が存在しない

SPEC 第19.1 F-10 のビルド表は「セキュリティ軽視」を想定ビルドの1つに挙げているが、ゲーム内にセキュリティの概念が無い（`src/` で該当する状態値・カード・イベントは存在せず、`security` の語はボス名にのみ現れる）。検証を省いて速度を買い、事故の期待値と信頼の下振れを引き受けるというトレードオフが成立しない。実装する（方針決定 2026-07-26）。

受入条件:

- 組織状態にセキュリティ水準を持ち、低いほど事故（`incident`）の規模または信頼低下が大きくなる。
- 検証を省いて速度を取る選択が、短期の出荷増と引き換えに下振れリスクを増やす形で成立する。
- セキュリティ軽視ビルドが `npm run playtest` の方針として定義でき、他ビルドと結果が分かれる。

### RI-88 インフラコスト軸が存在しない

SPEC 第19.1 F-10 のビルド表は「自前エージェントハーネス（肥大）」と「同（最適化）」を想定ビルドに挙げているが、ゲーム内にインフラコストの概念が無く、予算は採用・ショップ・レバーでしか動かない。AI を使うほど継続コストが積み上がり、コスト最適化がそれを抑えるという構造が成立しない。実装する（方針決定 2026-07-26）。

なお試練には `frontierModelCostPerDependency`（AI依存度あたりの利用コスト）が既にあり、これを恒常的な軸へ広げる形が最小の実装になりうる。

受入条件:

- AI 利用量または自動化水準に応じた継続コストが予算を圧迫する。
- コスト最適化への投資が、初期は損だが長期では回収できる選択として成立する。
- 肥大ビルドと最適化ビルドが `npm run playtest` の方針として定義でき、結果が分かれる。

### RI-89 敗因ごとに「打てた手」が違うかを測る手段が無い

SPEC 第19.1 F-9 は敗因ごとに「危険域へ入るまでのスプリント数・直前の状態推移・**その時点で打てた手**」が互いに異なることを要求する。前2つは計測できているが、3つ目が測れていない。

`SprintLog.attempts` に残るのは各方針が**実際に試した**アクションの結果だけで、危険域で**利用可能だった**手の全体ではない。`applyAction`（`src/sim/actions.ts`）は集中力・クールダウン・対象の有無を順に検査するが、対象の有無は効果関数 `EFFECTS[id]` を実行して `null` かどうかで判定するため、実行せずには分からない。実行すれば盤面が変わるので、読み取り専用の観測ができない。

このため現在は「進行速度と決着位置は敗因ごとに違う」までしか言えず、**進行速度だけが違って対処法は同じ**という可能性を排除できていない。

受入条件:

- 盤面を変更せずに、各アクションが発動可能かどうか（集中力・クールダウン・対象の有無）を判定できる。
- `npm run playtest:report` が敗因別に「危険域で発動可能だった介入の集合」を出力する。
- その集合が敗因ごとに異なることを確認したうえで、F-9 を全体として成立と判定できる。

実装案: `applyAction` の対象判定を効果適用から分離し（`EFFECTS` を「対象を探す」と「効果を適用する」の2段に割る）、`canApplyAction(id, sprint, org, tick)` を読み取り専用で公開する。ゲーム側でも介入ボタンの活性・非活性の根拠として使えるため、UI の presentation にも寄与しうる。
