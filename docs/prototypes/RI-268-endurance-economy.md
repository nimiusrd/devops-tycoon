# RI-268 耐久経営

対象は [#664](https://github.com/nimiusrd/devops-tycoon/issues/664)。判断は **再試作**。初回勝利後の6期を実シミュレーションで比較した。期首に資金を補っても、6期完走と連続した安定運営には差があった。

## 通常ランからの分岐

現行は1期6スプリントの固定トラックで、最終スプリントがボス。ボスと全社KPIを評価し、`met` / `exceeded` を承認すると通常の自動勝利種別で決着する。`missed_adjustable` は可能な目標修正の一つを選んで次期へ進む。修正した目標と組織・予算・編成等を引き継ぎ、Delivery目標に既存の減衰と下限が掛かる。継続不能なレビューやスプリント中の敗北は既存の判定で終了する。

試作の耐久は初回の通常 `won` が入口。勝利承認前の反実仮想フレームを手元に取り、元の `RunEngine` で実際に勝利を確定する。そのフレームから比較用のインスタンスを作り、達成後は次のボス定義から新しい目標を立てる。未達修正からの継続は耐久中も通常の `chooseGoalAdjustment` を使う。途中敗北・継続不能は既存判定で止め、耐久6期の上限に達した場合は `horizon` を記録する。6期目の途中敗北は `lost` であり、6期完走に数えない。比較用インスタンスへだけ継続・報酬の変更を適用できるように、`RunEngine` の次期開始とレリック付与を保護メソッドにした。通常ランは既定の修正目標の引継ぎと付与を使う。

通常はボス突破レリックの付与と、ラン決着時の `GameHandle` によるメタ報酬・コレクション記録が別経路。初回勝利まではボスレリックを実際に獲得し、メタ進行ポイントは既存式で計算して比較結果に記録する。試作中は通常側もメタに書き込まない。初回勝利以前のレリックを耐久へ引き継ぎ、耐久中はボス突破レリックの付与とメタ進行を止める。スプリント内の既存成長・ドラフト・進化・イベントは進める。本番統合する場合は、通常ランの決着・報酬・リプレイ保存を確定させてから別インスタンスを開始し、耐久の達成や敗北から通常報酬やデイリー進行を発行しない。

[RI-300 四半期リレー](RI-300-quarter-relay.md)（[#1198](https://github.com/nimiusrd/devops-tycoon/pull/1198)） はQ1未達の目標修正フレームをファイルで他の人へ渡し、Q2を担当してもらう。耐久は通常勝利後の同じ会社を同じ人が運営し、目標更新と長期の資源制約を評価する。試作同士に依存はない。

## 比較条件

難易度 `easy`、標準シナリオ、初期予算60、試練・優先施策なし、カードの候補は全解放。同一seedでは初勝利の直前までの行動・盤面と耐久各期の乱数種を共有する。通常部分は余力重視で最大6期進め、未達修正は候補先頭を選ぶ。初回勝利しない例も記録した。固定seedは探索から選んだ事例で、勝率推定には使えない。

- 共通操作。編成で復職者・採用者を適性に応じて配置し、実働コーダーを確保する。スプリントは手札を順に試し、1,000msごとにペアレビュー、レビュー待ち6以上で割り込み、延焼まで15tick以下の炎上に消火を試す。ドラフト先頭、進化は `review-1` → `quality-1` → `review-2` の順に可能なら解放。決断イベントは即時採用・即敗北を避ける先頭肢、判定イベントは先頭で進む。店では購入しない。
- 出荷優先。空き枠と予算があり、採用後も残高が正なら採用する。採用しない休息は先頭カードを強化し、修正は `cut_scope` を優先する。
- 余力重視。稼働可能な人が2名以下で採用後も採用費1回分を超える場合に採用する。採用しない休息は対象チームの負債15以上かつシニア体力60以上で返済し、それ以外で回復。修正は `quality_pivot` を優先する。両方針とも優先修正の提示がなければ候補先頭を選ぶ。
- 予算条件。現在の繰越のみと、期首ごとに12を加算する比較を両方針で行う。加算は前期の達成・ボス突破・敗北に連動せず、既存の繰越上限の適用後、次期の最初の編成時に一度だけ行う。繰越対照も同じフレーム復元を通る。12は事前探索で観測したボス開始時の課金がおおむね6〜11だったことに基づく比較値。既存インフラ単価、採用費25、目標修正の費用は既存定義を使う。

達成判定に加えて、期末に採用費1回分以上の予算と配属済みの実働メンバー2名以上を確保できた期を安定期とした。比較では「観測できたレビュー数」「安定期の最長連続」「期末残高・信頼」「出荷対目標・未達KPI」「期首/期末の編成・体力・負債・デッキ」「行動と期末結果」を見る。レビュー前に敗北した期は完了数に含めず、部分出荷はログに残す。`bossInfraCharge` はボス開始時の実際の引き落とし。スプリント中のカードによる返金より前の値で、到達しなければ空欄になる。

## 履歴上限と本番統合時の受入条件

試作は勝利前も耐久も各6期を上限とするメモリ内の比較で、保存ファイルから再開する機能は持たない。本番候補は通常セーブと別の保存領域・形式にし、専用rulesetと既存のバランス版・指紋を持たせる。通常セーブの移行や、通常リプレイから勝利後の状態を推測する処理は不要。通常の共有・自動保存・タブ所有権の入口には耐久データを渡さない。

無期限の継続を再試作する場合、四半期末の `reviewHistory` / `trendHistory` / 修正履歴は直近6期、過去分は完了数・達成数・安定期数・連続数の集計値で保持する。最終勝利の情報は専用の固定項目一件で保持する。各期の復元は現在期の開始時チェックポイント1個と、現在期の入力／リプレイを上限とする。保存単位を期で切り、過去期の全入力・全フレームを増やし続けない。通常の保存件数上限だけでは1件内の肥大化を抑えられないため、耐久の入力列と直列化サイズにも測定に基づく上限を設ける。現行の `goalAdjustmentsTaken` は記録用で、再選択条件は現在の資源・KPI・候補安全性によって決まる。将来、履歴に基づくルールを追加する場合は必要な集計値を保持する。

履歴を切るだけではデッキやメンバー通知の識別子が増え続ける。デッキが満杯になったときの置き換え、現存しないメンバーの通知フラグの破棄、保存上限に達した場合も最新地点から再開できることを本番受入に含める。長期試作では、同じrulesetと記録入力で再開前後の状態と次の乱数消費が一致し、通常セーブおよび通常決着の報酬が影響を受けず、上限到達前後で保存サイズが有界であることを検証する。

## 次の判断条件

**再試作**。期首の加算だけでは安定期が続かず、同じ修正が反復された。次は目標の持ち越しに残ったKPIと実働人員不足をプレイヤーが事前に読み取り、出荷を取りに行く期と回復へ振る期を選び分けられる小さなプレイ用試作を作る。AI採用率の持ち越しと期首資金を一要因ずつ変え、少なくとも2つの局面で選ばれる手が変わることを確認する。人間のプレイで、行動の効果・代償と、同じ操作を繰り返した理由を記録できることを終了条件にする。今回はUI・人間のプレイ評価・本番の保存再開を実施していない。
