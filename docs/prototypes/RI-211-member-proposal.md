# RI-211 巨大PRへの改善提案

対象は #607、親は #548。判断は**再試作**。直近の出荷、レビュー余力、士気を交換する二択は固定条件で比較できた。次は、提案者の表示が判断に役立つかを実際のビートの文脈で確かめる。

## 提案者と二択

通常の選択イベント「巨大 AI 生成 PR が投下された」（`giant-pr`）を試作の起点にする。元の二択を見せ、該当する人物がいれば案の横に名前とトレイトを添える。

| 既存の選択肢 | 話者のトレイト | すぐ得るものと払うもの |
| --- | --- | --- |
| シニアが気合いでレビュー | レビュー鬼 | 品質 +4、シニア HP -14。試作では次の盤面でレビュー待ちの先頭最大4件に先に着手する。通常の手戻り・事故判定と処理ごとのHP消費がある |
| 分割を依頼する | ドキュメント魔 | 士気 -6、レリック「小さく出す文化」を獲得。レリックによりレビュー効率が1.15倍になる |

レビュー鬼は高いレビュー能力を活かす案、ドキュメント魔は小さく提出する手順を定着させる案を出す。同一ロスターでの二案の効果は、既存イベント定義と盤面条件で決まる。士気の消費は現行イベントの組織コストとして計上する。

イベント発生時にロスターから、休職していない該当メンバーを選ぶ。配置可能なベンチのメンバーも含む。採用候補はロスターに入った時点から対象になる。候補をIDで並べてイベントとトレイト別のseedで選び、両方のトレイトを持つ人物がいても、可能なら別人にする。該当者が足りない案は無記名で選べる。提示時に確定したID・名前・トレイトを保持するため、表示の読み直しや試作データのJSON往復でも同じ提案を表示する。

## 固定条件での比較

各seedで同じロスター、予算40、AI導入済みの既定組織（品質60、士気70、シニアHP100）、レリック・カード介入なし、同じタスク抽選（Normalの50件）から二択を比較した。初期メンバー3人とドキュメント魔の採用済み1人で開始する。残り時間は、次の1スプリントの実験用最終tick。開始時のレビュー待ちに指定件数を置く。選択と即時レビュー以外の入力は無介入。二択の解決・次のスプリントの組み立て・レビュー・残り工程の進行には既存の処理を使い、開始直前のシニアHP回復も適用した。期間・渋滞・負債を基準から一つずつ変えた。

表は同じ6seed `RI-211-a`〜`RI-211-f` の合計。各セルは即時レビュー案 / 分割案。

| 条件（レビュー待ち / 初期負債 / 最終tick） | 出荷ポイント | 完了件数 | 終了時レビュー待ち | 手戻り |
| --- | ---: | ---: | ---: | ---: |
| 締切間近（12 / 8 / 5） | 396 / 283 | 44 / 33 | 52 / 60 | 1 / 0 |
| 渋滞が軽い（1 / 8 / 5） | 141 / 166 | 18 / 19 | 7 / 1 | 3 / 2 |
| 負債が多い（12 / 44 / 5） | 350 / 283 | 41 / 33 | 54 / 60 | 4 / 0 |
| 時間に余裕（12 / 8 / 40） | 1982 / 2065 | 167 / 168 | 122 / 118 | 16 / 13 |

締切間近かつ渋滞している条件では、即時レビュー案は6seed中4seedで出荷ポイントが多かった。同じ締切で渋滞が軽いと、先に処理できるレビューが1件に減り、分割案が3勝3分だった。負債だけを増やすと即時レビュー案の手戻りが1件から4件に増え、出荷差は113から67に縮んだ。時間に余裕がある条件は分割案が4勝2敗だった。締切間近の `RI-211-a` では、終了時HPは86.14 / 95.24、士気は73 / 67.5で、出荷と別の得失も残った。

これは6seedでの固定条件、固定入力の比較。選択後は処理順に沿って乱数を消費するため、タスクごとに適用する乱数は分岐間でずれる。適応的な操作、継続した組織効果と勝敗、人物による理解や愛着について、人間のプレイ評価は未実施。比較は[ユニットテスト](../../src/prototypes/memberProposal.test.ts)から再計算できる。

## 次の判断条件

同じ既存ビートの枠で、提案者の表示がある場合と無記名の場合を、締切間近の渋滞と時間に余裕がある条件で人間が遊んで比較する。選択前に「どちらが先に効くか」「HP・士気のどちらを払うか」を説明でき、条件を変えたときに理由を伴って選び直せるかを記録する。表示を付けても判断理由や人物の理解に差が出なければ、人物提示の追加は見送る。

#538 の直接介入と仕組み化の交換を、既存ビート一件の二択に限定して試した。関連する案の #636 は後日談の予約を、#562 はタスク自体の分割を扱う。通常ランの統合を判断する際は、ビートの発生単位で提案者IDを保存する方法、既存セーブの無記名扱い、リプレイとruleset互換、既にレリックを所持している場合と付与枠不足時の分割案を設計する。
