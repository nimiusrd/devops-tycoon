# Codex レビュー依頼と対応ループ

実装が終わり PR がある状態で、Codex にレビューを依頼し、未解決スレッドがなくなり CI が通るまで対応を繰り返す。
マージ、draft 解除の強制、auto-merge 有効化は行わない（ユーザーが明示した場合のみ）。

## いつ使うか

- 実装・PR 作成後に Codex レビューを回すとき
- `/autopilot` で PR を merge-ready まで進めるとき
- 既存の Codex 指摘だけを消化するとき

前提: 対象 PR と作業ブランチが特定できること。未作成なら先に `commit-and-pr` スキルで PR を作る。

## ワークフロー

優先順位は常に **競合解消 → 未解決 Codex スレッド → CI 失敗**。

### 1. 対象 PR を確定する

1. 現在ブランチ、`gh pr view --json number,url,state,isDraft,mergeable,mergeStateStatus` で PR を特定する。
2. 作業ツリーが汚れていれば、今回の対応に必要な変更だけを残す。
3. `main`（または base）と大きく乖離して競合している場合は、先に rebase/merge で競合を解消する。

### 2. Codex にレビューを依頼する

未解決スレッドが無く、まだ最新コミットに対する Codex レビューが無い（または push 後に再レビューが必要な）ときは、PR の **issue コメント** として次だけを投稿する。

```text
@codex review
```

- 余分な文言・チェックリスト・署名を付けない（ユーザーが毎回これだけを投稿している）。
- Draft のままでもコメント依頼してよい。Ready 化はユーザーが明示したときだけ行う。
- 依頼直後はレビュー生成を待ち、数分経ってもスレッドが増えなければ `gh pr view` / GraphQL で再確認する。勝手に何度も `@codex review` を連投しない（目安: 同じ HEAD に対して 1 回。新規 push 後に再依頼）。

### 3. 未解決スレッドを収集する

1. GraphQL で `reviewThreads` を取得し、`isResolved == false` のみを対象にする。
2. 著者 `chatgpt-codex-connector` の指摘を主対象にする。人が付けた未解決コメントも、対応方針が明確なら同じループで処理してよい。
3. 各スレッドから `thread.id`（resolve 用）、先頭コメントの `databaseId`（返信用）、`path` / `line` / `body` / P1・P2 バッジを控える。
4. 古い・的外れ・現行 `main` や最新 HEAD で再現しない指摘は、修正せず **根拠付き dismiss** してよい。

コマンド雛形は [reference.md](reference.md) を使う。

### 4. 指摘ごとに修正する

1. 指摘を読み、再現手順・期待・現行コードを確認する。
2. 妥当なら最小差分で修正する。テスト・所見・数値を更新する場合は、このリポジトリの既存検証（例: `npm run lint`、`npm run format:check`、必要なら `npm test` / `npm run playtest:check`）を回す。
3. 妥当でない、または既に別コミットで解消済みならコード変更はせず、返信で dismiss 理由を書く。
4. 変更があれば `commit-and-pr` のコミットメッセージ形式でコミットし、`git push` する。
5. 複数スレッドをまとめて直してよいが、**返信はスレッドごと**に行い、内容とそのスレッドの指摘を対応付ける。

### 5. ユーザー文体で返信し、スレッドを resolve する

返信はエージェントが行う。ただし文体はユーザー（`nimiusrd`）のレビュー返信に合わせる。

#### 返信の書き方

- 一人称の長い経緯説明、謝罪文、「ご指摘ありがとうございます」などの前置きは書かない。
- 先頭は原則 `対応済み。` とする。
- dismiss や方針変更を含むときは `対応済み（dismiss + 再調整）。` のように括弧で補足してよい。
- 続けて、何をどうしたかを短く書く。パス・記号名・計測値・コミット SHA など事実を入れる。
- 検証した場合は `playtest:check` 通過やコホート結果など、確認した事実だけを添える。
- 「対応しました。」は使わない（エージェント口調に見えるため）。

良い例:

```text
対応済み。`stateAware` にはラン累積の `totals.reviewQueuePeak` ではなく直近スプリントの `reviewQueueMax` を渡し、解放のたびに既解放ブランチも見て順位を見直すようにしました。
```

```text
対応済み。F-1 本文の旧コホート前提の散文を、同一 `runs.json` の現行値に合わせて更新しました（`playtest:check` 通過）。
```

```text
対応済み（dismiss + 再調整）。指摘の前提は現行 `main` では再現せず、勝率崩壊の主因をこの PR の変更だけに帰属できない状態です。先端コストは再配分済みです。
```

悪い例:

```text
ご指摘ありがとうございます。おっしゃる通りだったので修正しました。
```

```text
対応しました。この問題を修正しています。
```

#### 返信と resolve の手順

1. 対象スレッド先頭コメントの `databaseId` に対して replies API で投稿する。
2. 投稿成功後、そのスレッドの `thread.id` で `resolveReviewThread` を呼ぶ。
3. 返信先を取り違えない。別 discussion に投稿しない。
4. コードを push する前に resolve だけして「対応済み」と偽らない。修正コミットが必要な指摘は **push 後**に返信・resolve する。
5. dismiss のみの場合は、根拠を書いた返信の直後に resolve してよい。

### 6. CI を確認する

1. `gh pr checks` で必須チェックを確認する。必要なら `--watch` する。
2. 失敗したらログを読み、修正 → commit → push → 必要なら該当スレッドへ追記、の順で戻る。
3. push 後に新たな Codex レビューが無ければ、再度 `@codex review` を 1 回投稿する。

### 7. ループ停止条件

次をすべて満たしたら停止し、merge-ready として報告する。**マージはしない。**

- マージ競合がない（`MERGEABLE` / `CLEAN`）
- 未解決レビュースレッドが 0
- 必須 CI が成功

未解決が 0 で CI 待ちだけなら、CI 結果を待ってから報告する。
同じ HEAD で Codex が追加指摘を出さず停止条件を満たしていれば、追加対応不要と報告して終了する。

## 報告フォーマット

各ターン終了時は短く日本語で報告する。

```markdown
## 結果
- PR: <url>
- 対応した指摘: <件数と要約>
- 再依頼: `@codex review` を投稿した / 不要だった
- CI: <成功 / 失敗 / 待ち>
- 未解決スレッド: <残数>
- マージ: していない
```

## 制約

- ユーザーが明示しない限りマージしない。
- `@codex review` 以外の定型で Codex を呼ばない（`@codex address that feedback` などはユーザー指示時のみ）。
- 秘密情報を返信やコミットに含めない。
- 指摘の捏造解消（返信だけで直したことにする）をしない。
- force push、`--no-verify`、無関係ファイルの巻き込みをしない。
- ManagePullRequest で line comment 返信や resolve ができる場合でも、失敗時は `gh api` / GraphQL にフォールバックする。
