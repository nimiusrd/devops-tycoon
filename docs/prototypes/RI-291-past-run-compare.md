# RI-291: 前回の自分との並走

対象 #687 / 親 #548。結論: **境界比較の仮説採用、本番統合保留**。人間のプレイ評価は未実施。

## 照合と比較の契約

通常ランから隔離した純TS試作。`comparePastRuns(a, b)` は、現行の `ReplayBlob` から比較に使う部分（`ComparableReplay`）だけを読む。過去の会社をライブsimとして動かさず、記録済みキーフレームの値だけを並べる。結果は `source: 'recorded-boundaries'`、`liveSimulation: false` を持つ。

開始条件は8項目を照合する。1つでも `match` 以外なら比較不能とし、行・時間帯・終端を返さない。

| 項目 | 読む場所 | 不足（`missing`）になる記録 |
| --- | --- | --- |
| seed / 難易度 / 試練 | リプレイ本体 | — |
| シナリオ / ラン種別 / 解放プール | ラン開始時の setup フレーム（スプリント0） | 開始時の setup を持たない記録。各スプリント前の setup では代用しない |
| 研修方針 | 同じ setup フレームの `preferredCardIds` | 開始時の setup を持たない記録。フィールド欠落は空配列（旧記録の復元と同じ）で、`missing` にはしない |
| ruleset | `ruleset` | 旧v1リプレイ（`null`） |

行はスプリント結果に残り、同じ画面の後続操作では置き換わらない値から作る。通常は `result`、ボス回は `quarterReview`。ドラフト・各スプリント前の setup・途中敗北の終端は行に足さない。両方にある回は `common`、片方だけの回は `only-a` / `only-b` で、片方だけの行には優劣を付けない。

各共通行は指標ごとに有利な側（`a` / `b` / `tie`）を持つ。高いほど有利なのは累計出荷・回の出荷。低いほど有利なのはレビュー滞留の最大値。時間帯の得手は、出荷（回の出荷）・滞留（レビュー滞留）の2系統で、有利だった回の番号を別々に返す。合算した総合点は持たない。終端（勝敗・敗因・何スプリント完了後か）は行と分けて返す。

シニア余力・士気・技術的負債・予算は境界の優劣に使わない。結果画面や四半期レビューで組織レバーを使ったり別チームへ入り込んだりすると、保存されるキーフレームは同じ phase のまま操作後の `org` と `budget` に置き換わる。スプリント完了直後の値は記録に残らない。出荷と滞留は `lastResult` に固定されたままなので、置き換え後のフレームからも読める。

## 同条件比較

実エンジン（`RunEngine`、難易度 normal、試練なし、default シナリオ）を同じ seed で2方針に分けて走らせ、ゲームと同じ規則でキーフレームを集めた。素の方針は手札を出して進めるだけ。熟練方針はペアレビュー・渋滞の割り込み・火消しを使う（`tests/unit/helpers/runFlow.ts` の `skilled`）。`toComparableReplay` で比較に使う境界と項目だけを残し、値は丸めずに固定データ `past-run-compare-fixtures.json` に保存した。固定データは記録時のバランスを写したもので、以後のバランス変更でテストを壊さない。

seed g2（a = 素、b = 熟練）。出荷は回の値。

| スプリント | 区間 | 出荷 a | 出荷 b | 滞留 a | 滞留 b |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | 共通 | 592 | **635** | 22 | **17** |
| 2 | 共通 | 634 | **705** | 16 | **15** |
| 3 | 共通 | 689 | **820** | 18 | 18 |
| 4 | 共通 | **931** | 788 | 29 | **22** |
| 5〜17 | aだけ | 568〜1030 | — | 19〜42 | — |

熟練方針は1〜3回の出荷で上回るが、4スプリント完了後にシニア燃え尽きで敗北する。素の方針は4回で出荷が逆転し、17スプリント完了後に予算切れで敗北する。出荷と滞留の得手は一致しない（出荷 b=1〜3・a=4、滞留 b=1,2,4・同値3）。単一の総合点では「序盤の速さ」と「どこで滞るか」を区別できない。途中の消耗は現行の記録では境界として残らないので、続くかどうかは終端（敗因と完了スプリント数）で分ける。

seed g1 は両方とも8スプリント完了後にシニア燃え尽きで敗北し、全8回が共通区間。出荷は熟練が1〜3,5,6回、素が4,7,8回で上回る。

固定データと比較結果を `past-run-compare-comparison.json` に記録する。

開始条件をそろえた2リプレイの境界比較で、方針ごとの得意な時間帯と、共通区間の後に片方だけ続く区間を示せる仮説を採用する。比べられるのは出荷と滞留までで、消耗の途中経過は現行記録では示せない。本番統合は保留。次は、表で読める回数の上限、片方だけの区間の見せ方、tick単位の比較に必要な記録の範囲、そしてスプリント完了直後の org と budget を上書きせず残す記録を評価する。通常ランの面白さの証明ではない。

## 本番境界と検証

現行のリプレイは開始条件の照合に必要な値を持つ（seed・難易度・試練は本体、シナリオ・ラン種別・解放プール・研修方針は開始時の setup フレーム、ruleset は v2 以降）。研修方針の欠落は空配列として照合する。旧v1と開始時の setup を欠く記録は比較不能として示す。org と budget は結果画面の後続操作で置き換わるため、境界比較には使わない。tick単位の同時刻ゴーストはスプリント中の記録がなく、対象外。リプレイ一覧（`src/ui/ReplayListScreen.tsx`）からの2件選択、表のUI、`src/ui/OrgTrendHistory.tsx` との重複整理は別Issueに分割する。リプレイ保存・共有・正規化は変更しない。

Node 24で対象ユニット（実際の `ReplayBlob` の照合を含む）、型、lint、format:checkを検証。UI/Pixi変更なし。E2Eとgalleryは対象外。
