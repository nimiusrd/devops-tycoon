# RI-274 一台で投資と現場を分担する協力プレイ

対象: [Issue #670](https://github.com/nimiusrd/devops-tycoon/issues/670)。基準 main `800199c6`。2026-11-18 JST。

**判断: 再試作。** 実RunEngineの一所有者、役割別の操作、明示的な引渡し、無消費拒否、自然な完走とRNG位置付きJSON再開はAPIで検証した。二人での人間プレイ、会話量、判断の増加、操作説明の理解は未評価。画面を持たない固定ケースの試作であり、本番採用・Issue完了とは扱わない。

## 仮説と今回の境界

投資担当が次のスプリントの編成・予算を決め、現場担当が残された集中力と組織体力で出荷する。同じ資源を共有するため、投資を使い切るか温存するか、カードや介入の消耗を受け入れるかを相談する余地がある、という仮説を置く。

今回追加する規則は、役割ごとの許可操作とsetupでの予約1件だけ。通常の固定トラック、組織レバーの価格/効果、初期空デッキ、カード発動、インフラ課金、イベント、四半期目標、勝敗とWinType自動判定は既存実装を使う。架空の終端・スコア・維持費は追加しない。予約は数スプリント後に完成する設備ではなく、**次のsetup引渡し直前まで実行を保留する指示**である。setupの間は時間が流れないため、予約の有無から時間待ちの面白さは評価できない。

通常save/meta/reward/replay/storage、GameHandle、タブ所有権、通常UIには接続しない。#531は既に完了しているが、その複数タブ保護を緩めたり協力機能として再利用したりしない。別端末/同時タブ/ネット対戦、本人認証、ショップ購入、チーム増設、自由なシナリオ設定は今回の対象外。

## 一所有者と進行契約

`createRoleHandoff(seed)`はnormal・試練なし・defaultで一度だけ開始し、クロージャ内部のRunEngine一つを所有する。公開するのは`view / dispatch / history / save`だけで、可変engine、hydrate、再開始、報酬付与の入口は返さない。view、応答、履歴は深く複製する。独立したセッションを複数作ることはできるが、共有保存を持たず、同じランをタブ間共有するAPIではない。

すべての操作に`requestId / revision / role / phase / action`を要求する。成功時だけrevisionと履歴を増やし、成功済みrequest IDをラン中保持する。同じフェーズへ戻っても古いrevisionは拒否する。未知フィールド・ID・矛盾した選択・担当違い・予約超過・二重引渡し・重複カード・集中力不足・クールダウン・完了後操作は資源、RNG、入力ログを消費しない。拒否したrequest IDは消費しない。これは同一端末の誤操作/古い表示への防御であり、悪意ある利用者の認証ではない。

| フェーズ | 担当 | 許可操作と進行 |
| --- | --- | --- |
| setup | 投資 | 配置、coding担当へのAI配布、3種のレバー即時適用/予約/取消。handoffで予約を適用して実スプリントを開始、現場へ渡す |
| sprint | 現場 | 手札発動/交換、既存8介入の自動対象選択、1〜5000msの進行。自然終了を待つ |
| result（返却前） | 現場 | handoffだけ。残資源と結果を確認して投資へ返す。engine自体は進めない |
| result（返却後） | 投資 | ackResultでdraftまたはquarterReviewへ |
| draft | 投資 | 候補カード取得またはnullでスキップ |
| evolution | 投資 | 有効ノードの解放、finishEvolution |
| beat | 投資 | 実イベントの有効な選択番号。判定イベントは0のみ |
| shop | 投資 | leaveShop。購入なしでsetupへ戻れる |
| rest | 投資 | heal / repayでsetupへ |
| recruit | 投資 | hire / skip。既存の採用費用・見送り士気ペナルティを適用 |
| quarterReview | 投資 | missed_adjustableなら候補の目標修正、その他はnullで既存の勝敗確定 |
| won / lost | 操作なし | 既存の自然終端。すべて無消費拒否 |

開始時課金でlostになった場合も実RunEngineの終端をそのまま返す。途中敗北から架空のresultを作らない。現場は自動的に投資へ戻らず、resultでの明示返却が必要。中間フェーズは投資が持ち、手順を止めない。

## 引渡し表示データと効果時点

`view.resources`は現金予算、予約予算、利用可能予算、集中力、シニアHP、士気、負債、AI依存度を持つ。`view.state`には実結果、ロスター、手札、信頼、目標等も含む。集中力はresult等に残る直前スプリントの値も保持し、操作可能性はphaseとallowedで判別する。

予約対象は`standardize`（全社30）、`prSizeLimit`（稼働部門10）、`teamAiThrottle`（稼働チーム5）。対象は現在の実チームから導出し、存在しない部署/チームを指定できない。拡張チームや士気ペナルティを持つレバーは公開しない。予算0を予約だけで作らないよう、価格より大きい残予算を要求する試作上の制限を置く。

- 予約時: 現金/組織は不変。利用可能予算だけを拘束する。他の即時投資が予約分を使うことはできない。取消は無料。
- setup引渡し: 実`applyOrgLever`が一度だけ価格を払い効果を適用し、その後`beginSetupSprint`を呼ぶ。開始時の既存インフラ費は別途実engineが課金する。
- 即時レバー: そのsetupで組織へ適用される。スプリント開始時の編成係数と共に次の盤面へ入る。
- 獲得カード: draftでは取得だけ。次の手札に配られ、現場のplay成功時に集中力と効果が発生する。永続加算系も既存engineの適用規則に従う。
- 休息repay/イベント: 既存`pendingSprintModifiers`を`nextSprintModifiers`として表示し、次の開始時に一度消費する。

履歴receiptには操作、前後の役割/フェーズ/資源、実行した予約IDを残す。g1のstandardize予約テストでは現金45・予約30・利用可能15のまま組織が不変で、引渡し後は直接同じレバーを適用したRunEngineと全状態が一致する。比較JSONには最初の引渡し前後とラン全体の投資費・現場集中力消費を記録する。画面の編集/完成UIでの説明理解を確認した記録ではない。

## 再現条件と固定比較

全ケースでnormal、試練なし、default、初期予算45、初期空デッキ、同じseedごとの初期組織/ロスターを使用する。3 seed × 4条件。投資だけをなし→初回setupでteamAiThrottle予約→prSizeLimit予約に変える比較と、無投資のカード使用だけをOFFにする比較。係数・資源・手動スコアの改変はない。

## 保存・再開・上限

専用JSON version 1はseed、成功入力列、現在の役割/予約と`exportCounterfactualFrame`（終端は`exportReplayFrame`）を含む。スプリント本体、tick、端数時間、RNG消費位置を落とさない。再開は一つのengineを初期化して成功入力を再生し、保存checkpointを完全照合する。任意frameをhydrateしないため、不正な資源/タスク/RNGを注入できない。キー順の差は許容し、未知フィールド・矛盾・重複入力は拒否する。これは同じコード/コンテンツに限る実験契約で、通常保存/リプレイの互換を保証しない。将来の変更で照合できなければ拒否する。

成功操作・履歴・request IDは2048件、予約1件、seed80文字、ID64文字、1進行5000ms、入力JSON200万文字、深さ48、検査ノード25万、配列5000件、文字列16000文字を上限とする。操作に自由なタスク/履歴/カード/初期資源を渡す入口はなく、盤面は固定normal・実イベントから生成する。読込frameの配列にも5000件の上限を適用した後、実入力列との一致を検査する。上限到達は追加操作を拒否するだけで架空のゲーム終了へ変換しない。検証ケースの最大成功操作は588件で上限内。

## 検証と次の判断条件

対象unitで、役割/フェーズ/revision/ID、編成/AI、予約の二重作成/取消/予算拘束/効果時点、実カード/介入重複、未知選択、可変参照の遮断、3 seedの同入力再生・途中RNG再開・各到達フェーズ再開、完了後操作、JSON改ざんと上限を確認する。スプリント途中の端数時間も含む。実到達のshop/rest/recruit/quarterReviewを通し、lost/wonをどちらも確認した。通常storageへの書込みや報酬付与コードは存在しない。
