### RI-77 AI 導入が既定 ON で、既定のまま進むのが有利

初期ロスターは `aiAssigned: arch.preferred === 'coding'`（`src/sim/member/roster.ts:135`）でコーダーに最初から AI が配られており、既定プレイの AI 利用率は 81.8%、最終 AI 依存度は 100。明示的な「AI 全配布」方針（`aiFullBet`）は既定とほぼ同じ結果になる。

**AI の効き方は実務感覚と逆向きである。** AI 配布だけを外した統制条件 `noAiCtl`（`skilledNoHire` から `setMemberAi` だけを false にしたもの）と比べると、勝率は 6/40→2/40 と下がる一方、カード・介入・進化を揃えた比較の結果は依然として単純な因果を示さない。`aiFullBet` は 2/40、`noAi` は 3/40 で、方針間の差は小標本に留まる。敗因の構成と出荷の差も難易度・スプリント位置で揺れるため、AI導入の優劣は未確定として追跡する（RI-68 が絡む可能性がある）。

なおこの統制条件にも残差がある。`spec.ai` が変えるのはロスターの `aiAssigned` だけで、そこから決まるのは intake の AI 採用率（`aiAdoptionShare`）である。`org.aiEnabled` は true のままなので、`assignTask` 介入が `defaultAssignee` 経由で個別タスクを AI へ回す経路が残る（実測で492スプリント中5件、最大4%）。残差は小さく上の結論を動かさないが、「AI を完全に断つ」条件を測るには `org.aiEnabled` 側も落とす別の統制が要る。

AI の on/off が状態へ伝播していること自体は正しい（AI 利用率 0%、最終 AI 依存度 100→47.0）。問題は、「AI を入れると出荷が増え、その代償として別の何かが悪化する」という因果が出荷の増減として体感できないことである。なお以前この節は「AI 配布を全解除すると出荷 334.5→291.4」を因果の根拠にしていたが、これは統制条件ではない `noAi`（AI に加えて andon・進化ブランチ・ドラフト選好・採用まで違う）の値で、しかも現在は向きが逆である。

選択の入口は存在する。新規ランは第1スプリント前に必ず `SetupScreen`（見出し「編成 — スプリント開始前に配置とAIを決める」）を通り、`FormationScreen.tsx:172` の「🤖 AI配布中」ボタンから `setMemberAi` で解除できる。したがって課題は場の不在ではなく次の3点である。(1) 既定が ON で、選び直す動機が薄い（`aiFullBet` 2/40・`skilledNoHire` 6/40）。(2) 解除の勝率差は現行コホートでは `noAiCtl` 2/40、`noAi` 3/40 で、`skilledNoHire` 6/40を上回らない。**ただし当初ここに書いていた「`budgetExhausted` 敗北の過半を占める。AI で稼げないぶん予算を維持できず」という説明は取り下げる**（訂正履歴88）。`budgetExhausted` は現在1,360ラン中0件で、当時の14件はすべてハーネスの統制不足による回避可能な自滅だった。(3) 導入が編成画面の on/off だけで段階が無く、「どこまで広げるか」を四半期を通じて問い直す機会が無い。

受入条件:

- 開始時の既定値が、そのまま進めるだけで有利な状態でなくなる（既定のまま／解除の双方に成立条件がある）。
- AI を入れない選択が、目標未達による敗北へ一直線に繋がらない（別の勝ち筋が成立する）。
- AI の導入度合い（誰に配るか・どこまで広げるか）が、ラン中に複数回問い直される段階的な意思決定になる。
- 開始時 AI の全面撤廃は取らない。`SetupScreen` / `FormationScreen` の既存の編成上の意思決定を重複して作り直さない。
- AI あり／なしの結果差が代表 seed で検証されている（`tests/unit/helpers/aiAdoptionSeeds.ts` の枠組みを利用する）。

### RI-78 スプリント間投資のうち、ショップと休息の選択が結果を変えない — 実装済・ショップ純出荷の受入判定継続

カードと介入は集中力を共有したまま、カード定義へショップ価格と独立した `focusCost`（2〜4）を追加した。強化時は発動費をレベルごとに1減らし、下限1とする。休息は排他的選択を維持し、返済へ次スプリントの手戻り率 -8%、強化へ集中力上限 +2を付与した。休息イベントの出荷 -30%と新しい一時効果は既存 `pendingSprintModifiers` へ合成し、セーブ／hydrate／リプレイのスナップショットで保持する。

`assignTask` の対象省略時は Coding の複雑タスクを優先しつつ、空き枠がある場合は Backlog も自動対象にする。明示ターゲット、WIP上限、AI担当制約は維持した。プレイテストにはカード発動数、ショップ訪問・購入、休息選択、対象あり区間（集中力・クールダウンを除く連続区間）を記録し、同一メタ・難易度・seed・スプリント位置の共通機会だけで次スプリントKPIを比較する処理を追加した。次スプリントへ到達しない終端スプリントも `completed=false` として途中の計測値を保持し、KPI平均だけを完走ペアへ限定する。

### RI-93 子コンテンツの変更で再崩壊する画面レイアウト構造

**高優先度の技術基盤エピック。** RI-69 / RI-70 で確認済みの重なりと狭幅操作性は解消しているが、
スプリント画面全体は `Hud`・`RunBar`・盤面・手札・介入バーを `.app` 直下の1本の Flex 列へ並べ、
盤面を他要素が使った残り高さへ収めている。警告文、効果タグ、担当選択などの内容量が増えるたび、
`src/styles.css` 冒頭の `app-sprint-layout` へ `overflow`・固定値・メディアクエリを追加して補正しており、
変更が別の viewport / 表示状態で盤面縮小・重なり・情報欠落を再発させる。

根本原因は次の4点である。

- 画面全体の配置責務を持つレイアウトコンポーネントが無く、子コンポーネントの内容量が盤面寸法を直接変える。
- 全画面のスタイルが6,000行超の `src/styles.css` に集中し、離れたセレクタとソース順による上書きが暗黙の契約になっている。
- 860pxブレークポイント、DOM/Pixiの寸法・配色などが CSS / React / Pixi 間で手動同期されている。
- 通常CIのレイアウト契約は 1440×900 と 390×844 の初期スプリントに限られ、長文・警告・最大アイテム数・武装状態・短い画面などの組合せを検知しない。Pixi視覚回帰も既定CIではスキップされる。

受入条件:

- `SprintLayout` 相当の画面レイアウト所有者を設け、HUD・ステータス・盤面・操作領域を名前付きスロットとして配置する。通常高さでは盤面専用領域を確保し、収まらない高さでは明示的なスクロール構成へ切り替える。
- DOM/Pixi共通の `AspectStage` 相当へアスペクト比・contain・ResizeObserver責務を集約し、即時親要素を暗黙に参照して幅だけを書き換える構造を廃止する。
- 画面／コンポーネント単位のスタイル境界（CSS Modules または同等のスコープ）とレイアウトプリミティブを導入し、`.app.app-sprint-layout .子要素` の横断上書きやファイル末尾のソース順依存を解消する。
- ブレークポイント、盤面設計寸法、DOM/Pixi間で共有する主要寸法・色の正本を一元化し、「styles.css と同値」という手動同期を残さない。
- 320×568、390×844、768×1024、1024×768、1440×900 以上の代表 viewport と、HUD展開、最長警告、最大レリック、長い効果タグ、担当選択、結果オーバーレイを組み合わせたレイアウト契約E2Eを通常CIで実行する。
- 契約E2Eで横スクロール無し、主要領域の非交差、盤面比率・最低寸法、操作バー到達性を検証し、DOM/Pixi双方の合成画面を少数の視覚回帰で固定する。
- 既存のRI-69 / RI-70 E2E、通常E2E、`npm run lint`、`npm run format:check` が成功する。

分割順:

1. [RI-94](#ri-94-レイアウト契約e2eの状態fixtureとviewportマトリクス) で現状を契約テストとして固定する。
2. [RI-95](#ri-95-スプリント画面シェルの名前付きスロット化) で画面全体の配置責務を独立させる。
