# ゲーム案の試作ライフサイクル

ゲーム案を最小の検証可能な試作にし、判断材料を残して次の状態へ進める。試作PRがマージされたことを本番採用の根拠にしない。

## 作業の進め方

1. 親Issue・個別Issue・関連PR・既存実装・`docs/prototypes/` を確認し、記録と現在のコードを照合する。GitHubの状態は本文の古い集計を前提にせず、最新状態を取得する。開始前に `git status --short` を確認し、無関係な変更を保護する。
2. プレイヤー価値、検証する判断、選択肢ごとの利益と代償、結果が変わる条件を明記する。既存ルールの改善と新しいルールの追加を区別し、他Issueとの重複や依存を調べる。
3. その判断に必要な最小の試作を選ぶ。純粋なルール比較は通常ランから隔離してよい。面白さ、操作の分かりやすさ、継続意欲を確かめる場合は、実際に遊べる文脈で人間のプレイ評価を行う。見せかけの統合や固定スコアだけで、プレイヤー価値を証明したと扱わない。
4. 比較条件・seed・資源・係数・入力列・結果を保存する。乱数が関係する判断には、複数seedや係数感度の確認を使う。固定戦略同士の計算はその前提内の比較として報告し、適応的なプレイヤー行動や楽しさの証拠へ読み替えない。プレイ評価をしていない場合は明記する。
5. 各Issueに採否と根拠、未解決点、次の判断条件を記録し、状態を選ぶ。

## 採否後の扱い

- **採用:** 本番実装の範囲を分割し、既存仕様との整合、保存・再開・リプレイ・rulesetへの影響、受入条件を決める。採用判断と試作マージを混同しない。
- **再試作:** 次に解く不確実性を一つ以上具体化し、終了条件を置く。同じ条件の比較を根拠なく繰り返さない。
- **保留:** 待つ依存条件と、再評価するきっかけをIssueに書く。時期や担当が決められるなら残し、期限のない保留にしない。
- **見送り:** 試作用のコードをリポジトリから削除する。`src/prototypes/` の実装・テスト・比較スクリプトに加え、試作用ルート、UI、設定、依存があれば参照を調べて片付ける。採用済み機能と共有するコードは分離し、使われている部分を誤って削除しない。Issueまたは `docs/prototypes/` には仮説、比較条件、結果、見送り理由、再検討条件だけを残す。過去の実装はGit履歴から確認できる。

再評価条件が残る場合も、現在の本番採用を見送った試作用コードを常設しない。条件が満たされた時点で、最新の本番状態から必要な試作を作り直す。

## 完了確認

- Issueの採否とコード・文書の状態が一致している。
- 見送り時は試作用コードへの参照が残っておらず、比較結果と判断根拠は追跡できる。
- 採用時は試作の数値をそのまま本番値とせず、本番統合の設計と受入条件が明記されている。
- UIを変更する場合は、先に [`devops-tycoon-design-system`](../devops-tycoon-design-system/SKILL.md) と `docs/design-system.md` を読み、検証マトリクスに従う。
- コマンド実行、保存形式、lint/format、PR前確認はリポジトリの `AGENTS.md` に従う。
- Issue・PRなど外部サービスへの変更は、ユーザーがその変更を依頼した範囲で行う。
