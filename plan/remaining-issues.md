### RI-116 バランスルールセットの版と指紋

状態: 完了。`BALANCE_RULESET_VERSION` を `1` から始め、レジストリ実行値と既存コンテンツのゲーム影響フィールドから決定論的指紋を算出する。表示・検証専用メタデータと体験目標帯は指紋から除外し、オブジェクトキー順だけを正規化して抽選配列順は保持する。ブラウザと Node で同じ SHA-256 になるよう純 TypeScript で計算し、版の更新規則と指紋対象を生成パラメータ表へ表示する。セーブ／リプレイ／デイリーへの記録は後続 RI で扱う。

手動更新する`BALANCE_RULESET_VERSION`と、バランスレジストリおよびRI-115のコンテンツカタログから決定論的指紋を追加する。レジストリは安定IDとゲームが参照する実行値だけへ射影し、表示・検証専用メタデータを入力から除外する。意味のないオブジェクトキー順だけを正規化し、抽選・評価に使う配列順は指紋へ保持する。指紋計算はブラウザとNodeの双方で同じ結果になる方式にする。

受入条件:

- `BALANCE_RULESET_VERSION`を`1`から始める単調増加整数として追加し、結果へ影響する値、式、分岐、丸め、乱数消費順、コンテンツ、配列順、指紋方式の変更で直前の版から1増やす規則を文書とテストで固定する。
- 意味を持たないオブジェクトキー順の違いでは指紋が変わらず、ゲーム結果へ影響する値・ID・重み・配列順の変更では指紋が変わる。
- `label`、`description`、`unit`、`allowedRange`、`tags`、`derived`など表示・検証専用メタデータだけの変更では指紋が変わらない。
- 検証メタデータ、表示専用値、テスト条件、生成整形だけの変更では版を増やさず、版の更新規則と指紋対象を生成文書へ表示する。
- seedや入力列を指紋へ混ぜず、ルールセット識別と実行識別を分離する。

- 旧日付キーのデイリー記録を「ルールセット不明」として保持し、既存メタ進行を失わない。

- 曲線生成のためにゲーム式を複製せず、モデル変更を同じPRへ含めない。

### RI-124 メタ進行・デイリー条件パラメータの移行

`src/state/meta.ts`のデイリー難易度・試練、優先カード上限、ラン報酬係数など、ゲーム結果や進行へ影響する値を`balance/meta.ts`へ移す。永続化スキーマの履歴値と表示専用値は対象外として理由を残す。

受入条件:

- メタ進行・デイリー条件の調整値を安定IDから参照し、RI-116の指紋入力へ含める。
- デイリー条件、アンロック、ラン報酬、優先カード上限の境界と代表seed結果が移行前後で一致する。
- 旧メタ進行データの互換処理と値調整を同じPRへ含めず、既存exportが必要な場合は互換別名を維持する。

### RI-133 途中セーブ・リプレイのファイル共有

開始レシピ（RI-127）はタイトルの開始条件だけを版付きJSONで受け渡す。途中セーブ（`RunSave`）と完走リプレイ（`ReplayBlob`）はIndexedDBに留まり、ファイルの書き出し・読み込みがない。外部APIや共有バックエンドは対象外のまま、ローカル完結のファイル共有を追加する。保存スキーマへルールセットを足すRI-117 / RI-118と衝突しやすいため、それらの直後、または同一スキーマ更新に合わせる。

受入条件:

- タイトルから現行の途中セーブをJSONファイルとして保存でき、同じスキーマのファイルを選んで再開できる。メタ進行・完了済みデイリー・他のリプレイは上書きしない。
- リプレイ一覧から選択中リプレイをJSONファイルとして保存でき、ファイルから読み込んで既存上限（`REPLAY_MAX_COUNT`）に従って保持できる。
- 破損、未対応スキーマ、ルールセット不一致（導入後）を開始レシピと同様に理由付きで拒否し、自動削除しない。
- 開始レシピの入出力をセーブ／リプレイへ流用して開始条件以外を混ぜない。ユニットとE2Eで往復・拒否理由を固定する。

### RI-134 AI依存モデルの再設計

現行の`aiDependency`は、AI利用で蓄積した共通Reworkリスクと「AIなしでは工程を維持できない依存」を一つの値へ混ぜている。[probability-model.md §4.5.1](./probability-model.md#451-ai依存度の意味と再設計課題)の候補式は未実装で、`manualCapability`もコードに存在しない。SSoTへの値移動（RI-104）とは別PRとし、移行完了後に式・状態・曲線を変える。着手前に、手作業能力をチーム状態として持つか既存値から導出するか、個人単位へ拡張するかを決める。

受入条件:

- 共有リスク、手作業能力、AI習熟を分け、AI支援あり・なしのリスクを独立して検証できる。
- 詳細モデルと粗粒度モデルで因果方向が一致し、セーブ・リプレイ・診断表示が新しい状態を往復する。
- 候補式の仮係数を本番値として固定せず、Monte Carloと代表曲線で確定した値だけをルールセット更新と一緒に入れる。
- 値移動PRやRI-123の現行曲線生成と式変更を同じPRに含めない。

### RI-135 組織診断ダッシュボードの深掘り

SPEC第23章は、ズーム階層本体に加えて時系列トレンドや部門間比較の深掘りを残している。部門現在値比較（RI-125）と完了四半期の診断・KPI時系列（RI-128）は実装済みで、業界ランキングの他社趨勢は演出値のままとする判断済みである。残る深掘り（チーム単位比較、指標切替、部門トレンドの追加系列など）は複数の有効な選択肢があり、選択で変更範囲が変わるため、範囲を決めてから実装する。

受入条件:

- 深掘りの対象（比較単位、指標、操作）と非対象（他社趨勢の実履歴化、外部ダッシュボード）を本項目または確定判断へ書き、実装PRはそれに従う。
- 全社マップの既存比較表・四半期トレンドを壊さず、sim・保存・勝敗を変えない表示追加に留める。
- 表示は状態を読むだけで、DOM / Pixiの両方で主要viewportのレイアウト契約を維持する。

### 第23章の残拡張（旧RI-34）

第23章の残拡張は RI-34 から次の個別IDへ切り出した。開始レシピ共有（RI-127）、診断・KPI時系列（RI-128）、四半期レビューのOKRテンプレート（RI-129）、ステークホルダー別交渉（RI-130）、複数四半期ロードマップ（RI-131）は完了。外部API・共有バックエンド、社内LT／経営プレゼンモードは対象外のままとする。途中セーブやリプレイのファイル共有は[RI-133](#ri-133-途中セーブリプレイのファイル共有)、組織診断ダッシュボードの深掘りは[RI-135](#ri-135-組織診断ダッシュボードの深掘り)で追跡する。

## 2. 確定した判断

- Zustandは要件ではない。`RunEngine`を状態の正本とし、決定論、保存、リプレイ、UI同期を満たせばよい。
- 巨大組織は表示用の合成チームではなく、独立状態を持つ複数チームとして扱う。
- カード、レリック、進化ノードのSPEC内の具体例は方向性であり、実装データとの差を許容する。
- カードはラン外のコレクション画面で一覧・解放状況を確認できるようにする。
- 診断・KPI時系列（RI-128）は四半期境界でセーブへ明示永続化し、業界ランキングの自社趨勢だけ実履歴化する。他社趨勢は演出値のままとする。
- ステークホルダー別交渉（RI-130）は既存7種へ交渉相手と、信頼差以外の提示条件（予算・次期目標・組織状態・次期予算上限・次四半期物理）を足す。対話ツリーや新しい GoalAdjustmentId は追加せず、`availableAdjustments()` の除外条件と効果量は変えない。
- 複数四半期ロードマップ（RI-131）は表示専用の見通しとする。sim・保存・勝敗は変えず、未達で継続可能な四半期レビューに Q+1 / Q+2 を出す。物理キャリーは次の1四半期だけのまま。拘束力ある Q+2/Q+3 約束は対象外。

## 4. バックログ運用

- IDは`RI-NN`の連番とし、欠番を再利用しない。
- ミューテーション改善はエピック`RI-{N}`（再ベースラインごと）と実装単位`RI-{N}-{GROUP}{SEQ}`（1PR = 1 GitHub Issue）に分ける。採番・進捗の正本はGitHub Issueとし、本ファイルへ番号予約や状態台帳を置かない。方針は[mutation-remediation.md](./mutation-remediation.md)を参照する。
- 状態は`未着手`、`進行中`、`保留（要判断）`、`完了`を使う。
- 1項目は原則1PRで完了できる大きさに分割する。エピックは受入条件と分割順を記載する。
- 完了時は個別節を削除し、上の完了要約と[spec-mapping.md](./spec-mapping.md)を更新する。
