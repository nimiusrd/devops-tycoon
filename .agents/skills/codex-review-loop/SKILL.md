# Codex レビュー依頼と返信の代行

コード修正・検証・CI 対応そのものは通常どおりエージェント判断で進めてよい。
このスキルが固定するのは、これまでユーザーが手動で繰り返していた次の操作だけである。

1. PR への `@codex review` 投稿
2. 各レビュースレッドへのユーザー文体の返信（と resolve）
3. 指摘対応後の再依頼
4. マージせず merge-ready で止めること

## 1. Codex レビューを依頼する

PR の **issue コメント** として、次の一文だけを投稿する。

```text
@codex review
```

- 余分な文言・チェックリスト・署名を付けない。
- 投稿タイミング:
  - 実装が終わり、最初に Codex を回すとき
  - 指摘を直して push したあと、再度 Codex を回すとき
- 同じ HEAD に対して連投しない。新しい push のあとなら再投稿してよい。
- Draft の Ready 化はユーザーが明示したときだけ行う。

```bash
gh pr comment <PR> --body '@codex review'
```

## 2. スレッド返信はユーザーの文体で行う

指摘へのコード対応が済んだら（または dismiss する判断ができたら）、スレッドへエージェントが返信する。
文体はユーザー（`nimiusrd`）の既存返信に合わせる。

### 書き方

- 先頭は `対応済み。`
- dismiss や方針変更を含むときだけ `対応済み（dismiss + 再調整）。` のように括弧で補足する
- 続けて、何をしたか／なぜ dismiss かを短く事実で書く（記号名・数値・検証結果など）
- 「ご指摘ありがとうございます」「おっしゃる通り」などの前置きは書かない
- 「対応しました。」は使わない

例:

```text
対応済み。`stateAware` にはラン累積の `totals.reviewQueuePeak` ではなく直近スプリントの `reviewQueueMax` を渡し、解放のたびに既解放ブランチも見て順位を見直すようにしました。
```

```text
対応済み（dismiss + 再調整）。指摘の前提は現行 `main` では再現せず、勝率崩壊の主因をこの PR の変更だけに帰属できない状態です。先端コストは再配分済みです。
```

### 手順

1. 修正が必要な指摘は **push 後**に返信する（返信だけで直したことにしない）
2. 対象スレッドの先頭コメントへ reply する（取り違えない）
3. 返信後にそのスレッドを resolve する
4. 返信はスレッドごとに行い、内容とその指摘を対応付ける

コマンド雛形は [reference.md](reference.md)。

## 3. ループの止め方

未解決の Codex 指摘が無く、CI も問題なければ merge-ready として報告して止める。
**ユーザーが明示しない限りマージしない。**
