# RI-288: 勝ち方別の短い結末（#684）

## 判断と最小実装

プレイヤーは、会社をどう終えたかを振り返り、既存の結果詳細を確認して次のランへ進む。既存の勝利種別ラベル・説明・称号・組織タイプ診断は維持し、その直後に短い結末と静的な記録欄を添える。

現行 `WinType` から `happiness`（現場幸福勝利）と `chaos`（カオス勝利）を選ぶ。前者は決着時の士気・体力、後者は出荷と障害の積み重ねを振り返るため、2種類でも焦点の差を理解しやすい。選択は結果フレームの `status === 'won'` と保存済み `winType` だけで行い、現行の `evaluateWinType` を呼ばない。対象外・種別なし・敗北には結末欄を追加しない。

| 結末 | 利益 | 代償・限界 |
| --- | --- | --- |
| 出荷の先に、現場の余力 | 出荷の後に残った現場の力へ視線を移す | 決着時の残量だけでは、全期間に人を守ったことや人物の感情は分からない |
| 障害も刻んだ、出荷の記録 | 出荷の数字に障害・消耗の記録を並べて振り返る | 障害が出荷を生んだという因果や、消耗の全履歴は分からない |

## 事実の正本と境界

- 出荷は当該結果フレームの `totals.delivered`、障害は `totals.incidents`。リプレイ一覧の outcome 集計や他フレームを参照しない。
- 士気は `org.morale`、シニア体力は `org.seniorHp`。既存の残量表示と同じ整数・0〜100の表示範囲で示す。欠落・非有限値は「記録なし」とし、0や現在の初期値で補完しない。
- 診断は既存の `state.diagnosis` 表示をそのまま使う。リプレイの summary/outcome 診断へ置換せず、結末から追加の診断を導出しない。
- 結末文は振り返りへの誘いであり、未記録の顧客、人物、全期間の安全性・感情・因果を追加しない。
- 勝敗、報酬、メタ解放、称号コレクション、保存形式、ruleset、シミュレーションは変更しない。旧記録から現在の勝利条件への適合も推定しない。
- `VisualIcon` の `morale` / `fire` と既存 semantic token（panel / line / text / text-dim / lav）を使う。新しい色・共有寸法・素材・盤面は追加しない。結末にアニメーションや操作待ちを設けず、通常/reduced motionとも同じ情報へ到達できる。

## 再現条件・検証

ランの戦略比較ではなく、決着直前の固定表示fixtureによる比較。共通 seed は `ri288-ending`、easy、試練なし、通常ランの初期資源・デッキを出発点に、公開セーブ取り込みから四半期レビューを承認する。初期状態と入力列は `tests/e2e/run-endings.spec.ts` の `finishFixture` を正本とする。係数・乱数・報酬式は変更しない。

両fixture共通: 出荷1234、障害35、延焼2、done/completed各100、AI補助/手戻り0、Reviewピーク3、品質50、documentation20、testCoverage30、重介入使用あり。happiness は security55・士気92・体力88、chaos は security20・士気43・体力36。保存した `winEvalOrg` は同じ組織値。四半期レビューの達成状態は表示fixtureとして固定しており、通常プレイでの到達可能性の証拠にはしない。

入力列: 新規ラン開始 → 一時停止 → setupセーブを取得 → 固定した決着直前のセーブを取り込み → 再開 → 四半期レビュー承認 → 初見結果 → タイトル → リロード → 保存リプレイの結果再閲覧 → タイトル → v1旧記録取り込み → 結果再閲覧 → タイトル。

同じ結果の初見/保存後再閲覧で結末・診断が一致することを確認する。旧v1ではsnapshotを除き、シニア体力を欠落させ、summary診断と結果フレーム診断を異なる値にして、補完せずフレーム側の記録を示すことを確認する。純粋表示モデルのユニットでもJSON保存/再生一致、現行閾値を満たさない保存済み勝利種別の維持、入力を変更しないことを検証する。

対象画面は `RunResultScreen` のみ。320×568、390×844、768×1024、1024×768、1440×900 × 2種類を、初見は通常motion、再閲覧/旧記録はreduced motionで確認する。実WebGL構成のE2Eで結末、称号、診断、累計出荷、キーボードでの次の操作、横overflowなしを確認し、各状態のPNGを `test-results/` に保存する。Pixi描画は変更しないため専用視覚回帰、複数画面変更ではないためgalleryは対象外。

## 採否と残条件

最小実装の技術的な整合性を検証し、2種類の結末を実際の結果画面で比較できる状態にする。人間による余韻・理解しやすさ・次は別の会社を作りたいという意欲の評価は未実施。自動検証やPRのマージを、その価値や全勝利種別への拡大採用の証明とは扱わない。

採否は**最小実装を評価可能な状態で取り込み、演出の価値判断と他種別への拡大は保留**。Issue #684 はopenを維持する。次の判断条件は、2種類を初見/再閲覧した人間が会社の終え方の違いを読み取れるか、数値欄の重複が振り返りを妨げないか、次の会社づくりへの動機になるかを確認すること。評価後に文言・配置の再試作、全種別展開、見送りを選ぶ。
