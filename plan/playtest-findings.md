### RI-67 オンボーディングとシニア燃え尽きの断絶（優先度: 高）

Easy でも「素直に遊ぶ」と第1四半期スプリント2でシニア燃え尽き（`seniorBurnout`）敗北する。

同一 seed（`review-hell`・Easy）で、介入と編成を切り分けた統制実験の結果:

| プレイ方針 | 結果 |
| --- | --- |
| D 無介入（自動進行のみ） | Q1 sprint2 で `seniorBurnout` 敗北 |
| A 編成のみ（middle を review へ、介入なし） | それでも Q1 sprint2 で敗北 |
| B 介入のみ（緊急対応＋andon、編成そのまま） | 12スプリント以上を燃え尽きずに継続 |
| C 編成＋介入（B に編成変更を追加） | Q1 sprint2 で敗北 |

敗北条件は `org.seniorHp <= 1`（`src/sim/outcome.ts:57`）で、これはメンバー個別の stamina ではなく
**抽象的なグローバル値**である。`org.seniorHp` の主な減少要因は次の2つ:

- レビュー1件ごとの一律消費 `REVIEW_HP_COST`=1.6（`reviewOne`、`src/sim/sprint.ts:252`）。担当のランク・
  人数に関わらず同額を削る。
- 猶予切れの炎上を受動処理する**自動鎮火** `INCIDENT_HP_COST`=12（`advanceBurning`、`src/sim/sprint.ts:340`。
  リザルトの `シニアHP -12` の主因）。緊急対応（firefight）で先に鎮火すれば `FIREFIGHT_HP_COST`=2 で済む。

スプリントは全タスクが Done になるまで進む（`isDrained`、`src/sim/sprint.ts:480`）。実測では第1スプリントは
seed 固定 25 タスクを endTick 46〜71 で完了し、`maxTicks`=1500（`src/sim/scenarios.ts:46`）の打ち切りには
達しない。ただしレビュー**回数**はタスク数固定ではない: 手戻りタスクは Rework 経由で Review へ戻り
（`advanceRework`、`src/sim/sprint.ts:378`）、緊急対応で鎮火したタスクも Review へ戻る（`fire.lane='review'`、
`src/sim/actions.ts:151`）ため、レビュー試行数＝タスク数＋（手戻り・炎上の再レビュー）となり、手戻り率・炎上率に
応じて増減する。したがって**手戻り率**を下げる施策（品質・PR分割・AIスロットル。`reworkProbability` の quality・
`task.split`・aiAssisted・aiDependency 項）は再レビュー回数を減らし、`REVIEW_HP_COST` と炎上判定回数を**間接的に**
減らしうる。ただしこれは「レビュー1件あたりの点火率（`incidentProbability`）」を下げるのとは別で、点火率が参照するのは
testCoverage・`task.aiAssisted`・カード効果のみ（品質値・`task.split` は参照しない）。一方 `org.seniorHp` は
毎 tick `REVIEW_HP_REGEN`=0.7
（炎上中は `BURNING_REGEN_MUL`=0.5 で半減、`src/sim/sprint.ts:474`）で回復し、炎上確率 `incidentProbability` は
レビュー1件ごとに評価され**待ち行列長を入力に取らない**（`src/sim/model/process.ts`）。よって「待ち行列を短くすれば
点火が減る」は成り立たない（当初この所見が編成の待ち行列短縮を生存要因としていた点を、Codex レビューの指摘と
下記実測で訂正）。

第1スプリントの実測（同一 seed、条件別の自動鎮火回数と終了時 `org.seniorHp`）:

| 条件 | endTick | 自動鎮火(−12) | HP終値 |
| --- | --- | --- | --- |
| D 無介入 | 65 | 3 | 42 |
| A 編成のみ | 54 | 3 | 36 |
| 緊急対応のみ | 62 | 1 | 62 |
| B 緊急対応＋andon | 71 | 0 | 74 |
| C 編成＋介入 | 46 | 1 | 55 |

読み取れる実際の要因（直接測定できた範囲）:

- **HP を最も動かすのは自動鎮火（−12）の回数**で、これを直接減らすのが **緊急対応**（−12 になる前に −2 で鎮火。
  ただし鎮火後は Review へ戻り再レビュー1件ぶんの `REVIEW_HP_COST` は掛かる）。緊急対応のみで自動鎮火 3→1、
  HP 42→62 に改善し、これは条件を1つだけ変えた比較として最も確度が高い。andon はレビュー件数を減らすのではなく、
  流入を一時停止（`intake` の早期 return、`src/sim/sprint.ts:183`、通常 30 tick）して**既存キューを捌く猶予**を作り、
  同時炎上を抑えて緊急対応を間に合わせる補助（B で自動鎮火 0）。
- **編成（middle を Review へ）は単一要因ではない**。review 増員（`reviewCapacityMul`）だけでなく Coding 担当が減り、
  `foldFormationEffects`（`src/sim/member/roster.ts:251`）経由で `codingSpeedMul` / `codingSlotBonus` / `aiAdoptionShare`
  と AI 由来の確率補正が次スプリント生成に同時適用される。C（編成＋介入）が B（介入のみ）より早く燃え尽きた事実は
  確かだが、複数因子が連動するため B/C 差を「レビュー速度×回復」等の単一機序に帰属できない。確実に言えるのは、
  **編成変更はシニアHP保護の主手段ではなく（A は無介入と同じく即死）、燃え尽き回避を編成に頼らせるべきでない**こと。
  厳密な寄与分解には Coding 側を統制した比較が要る（RI-66 の統計検証と合わせて後追い）。
- AIスロットルは流入を止めず、新規タスクの `aiAssisted` を false にして AI 由来の手戻り・炎上確率
  （`reworkProbability` / `incidentProbability` の aiAssisted・aiDependency 項）を下げる。上記のとおり手戻り減は
  再レビュー減につながるため、HP 消費・炎上判定の**間接的な**緩和にはなる。

素直プレイが即死する構造は、シニア1人＝唯一のレビュアー（`src/data/members.ts` `STARTER_ARCHETYPES`）で
炎上が起きやすいうえ、チュートリアル（`src/ui/tutorial.ts`）が介入バー・レビュー渋滞・コンボの3点のみで、
**シニア体力（燃え尽き）と、燃え尽きを防ぐ主手段＝炎上を自動鎮火前に緊急対応で鎮火することを教えていない**ため。
Easy は導入難易度（「モダンなプロダクトチーム」）であり、この即死は体験を損なう。

改善方向（いずれか／組み合わせ）:

- チュートリアルに「シニア体力（燃え尽き）」と、それを防ぐ最大手段＝炎上を自動鎮火 −12 になる前に緊急対応で
  −2 鎮火することを追加する。補助として、andon（既存キューを捌く猶予）、AIスロットル（レビュー1件あたりの
  点火率と手戻り率を下げる）、品質・PR分割（手戻り率を下げて再レビューを減らす。点火率自体は下げない）も
  位置づける。編成での review 増員はスループット策であり燃え尽き回避の主手段ではない点を明確にする。
- `org.seniorHp` の収支（`REVIEW_HP_COST` / `INCIDENT_HP_COST` / `REVIEW_HP_REGEN`、`src/sim/model/process.ts` ほか）や、
  Easy 序盤の障害率を見直し、標準的な操作理解のプレイが2スプリントで即死しないようにする。
- 燃え尽きが近いときに盤面・HUD で明確に警告し、対処アクション（緊急対応・andon・スロットル）へ誘導する。

### RI-68 四半期レビュー Delivery KPI のスケール不整合（優先度: 高）

第2四半期レビューで **Delivery 目標20 に対し実績1693（約80倍超過）**、Quality/Morale/TechDebt も
すべて「超過」。目標生成（`src/sim/run/quarterReview.ts` の `deliveryTarget`、概ね1スプリント相当の
`minSprintDelivered` ベース）に対し、判定は四半期累計 `quarterTotals.delivered` を比較しているため、
看板KPIの「出荷ポイント＝勝利条件の進捗」が常に自明達成となり意味を失う。プレイヤーには
「目標20 → 実績1693 超過」が壊れて見える。

改善方向:

- `deliveryTarget` を四半期の実出力スケールに合わせて設定する、
  または判定・表示の単位（1スプリント平均 vs 四半期累計）を一致させる。
- 実際に効いている制約（Morale・Quality・Incident・燃え尽き）が勝敗条件として伝わる表示にする。

### RI-69 スプリント上部操作バーと盤面の重なり（優先度: 中）

デスクトップ幅（1440px、DOM レンダラ `?renderer=dom` で実測）で、上部の操作バー（`通常スプリント /
❚❚ / 1x-2x / 渋滞メーター / 炎上タイマー / COMBO`）が盤面領域の上端と重なり見切れる。1行への詰め込み過多。
DOM 経路の盤面は Pixi キャンバスではなく DOM 要素（`FlowArrows` / `TaskDot`）で描画されるため、これは
レンダラ非依存のヘッダ／盤面コンテナのレイアウト問題として扱う（Pixi レンダラでも別途再現確認する）。
対象: スプリント画面のヘッダ／盤面レイアウト（`src/ui/SprintScreen.tsx` 周辺）。

### RI-70 モバイルのスプリント操作性（優先度: 中）

390px 幅で横スクロール・崩れは無い（`documentElement.scrollWidth === innerWidth`）が、縦積みの
KPIカードの下に盤面とアクションバーが来るため、時限スプリント中に盤面のタスク流動と介入ボタンを
見るのにスクロールが必要。リアルタイム介入ゲームとして操作性が落ちる。
改善方向: 狭幅ではKPIを折り畳み／要約し、盤面＋アクションバーを一画面に収める。

### RI-71 favicon 未設定による 404（優先度: 低）

`index.html` に favicon 宣言が無く `public/` にも実体が無いため、`/favicon.ico → 404` が毎ロード時に
コンソールへ出る（`curl` で 404 を確認）。ブラウザタブのアイコンも空。`<link rel="icon">` の追加と
アイコン配置で解消できる。

## 結論の要約

**成立している基準**:

- **F-5 介入は結果を改善している**。全40ラン（4難易度 × 10seed）での勝利数は
  完全放置 7 → 無介入 9 → 初見相当 15 → 上級者相当 16。介入するほど負ける構造は無い。
- **F-9 敗因ごとに進行速度が明確に違う**。敗北までのスプリント数 p50 は
  `aiDependency` 1 / `seniorBurnout` 2 / `moraleCollapse` 2 / `techDebt` 4 /
  `reviewFreeze` 8 / `reorgRequired` 18 / `budgetExhausted` 19 / `trustExhausted` 24。
- **F-2 第4層は選択が結果を変えている**。目標修正の初回選択別の勝率は
  `cut_scope` 47.7% / `extend_deadline` 50.0% / `quality_pivot` 83.3%。
- **撃ちすぎは損になる**。全介入を毎 tick 撃つ `probe` は 10/40 で、初見相当（15/40）より弱い。

**成立していない基準**:

| 基準 | 未充足の内容 | 対応 |
| --- | --- | --- |
| F-1 | 緊急対応だけを打ち続ける方針が全21方針中で最強（21/40）。複合方針（16/40）を上回る | RI-72 |
| F-2 | 第2層（カード）が勝率を動かさないまま集中力だけ消費する | RI-77 |
| F-4 | スプリントが規定の半分以下。easy は 55% が絶対下限30秒を割る | RI-74 |
| F-7 | 難易度別の勝率が 80% / 41% / 17% / 0% で、初見の目標20%前後に合うのは hard のみ | RI-72 |
| F-8 | Nightmare は 210ラン全敗、うち165ランが第1スプリントの `aiDependency` 敗北 | RI-73 |
| F-10 | 勝利種別が実質2種（`noDamage` 152 / `healthy` 136 / `happiness` 1、残り4種は0件） | RI-75・RI-76 |
| F-12 | ドラフトのマリガンが無い | RI-80 |

**前回（第1回集計）からの主な訂正**: 「介入・カード・採用は投入するほど勝率が下がる」は誤りだった。
ハーネスの進化フェーズ処理に不具合があり、進化ポイントを使い切らないまま集計していたため。
修正後は介入が明確にプラスに働く。詳細は RI-72 に記す。

敗北条件は `org.aiDependency >= 95 && org.aiLiteracy <= 30`（`src/sim/outcome.ts:63-65`）で、
nightmare の初期値 `aiDependencyBase`=55 / `aiLiteracy`=25（`src/data/difficulties.ts`）は
リテラシー側を最初から満たしている。`aiDependency` は AI 割当タスク1件ごとに
`AI_DEP_PER_TASK`=2.2 加算され（`src/sim/sprint.ts:193`）、`taskCountMul`=1.2 のタスク量で
第1スプリント中に 95 へ到達する。

問題は回避不能なことではなく、**回避に必要な方針が事前知識を要し、外すと第1スプリントで終わる**こと。
初手で終わるため「負けて学ぶ」が成立しない。

依存度を下げる手段は既に存在する（カード `ai-guideline` の `aiDependencyAdd: -10`、
レバー `aiGuideline` / `teamAiThrottle` の `aiDependencyDelta: -10`、`aiThrottleDept` の -8）。
一方で AI を抑えない方針の最終依存度は easy 94.9〜100 / normal 99〜100 / hard 99.6〜100 /
nightmare 100 と、**全難易度で上限に張り付く**。したがって不足しているのは手段の有無ではなく、
既存手段の効果量・入手機会・発見性である。

### RI-74 スプリントが規定の半分以下で、難易度が低いほど短い（優先度: 高 / F-4・第3.1）

1x 換算の通常スプリント長（840ラン・5,111スプリント）:

| 難易度 | n | p10 | p50 | p90 | 30秒未満 | 60秒未満 |
| --- | --- | --- | --- | --- | --- | --- |
| easy | 1518 | 10.9秒 | **27.2秒** | 51.7秒 | **55.1%** | 95.1% |
| normal | 1832 | 17.0秒 | **37.4秒** | 63.2秒 | 33.8% | 86.5% |
| hard | 1463 | 27.2秒 | 46.2秒 | 80.9秒 | 14.1% | 70.8% |
| nightmare | 298 | 57.8秒 | 100.0秒 | 152.3秒 | 0.7% | 13.1% |

ボススプリント（規定 90〜180秒）の p50 は easy 36.7秒 / normal 46.9秒 / hard 59.8秒 /
nightmare 81.6秒で、**全難易度が規定下限を下回る**。

第3.1 の規定は「通常60〜120秒・最短でも30秒」だが、**初見が最初に触れる easy が最も短く、
半数以上が絶対下限の30秒すら割る**。p10 は10.9秒で、盤面を見る前に終わるスプリントが常態化している。
F-4 の「ゆっくり流れる時間 + 締め切り」と真逆になっている。

既存のペーシング回帰テスト（`tests/unit/sprintTempo.test.ts`）は、無介入経路
（`collectSprintTicks` はカードも介入も発動せず `step` だけで進める）で通常スプリントの
絶対下限・p50・p90 を既に検査している。検知できていないのは**難易度の範囲**で、対象は normal のみ。
ボスも上限（180秒）しか検査しておらず、下限（90秒）は未検査。

### RI-75 勝利種別が実質2種で、最も受動的なプレイが最上位勝利を取る（優先度: 高 / F-10）

840ラン中289勝の内訳:

| 勝利種別 | 件数 |
| --- | --- |
| `noDamage`（ノーダメージ勝利） | **152（53%）** |
| `healthy`（健全勝利） | 136（47%） |
| `happiness`（現場幸福勝利） | 1 |
| `aiSuccess` / `management` / `chaos` / `normal` | **0** |

原因は `evaluateWinType`（`src/sim/outcome.ts:103-118`）が**固定の優先順ラダー**である点。
最初の判定が `!usedHeavyActions && totals.spread === 0`（残業・アンドン未使用かつ延焼ゼロ）のため、
**何もしないほど「やり込み枠」のノーダメージ勝利になる**。勝利種別は実質「重アクションを
使ったか」だけで分岐している。

組織診断も同様に偏る（`seniorSacrifice` 448 / `reviewHell` 345 / `documentationKingdom` 20 /
`healthyAcceleration` 18 / `aiOverproduction` 9 / `reworkSpiral` 0）。

F-10 は「ビルドによって目指す勝ち筋が変わること」を要求するが、現状はプレイヤーが勝ち筋を選べず、
結果に対して自動的にラベルが付くだけになっている。

### RI-76 AI 導入が既定 ON で、既定のまま進むのが有利（優先度: 高 / F-1・F-2・F-10）

初期ロスターは `aiAssigned: arch.preferred === 'coding'`（`src/sim/member/roster.ts:135`）で、
**コーダー志向のメンバーには最初から AI が配られている**。既定プレイの AI 利用率は
全難易度で 81〜86%、最終 AI 依存度は 94.9〜100。

- `aiFullBet`（全員に AI 配布）は既定とほぼ同じ結果になる（easy 9/10、AI 利用率 82.4%）。
  **明示的な「AI 全ベット」は既定と区別がつかない**。
- 一方 `noAi`（AI 配布を全解除）は明確に別のゲームになる:

| 指標（easy、スプリント平均） | 既定（`skilled`） | `noAi` |
| --- | --- | --- |
| 出荷 | 334.1 | **165.4** |
| AI 利用率 | 82.3% | 0% |
| 最終 AI 依存度 | 100 | **35.5** |
| 勝率 | 9/10 | **5/10** |

**選択の入口は存在する**。新規ランは第1スプリント前に必ず `SetupScreen`（見出し「編成 —
スプリント開始前に配置とAIを決める」）を通り、各コーダーの「🤖 AI配布中」ボタン
（`FormationScreen.tsx:172`）から `setMemberAi` で解除できる。実測の `noAi` 方針も
この公開 API で成立している。したがって課題は「決める場が無い」ことではなく、次の3点である。

1. **既定が ON で、しかも既定のまま進むのが有利**。解除側（`noAi`）は全難易度合計 8/40 で、
   既定側（`skilled` 16/40）の半分。選び直す動機が無い。
2. **解除側の代償が一方的に大きい**。出荷が半減し、`budgetExhausted` 敗北14件のうち7件が `noAi`。
3. **段階が無い**。導入は編成画面の on/off だけで、「どこまで広げるか」を四半期を通じて
   問い直す機会が無い。SPEC 第19章が想定する「雑に使うと壊れる」の学習が1回の初期設定に圧縮されている。

因果（AI を入れると速いがレビューが詰まりシニアが削れる）自体は正しく効いている。
開始時 AI を全面撤廃するのではなく、既定値の誘導・解除側の代償・導入の段階化を対象にすべきである。

### RI-77 カードが集中力だけを消費し、勝率を動かさない（優先度: 高 / F-2・F-4）

**「介入すべき状況が盤面に現れない」は誤りだった**（第1回の記述を撤回）。
毎 tick 全8種の介入を試す `probe` 方針で発動可能回数の上限を測ると、
成立回数は easy p50=7 / hard p50=8 / nightmare p50=8 で、いずれも第3.1 の規定
「1スプリントあたり 3〜8回」の帯に**収まっている**。介入の機会自体は足りている。

実プレイ相当の方針が p50=1〜3 に留まる原因は、盤面の対象不足ではなく**集中力の奪い合い**である。
統制条件（カードだけを外す）での試行結果内訳:

| 条件 | 成立 p50 | ok | no-focus（集中力不足） | cooldown | focus 残 |
| --- | --- | --- | --- | --- | --- |
| easy `skilled`（カードあり） | 2 | 155 | **277** | 783 | 3.3/15.6 |
| easy `skilledNoCards` | 3 | **350** | **0** | 1711 | 9.4/16.1 |
| normal `skilled` | 2 | 244 | **1588** | 1818 | 1.9/16.1 |
| normal `skilledNoCards` | 4 | **582** | **0** | 3563 | 8.5/16.5 |
| hard `skilled` | 3 | 299 | **2390** | 2675 | 1.7/16.4 |
| hard `skilledNoCards` | 5 | **476** | **0** | 3456 | 7.6/16.2 |

カードを止めると集中力不足による介入失敗が**完全に消え**、介入成立数が 1.6〜2.4 倍になる。
にもかかわらず**勝率は変わらない**（easy 9/10 → 9/10、normal 4/10 → 5/10、hard 4/10 → 2/10）。

つまりカードは、**集中力という共通資源を大量に消費しながら、結果に寄与していない**。
F-2 が求める「スプリント間の投資が結果を変える」が第2層で成立していない。

なお対象不足（`no-target`）が実在するのは緊急対応だけで、
`onlyFirefight` は easy で ok=60 に対し no-target=521、normal で ok=149 に対し no-target=1061。
炎上の発生頻度に対して撃ちたい回数が多い。

### RI-81 敗北画面に「次の一手」が無い（優先度: 中 / F-6）

`RunResultScreen` が敗北時に示すのは、敗因ラベル＋一文の説明（`LOSE_LABEL`、`src/ui/RunResultScreen.tsx:26-52`）、
組織タイプ診断、メタ進行ポイント。**次のランで何を変えるかは提示されない**。

教訓文（`FAILURE_LESSONS`、`src/sim/diagnosis.ts:64-81`）は存在し、**初回敗北でも表示される**。
ラン終了を検知した `recordIfFinished`（`src/game.ts:401`）が `applyRunReward` 経由で
今回の失敗診断を `collectedDiagnoses` に加えてから画面を更新するため、
`failureInCollection`（`src/ui/RunResultScreen.tsx:81`）は初回敗北時点で true になる。

残る問題は対応範囲と粒度である。

- 教訓は敗因（`LoseReason` 10種）ではなく**組織タイプ診断に紐づいており**、
  かつ `FAILURE_LESSONS` が対応するのは失敗診断4種（`reviewHell` / `aiOverproduction` /
  `reworkSpiral` / `seniorSacrifice`）だけである。実測では診断が `healthyAcceleration`（18件）や
  `documentationKingdom`（20件）のまま終わるランがあり、その場合は教訓が一切出ない。
- 敗因と教訓が独立しているため、`budgetExhausted` / `trustExhausted` / `aiDependency` /
  `reorgRequired`（実測合計218件）で負けても、表示されるのは診断由来の一般論であり、
  **その敗因に対する次の一手にはならない**。
- 教訓は「何を避けるか」の一般論であり、「次のランで最初に変える一手」の粒度にはなっていない。

## 良かった点（回帰させないため記録）

- **介入は結果を改善している**（F-5）。全40ランでの勝利数は 完全放置 7 → 無介入 9 →
  初見相当 15 → 上級者相当 16。加えて**撃ちすぎは損**（全介入を毎 tick 撃つ `probe` は 10/40）。
  「無介入でもそこそこ回るが、丁寧に介入した方が良く、乱打は損」という関係は成立している。
- **敗因ごとの進行速度が明確に違う**（F-9 の中心要件）。敗北までのスプリント数 p50 は
  1〜24 スプリントの範囲に分かれており、`seniorBurnout` の急死と `trustExhausted` の
  じり貧はプレイ感として別物になっている。
- **目標修正の選択が結果を変える**（F-2 第4層）。初回選択別の勝率は `cut_scope` 47.7%（n=260）/
  `extend_deadline` 50.0%（n=12）/ `quality_pivot` 83.3%（n=12）で、到達四半期も 3.0 / 3.2 / 2.2 と異なる。
  ただし `quality_pivot` が突出しており、F-1 の観点では固定の強手になっていないか要確認
  （n=12 と小さいため、提示条件を揃えた追試が必要）。
- **AI の因果は正しく実装されている**。AI 配布を切ると出荷が半減し（334→165）、
  最終 AI 依存度が 100→35.5 になる。トレードオフ自体は生きている（RI-76 は既定値と代償の非対称の問題）。
- seed 固定の決定論が完全に効いており、`npm run playtest` は同じ入力に対して常に同じ結果を返す。
  本所見の全数値は同コマンドで再計測できる。

## 計測方法の訂正（第1回集計からの差分）

第1回の集計には次の2つの誤りがあり、本節の数値はいずれも修正後のものである。

1. **進化ポイントを使い切っていなかった**。ハーネスが進化フェーズで解放を1ノードで打ち切っていたため、
   実際のプレイより弱い状態で集計していた。これにより「介入・カード・採用は投入するほど勝率が下がる」
   という誤った結論が出ていた。修正後は介入が明確にプラスに働く。
2. **介入の「発動できなかった理由」を測っていなかった**。方針の閾値による見送りと、
   盤面に対象が無いことを区別できていなかったため、「介入すべき状況が盤面に現れない」と誤って結論していた。
   `probe` 方針で上限を測ると、発動可能回数は規定の 3〜8回帯に収まっている（RI-77）。

あわせて、母数を全難易度で 21方針 × 10seed に揃えたため、
第1回にあった「難易度ごとに方針数が異なる」「重複実行の除外」という但し書きは不要になった。
