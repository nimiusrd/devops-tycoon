# RI-293: 会社ビルドの履歴帳

対象 #689 / 親 #548。結論: **要約と開始変換の契約を採用、本番統合保留**。UIは未作成。人間のプレイ評価は未実施。

## 要約の契約

通常のメタ・リプレイ保存から隔離した純TS試作。`summarizeBuild(replay)` は完走リプレイの末尾キーフレームだけを読む。末尾が `won` / `lost` であり、かつ結果の種類と一致するときだけ要約する。途中の勝敗フレームや、末尾が勝敗でない記録は要約しない。現行メタの所持では置き換えない。

履歴へ保存するのは記録時の比較用定義（`recorded`）であり、`current` / `changed` / `retired` / `unknown` は保存しない。閲覧時に `resolveContentStatus` が現行カタログと照合する。元リプレイが上限で消えても、この記録時定義は要約に残る。

| 項目 | 読む場所 | 記録時の定義との照合 |
| --- | --- | --- |
| カード | 終端の `deck`。定義IDごとの枚数と最大強化レベル | `contentSnapshot.cards` の名前・コスト・集中力・効果・レアリティ・説明を残す。現行に無ければ `retired`、記録が無ければ `unknown`、一致なら `current`、それ以外は `changed`。効果オブジェクトのキー順だけでは `changed` にしない。一覧の名前は記録時を優先 |
| レリック | 終端の `relics` | `contentSnapshot.relics` の名前・効果・パッシブ・説明を残し、カードと同じ4分類 |
| 進化 | 終端の `evolution.unlocked` | 記録時の定義を持たないため `present` / `retired` だけ。これも閲覧時に現行カタログから決める。変更は確かめられない |
| 編成 | 終端の `roster.members`（名前・段階・レベル・トレイト・配置・AI配布） | — |
| 結果・条件 | 本体の seed・難易度・試練・ruleset・結果、ラン開始時の setup フレーム | ruleset を要約に写す |

取得順の年表は終端の状態から推測しない。

## 履歴と元記録

`addBuildHistory` は要約を自己完結した写しとして残し、任意の名前を付ける。空白は詰め、24文字までにする。空なら「seed / 勝利種別」を作り、それも同じ空白正規化と文字数制限を通す。同じリプレイを再登録すると、名前だけを更新する。照合は元リプレイIDに加え、切り離し後も残る履歴ID（`build:` にリプレイIDを付けたもの）で行う。再登録しても参照は戻さない。

履歴は既存リプレイの上限10件とは別に、新しい順で20件まで残す。リプレイが上限で消えたら、`detachRemovedReplays` が元記録への参照（`sourceReplayId`）を `null` にする。要約は残り、壊れた参照は残らない。元のリプレイを後から変えても、保存済みの要約は変わらない。

## 開始への変換

`startFromBuild` は既存の開始レシピ（`src/state/startRecipe.ts`）へ変換できる範囲だけを返す。引き継ぐのは seed・難易度・試練・シナリオ・研修方針（ラン開始時の setup フレームの値）。デッキ・強化レベル・レリック・進化・編成・予算は `notCarried` として明示し、引き継がない。完成ビルドを貸し出す機能にはしない。

| 結果 | 条件 |
| --- | --- |
| `ok` | 開始時の setup がある・ruleset が現行と一致・開始レシピの構造検査と受信側メタの解放検査を通る |
| `no-start-frame` | 開始時の setup を持たない記録 |
| `ruleset-unknown` | 旧v1リプレイ（ruleset なし） |
| `ruleset-mismatch` | 版または指紋が現行と違う |
| `invalid-start` | 未知の難易度・試練・シナリオ・施策、試練や研修方針の重複、研修方針の上限超過（`parseStartRecipe` が拒否） |
| `locked` | 構造は有効で、未解放の難易度・研修方針（`validateStartRecipe` が拒否） |

## 実リプレイでの確認

実エンジン（`RunEngine`、難易度 normal、seed g1、進化を解放する自動プレイ）の完走リプレイで、要約が終端の実状態と一致することをテストで確かめた。この記録は5スプリント完了後に敗北（診断 `seniorSacrifice`）で、カード5種各1枚（AI利用ガイドライン・ドキュメント整備・フィーチャーフラグ・PRサイズ制限・静的解析導入、すべて強化レベル1）、進化「レビュー容量増強」、編成3人（ミドル2人が実装、シニア1人がレビュー）、レリックなし。開始は normal・試練なし・default シナリオ・研修方針なしへ変換できる。テストは実状態との一致を確かめ、カード名などの値は固定しない。以後のバランス変更でテストを壊さない。

要約・履歴・開始変換の契約を採用する。本番統合は保留。次は、リザルトとリプレイ一覧からの登録UI、要約の表示密度、`changed` のカードを示す文言、研修方針を終端のデッキから提案するかどうかを評価する。

## 本番境界と検証

#537 は進行中の会社の現在プロフィールで、本件はランをまたぐ構成の履歴。本番化では履歴の保存先（IndexedDB のストア追加と移行）、完走時の保存トランザクションとの関係、名前入力・一覧・開始のUI（`src/ui/ReplayListScreen.tsx`・`RunResultScreen.tsx`）、進化定義のスナップショット追加を別PRに分割する。今回の試作はリプレイ・メタ・開始レシピの保存とUIを変更しない。

Node 24で対象ユニット（実エンジンの完走リプレイを含む）、型、lint、format:checkを検証。UI/Pixi変更なし。E2Eとgalleryは対象外。
