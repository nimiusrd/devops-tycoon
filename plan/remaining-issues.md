## 1. 現在の課題

### RI-140: 中央「現場」のWebGL演出リッチ化（エピック） — 進行中（RI-141完了）

**難易度: 高。** 現在の `BoardPixiLayer` / `PixiBoardRenderer` はフロー線・タスク粒・
ステーションキャラクターを WebGL で描き、炎上・介入・オーラなどの短時間演出は DOM +
Framer Motion で重ねている。本エピックでは中央のスプリント盤面だけを対象に、状態理解を
強める GPU 演出へ段階的に拡張する。HUD、手札、アクションバー、チュートリアル等の離散 UI
を canvas 化することは対象外とする。

- **プレイヤー価値:** Review の渋滞、手戻り、炎上、介入の因果と緊急度が、粒の流れ・熱・
  光・短時間の反応として即座に読み取れる。画面を派手にするだけで、操作対象や次の一手を
  隠してはならない。
- **受入条件:** `boardScene` 等の純粋な表示モデルを状態→演出の正本にし、WebGL と
  `?renderer=dom` の双方で、状態名・数値・選択可否・操作結果が等価に分かるようにする。
  新しい演出色・共有寸法は `visualTokens.ts` を正本とし、DOM と Pixi で値を複製しない。
  `prefers-reduced-motion` では演出を即時化または抑制しても情報を失わせない。既存の
  ドラッグ操作、WebGL 初期化失敗時の DOM フォールバック、リサイズ時のコンテキスト維持を
  壊さない。
- **難易度が高い理由:** 状態差分からの一回限りの演出計画、Pixi の ticker／深度順／
  スプライトプール、DOM フォールバックとの意味的同等性、5 viewport と実 WebGL の視覚回帰を
  同時に扱う。レンダラ、演出モデル、React 境界、アクセシビリティ、E2E にまたがり、8ファイル
  以上の変更と実ブラウザでの検証を要する。
- **非対象:** ゲーム全 UI の WebGL 化、sim・保存・リプレイの意味変更、WebGL を必須にする変更、
  新しいゲームルールの追加。

分割して、各項目を原則 1 PR で完了させる。

## 2. 確定した判断

- Zustandは要件ではない。`RunEngine`を状態の正本とし、決定論、保存、リプレイ、UI同期を満たせばよい。
- 巨大組織は表示用の合成チームではなく、独立状態を持つ複数チームとして扱う。
- カード、レリック、進化ノードのSPEC内の具体例は方向性であり、実装データとの差を許容する。
- カードはラン外のコレクション画面で一覧・解放状況を確認できるようにする。
- 診断・KPI時系列（RI-128）は四半期境界でセーブへ明示永続化し、業界ランキングの自社趨勢だけ実履歴化する。他社趨勢は演出値のままとする。
- 組織診断ダッシュボードの深掘り（RI-135）は表示専用とし、現在値は部門4指標とチーム7指標を単位・指標タブで切り替える。部門トレンドは既存3系列と四半期ごとの健全度バッジを切り替える。組織順は固定し、sim・保存・勝敗、他社趨勢の実履歴化、外部ダッシュボードは対象外とする。
- ステークホルダー別交渉（RI-130）は既存7種へ交渉相手と、信頼差以外の提示条件（予算・次期目標・組織状態・次期予算上限・次四半期物理）を足す。対話ツリーや新しい GoalAdjustmentId は追加せず、`availableAdjustments()` の除外条件と効果量は変えない。
- 複数四半期ロードマップ（RI-131）は表示専用の見通しとする。sim・保存・勝敗を変えず、未達で継続可能な四半期レビューに Q+1 / Q+2 を出す。物理キャリーは次の1四半期だけのまま。拘束力ある Q+2/Q+3 約束は対象外。
- バランスパラメータSSoT（RI-104）は子課題 RI-105〜124 の完了により親エピックも完了とする。AI依存モデルの意味変更と係数確定はRI-134で完了した。
- RI-134 は`manualCapability`を導入しない。`W`は既存のリテラシー・習熟・ドキュメントから導出し、プレイヤー判断は AI 前提ワークフローの組み込みとする。AI なし実装による能力回復、個人単位への拡張、タスク担当者は対象外とする。係数は64 seedの統制Monte Carloと既定コホートで確定し、ルールセットv4へ反映した。
- F-9 の定性的な判定基準と RI-132 の合否ゲートは維持する。全合法手列の完全計測は、状態空間が組合せ的に増大し費用対効果が合わないため RI-136 で対象外とした。RI-139 では7敗因の代表シナリオを限定評価して fingerprint の分離を確認した。完全探索の再検討時は探索範囲と計算予算を定義した新しい RI を起票する。

## 4. バックログ運用

- IDは`RI-NN`の連番とし、欠番を再利用しない。
- ミューテーション改善はエピック`RI-{N}`（再ベースラインごと）と実装単位`RI-{N}-{GROUP}{SEQ}`（1PR = 1 GitHub Issue）に分ける。採番・進捗の正本はGitHub Issueとし、本ファイルへ番号予約や状態台帳を置かない。方針は[mutation-remediation.md](./mutation-remediation.md)を参照する。
- 状態は`未着手`、`進行中`、`保留（要判断）`、`完了`を使う。
- 1項目は原則1PRで完了できる大きさに分割する。エピックは受入条件と分割順を記載する。
- 完了時は個別節を削除し、上の完了要約と[spec-mapping.md](./spec-mapping.md)を更新する。
