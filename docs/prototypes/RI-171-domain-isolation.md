# RI-171: 障害の影響範囲を隔離する

対象 #567 / 親 #548。結論: **限定比較の仮説採用、本番統合保留**。人間のプレイ評価は未実施。

## 固定盤面と隔離契約

通常ランから隔離した純TS試作。RI-169 (#565 / PR #763) の復旧見積と障害型を共用するため、同PRの子として公開する。復旧方式の選択と、止める領域の選択は別ルール。本試作は修正のみを利用する。

seed `RI-171` は盤面識別子で乱数は使わない。領域はproduct/platformの2種、公開済み成果20、集中力6、期末8tick。各領域には価値8・Coding2→Review2の仕事と、未投入の予備仕事（価値4）がある。各領域1工数/tick、別枠の復旧担当1工数/tickを固定する。軽い障害は修正2工数・元の顧客損失1/tick、重大障害は修正6工数・損失4/tick。各盤面内で方針間の資源をそろえる。

- 隔離なし: 元領域と対象外がともに停止し、対象外にも顧客損失1/tickが波及する。
- 隔離: 集中力2でproductを隔離する。productのCoding/Review進捗と新規流入を停止し、platformの進捗・流入とその領域への延焼抑制を許可する。元の事故と顧客損失は続く。
- 修正: RI-169の見積どおり集中力1を払い、復旧担当が毎tick1工数を進める。復旧完了tickまで通常仕事を止め、次tickから再開する。
- 解除: 復旧完了後のみ集中力1で解除でき、停止した同じID・工程・残工数から再開する。解除できる資源がなければ隔離は続く。
- 重複隔離、未復旧の解除、解決済み事故の再隔離、未知/重複投入、対象外隔離、資源不足、期末操作は無消費で拒否する。流入は固定の予備仕事だけを一度投入でき、無限生成しない。

隔離は公開済み成果を減算しない。譲った出荷機会は未完仕事の価値、止めた容量は領域別の`blockedCapacity`（1枠が待ったtick）、隔離継続時の停止価値は`pausedValue`で確認する。未完のCoding/Review、隔離状態、事故と残復旧工数は期末にも残す。隔離・解除を繰り返して損失・投入費用・事故を消せない。

初回の「未隔離なら対象外も停止」は次節で波及確率と軽減率に分けて評価する。上の4行は対照であり、同じ比較を新しい根拠にはしない。

## 要因を一つずつ動かした比較

対照は初回と同じ資源である。seed `RI-171`、公開済み成果20、集中力6、期末8、product/platform、復旧担当1工数/tick、各領域の仕事は価値8でCoding2とReview2、予備は価値4。軽い障害は修正2・損失1、重い障害は修正6・損失4。固定戦略も初回と同じで、未隔離は修理してtickし、隔離はproductを隔離してから修理し、復旧後に解除する。再隔離はしない。人間のプレイ評価はしていない。本番採用の結論は出さない。

動かすのは一つの要因だけである。障害2件は同じ損失率の製品障害で、1件目の解決後に修理をもう一度始め集中力1を追加する。損失率は重ねない。再流入は、復旧開始時に隔離されていない領域の予備を1件入れる。隔離中の製品予備は拒否する。公開予測は、差引の顧客損失を修理時点の見積へ置き換える。見積は、その時点で隔離済みなら波及0、未隔離なら波及1を、復旧工数ぶん足す。依存は、tick開始時に製品の仕事が未完なら基盤を進めない。再発は、解決の次の状態で同じ障害が1回戻り、追加の修理はしない。未隔離も解決後に戻る。遅れは修理を先に行い、指定tickのあとで一度だけ隔離する。

波及確率と軽減率は抽選しない。波及が復旧の全期間に当たる試行と、全期間外れる試行の期待値である。軽減率1の隔離は当たる側の重みが0になる。差引の式は初回と同じで、公開予測の行だけ顧客損失を見積に置き換える。

軽い障害は、障害2件で波及損失4が追加集中力3を上回り、再流入では基盤だけが予備価値4を出荷して31対34になる。公開予測の見積は実損失と一致し、順位は変わらない。依存は両方の基盤出荷を止めるため、軽い障害の差は初回と同じ1のまま未隔離が上である。再発は両方の出荷を0にし、未隔離が1上のままである。重い障害の依存は基盤価値が0でも、避けた波及損失6が追加集中力3を上回り、隔離が-8で未隔離-11より上である。再発後も基盤の出荷8は復旧中に確定し、隔離が-40で未隔離-51より上である。

`domain-isolation-factor-comparison.json` に条件、入力列、差引、反転を記録し、テストが再計算と照合する。対照の入力列と差引は初回の比較JSONと一致する。rules が無い保存状態は初回の規則として再生する。

次に解く不確実性: 波及は全期間の当たり外れの期待値であり、復旧tickの一部だけ対象外が止まるときに基盤の4工数の出荷をまたいで3/14の境界が動くかは未検証。

## 本番境界と検証

Taskに領域属性を追加せず、通常firefight/介入表示・固定トラック・勝敗・WebGL停止契約を変更しない。通常保存/rulesetへは接続しない。本番採用時は領域と依存関係、隔離状態と未完仕事の繰越、復旧担当の編成容量、入力リプレイ・保存マイグレーションを別Issueで設計しrulesetを更新する。version 1の保存は信頼済み内部JSONのみ対応する。

初回は Dev Container Node 24 で親・子の対象ユニット・型チェック・lint・format:checkを検証した。要因比較は Node 24 で対象ユニット・入力再生・lint・format:checkを確認する。UI/Pixi変更なし。E2E・galleryは対象外。通常ランの本番、UI、保存、rulesetへは接続していない。
